# The ten-area classification

Read this before adding, moving or cross-listing topics in the library. The user chose ten broad areas to cover the whole software engineering profession. Their exact names, descriptions, example topics and available-learning links have one source of truth: [assets/library-areas.json](../assets/library-areas.json).

## Classification rules

- Keep the ten broad areas stable while adding topics beneath them. Their numbering is a navigation aid, not a prerequisite order.
- Give each course one primary home according to its main learning outcome. For a course spanning several areas, describe that breadth and surface relevant lessons in other areas through `related` links.
- Keep one authoritative copy of each lesson. A cross-listing points to the existing URL; it does not create a duplicate course or move its source files.
- Keep subjects separate from learning paths. Interview preparation, designing systems, and Senior → Staff → Principal are goal-based routes through material. New learning paths can connect several areas.
- Topic scope and delivered coverage are different. `topics` lists what belongs in an area, including future additions; `entries` and `related` link only to material that exists. An area without a dedicated course must say so, even when related lessons are available.
- Preserve saved links. The former `coding`, `systems`, `reliability`, `practice` and `leadership` home-page anchors remain as aliases; new links should use the descriptive area IDs.

## Add learning material

1. Follow [the course-authoring workflow](course-authoring.md) to create the requested material.
2. Choose the primary area in `assets/library-areas.json`. Add a course or path to its `entries`, with a title, root-relative local URL, description and optional metadata/resource links. Here “root-relative” means relative to the repository root, without a leading slash, so deployment under a GitHub Pages project path works.
3. Add focused `related` links in any other relevant areas. State what a linked lesson actually covers, rather than implying it teaches that area's entire scope.
4. Use an optional `md` field for a link's Markdown fallback when its published HTML page is generated by Jekyll. A link to an already generated HTML page needs no fallback.
5. Run `python3 scripts/build-library.py`. It validates catalog destinations, unique IDs and primary homes, then rebuilds the marked directory regions in `index.html` and `README.md` using only the Python standard library.
6. Check the generated navigation, links, coverage labels and layout. Preserve each `library-areas:start` / `library-areas:end` marker pair. Edit the catalog rather than the generated regions; the rest of each page remains editable normally.

The catalog is consumed at authoring time. The delivered directory is static HTML and works without fetching JSON or running a client-side application.
