Queue ↔ Topic — Delivery Topology Cheat Sheet

Compressed from Lesson 02•Print-friendly

The one-line test

Decide in five seconds

Work to be done once? → Queue (point-to-point).
Announcement others react to? → Topic (publish-subscribe / fan-out).

Core distinctions

Queue · point-to-pointTopic · publish-subscribe
Each message goes toExactly one consumerA copy to every subscriber
Add more consumers →Shared work (competing consumers, faster)More copies (each gets everything)
IntentDo this taskThis happened; react if you care
Scaling leverMore consumers on the queueIndependent subscribers, scaled separately
Never forget

Competing consumers work only on a queue. Extra consumers on a topic = duplicate processing, not shared load. ("Why did we send 10 emails?")

Kafka: get both from one topic

  • One consumer group = competing consumers (point-to-point). Partitions split across members.
  • Many consumer groups = fan-out (publish-subscribe). Each group sees every message.
  • Spring lever: same groupId → shared work; different groupId → each gets a copy.
  • Cap: active consumers per group ≤ partition count. Extra consumers idle.
  • Order & key: order holds only within a partition; the message key picks the partition.

Same shape, every broker

BrokerHandled onceFan-out
KafkaOne consumer groupMany consumer groups
RabbitMQConsumers on one queueFanout/topic exchange → many queues
AWSSQS queueSNS topic → many SQS/HTTP
RedisStream + consumer groupPub/Sub, or multiple stream groups
PulsarShared / Key_Shared subscriptionMultiple subscriptions on a topic

Spring Kafka snippets

// Competing consumers — scale by running more instances
@KafkaListener(topics = ["order.placed"], groupId = "fulfillment")
fun handle(e: OrderPlaced) = fulfillment.reserveStock(e)

// Fan-out — a different groupId gets its own full copy
@KafkaListener(topics = ["order.placed"], groupId = "analytics")
fun record(e: OrderPlaced) = analytics.record(e)
