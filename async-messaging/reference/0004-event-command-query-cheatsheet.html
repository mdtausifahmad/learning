Event / Command / Query — Intent Cheat Sheet

Compressed from Lesson 04•Print-friendly

The one-line test

Read the name; know the intent

Imperative (ShipOrder) → Command.
Past tense (OrderShipped) → Event.
Interrogative (GetOrderStatus) → Query.

Side-by-side

CommandEventQuery
Says"Do this""This happened""Tell me this"
NameImperativePast tenseInterrogative
HandlersOne ownerZero to manyOne responder
Reply?Maybe ack/resultNoYes — the data
ChannelQueue (p2p)Topic (pub/sub)Sync request/reply
Who decides the reactionThe senderEach consumerThe responder
Coupling points…Sender → receiver's capabilityConsumer → producer's factCaller ↔ responder contract

Why it matters

  • Events invert coupling → extensibility. Add a reaction by subscribing; the producer never changes.
  • Commands centralize the decision. Use when you genuinely depend on a specific action being done.
  • Queries need answers. Keep them synchronous; async is the wrong tool.
The honesty test (Fowler)

An event that exists only to make one specific consumer act is a passive-aggressive command — hidden coupling + ambiguous ownership. If you depend on the action, send a command and name it as one.

Kotlin conventions

data class ShipOrder(val orderId: String, val address: Address)         // command
data class OrderPlaced(val orderId: String, val total: Money)           // event
data class GetOrderStatus(val orderId: String)                          // query

// same groupId shares a command queue; different groupIds fan an event out
@KafkaListener(topics = ["shipping.commands"], groupId = "shipping")    // one owner acts
@KafkaListener(topics = ["order.events"],      groupId = "loyalty")     // one of many reactors
