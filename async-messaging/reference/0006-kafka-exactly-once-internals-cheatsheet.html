Idempotent producer (how numbering works)

  • Broker assigns a Producer ID (PID); each batch carries PID + a monotonic sequence number per partition.
  • Leader tracks the highest accepted seq per (PID, partition). Repeat seq → dropped, still acked. Gap → OutOfOrderSequenceException.
  • Sequence is persisted to the replicated log → dedup survives leader failover. "Like TCP."
  • Gives exactly-once in order, per partition, for one producer's retries only.
  • Needs acks=all, max.in.flight ≤ 5. Default-on since Kafka 3.0.

Transactions

  • Offset commit is just another topic write → put output B + offset of A in one transaction = atomic read-process-write.
  • Zombie fencing: transactional.id + bumped epoch; older-epoch producer rejected.
  • Coordinator writes commit/abort control markers into each touched partition.

read_committed (why it matters)

  • Txn messages are appended before the commit/abort decision → the log may hold soon-to-be-aborted data.
  • read_uncommitted (DEFAULT) delivers them immediately → dirty reads of aborted data.
  • read_committed reads only up to the Last Stable Offset (LSO), withholds open-txn messages, filters aborted via markers.
Gotchas

Default is read_uncommitted — forgetting to set read_committed silently loses exactly-once. A hung transaction stalls all read_committed consumers at the LSO until it commits/aborts/times out. None of this helps external side effects → still Route A (at-least-once + idempotency).
