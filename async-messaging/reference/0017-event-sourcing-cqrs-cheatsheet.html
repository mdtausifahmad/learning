Event Sourcing & CQRS — Cheat Sheet

Compressed from Lesson 17•Print-friendly

Event sourcing

Core

Store the sequence of events as the source of truth; derive current state by replaying (folding) them. Append, never mutate. Saving an event is atomic → no dual write (L14).

  • Free audit trail + temporal queries (replay to any point) + rebuild/replay.
  • Event store also acts as a broker (subscribe to events).
  • Snapshots = periodic saved state so you don't replay from zero.
  • Costs: derive-to-query, schema evolution critical (events live forever, L16), replay + external effects = non-determinism, hard deletes (GDPR).

CQRS

Core

Different model to write than to read. Command side enforces invariants; read side(s) are denormalized per query. Projections build read models from the event stream.

  • Read & write scale independently; multiple read models (SQL view, search index, cache).
  • Eventually consistent (read after write may lag) — design the UX.
The big caution (Fowler)

"For most systems CQRS adds risky complexity." Same for event sourcing. Use in complex, audit-heavy domains (finance/ledgers) and scoped contexts — NOT as a default for CRUD.

fun rebuild(events: List<Event>) = events.fold(Account()) { a, e -> a.apply(e) }   // ES
@KafkaListener("account.events") fun project(e: Event) = view.apply(e)             // CQRS projection
