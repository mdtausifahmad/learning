Async & Messaging · Reference 07

Operating Kafka Exactly-Once — Cheat Sheet

Compressed from Lesson 07•Print-friendly

1. Hung transaction = phantom lag

  • read_committed consumers can't advance past an open txn → position pinned at the LSO.
  • Signature: records-lag-max climbs steadily, 0 errors, ~0 throughput, then drops in one step.
  • Confirm: log-end-offset − LSO gap is wide & growing (stuck txn, not a slow consumer).
  • Self-heal: transaction.timeout.ms (capped by broker transaction.max.timeout.ms) → coordinator aborts → LSO jumps.

2. transactional.id rules

  • Stable across restarts (so the restart fences its own zombie via a bumped epoch).
  • Never shared by two active producers (they'd fence each other).
  • Pre-KIP-447: one id per input partition (Kafka Streams: appId+task).
  • EOSMode.V2 / Spring 3.0+: just a transactionIdPrefix unique per instance (group-metadata fencing).
  • Each id hashes to exactly one transaction coordinator.
  • Gotcha: idle past transactional.id.expiration.ms (7d) → fenced; set producer factory maxAge lower.
producer: { transaction-id-prefix: ${HOSTNAME}-tx-, properties: { transaction.timeout.ms: 60000 } }
consumer: { isolation-level: read_committed }

3. Commit-interval dial

  • Txn overhead is per-commit, not per-record → throughput = records per commit.
  • Benchmark: 1 KB records, commit every 100 ms → ~3% throughput hit. Shorter/smaller → worse.
  • Longer interval → higher throughput but higher end-to-end latency (read_committed waits for commit).
  • Consumer side: no throughput penalty (zero-copy preserved) — the cost is latency only.
  • Spring trap: a transaction per record is worst-case → use batch listeners / bigger max.poll.records.
Remember

The dial trades producer throughput ↔ end-to-end latency. Batch more per transaction for throughput; commit more often for latency.
