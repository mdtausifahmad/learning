Kafka Consumer Group Internals — Cheat Sheet

Compressed from Lesson 03•Print-friendly

The one invariant

Memorize this

Within a group, one partition → exactly one consumer. Max useful consumers = partition count. Extras sit idle (as hot standbys).

Why (the design reason)

  • Ordering — a partition is one append-only log read by one cursor; order holds only within a partition.
  • Offsets — one committed offset per (group, partition) in __consumer_offsets; one owner = one writer, no races.

The protocol (how it's enforced)

  1. FindCoordinator — hash(group.id) % __consumer_offsets partitions → a broker becomes group coordinator.
  2. JoinGroup — coordinator elects a group leader (first to join); gives it the member + subscription list.
  3. SyncGroup — the leader computes the assignment client-side; coordinator relays each member's slice. (Idle consumers get nothing here.)
  4. Heartbeat — miss session.timeout.ms → declared dead → rebalance → partitions move to survivors.

The broker only knows membership; assignment is an embedded, client-side protocol.

Rebalancing

  • Eager (stop-the-world): all consumers revoke all partitions, then reassign. Disruptive.
  • Incremental Cooperative (CooperativeStickyAssignor): only moving partitions are revoked; the rest keep processing.
  • Static membership (group.instance.id): quick restarts skip the rebalance entirely.

Assignment strategies

StrategyPick when
RangeAssignor (default)You need co-partitioned joins across topics.
RoundRobinAssignorYou want the most even spread.
StickyAssignorEven + minimal churn across rebalances.
CooperativeStickyAssignorLarge / frequently-scaled groups (modern default).

Pros ↔ Cons

WinsCosts
Brokers stay dumb → scale to many groupsParallelism capped by partition count (set up front)
Per-partition ordering, single-writer offsetsOver-partitioning: more files/memory, slower failover & rebalance
Automatic failover to survivors/standbysChanging partitions reshuffles key→partition mapping
Elastic scaling up to partitions, no code changeHot partitions (key skew) overload one consumer; rebalances pause work

Spring Kafka levers

setConcurrency(4)                  // consumer threads in this instance (total = instances × concurrency)
partition.assignment.strategy = CooperativeStickyAssignor
session.timeout.ms = 45000         // heartbeat miss window -> rebalance
max.poll.interval.ms = 300000      // slow processing also triggers rebalance
group.instance.id = ${HOSTNAME}    // static membership
Field diagnosis

"Scaled pods, throughput flat" → consumers > partitions → extras idle. Fix = more partitions, not more pods.
