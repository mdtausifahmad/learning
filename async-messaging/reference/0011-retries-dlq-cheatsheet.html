Retries & Dead-Letter Queues — Cheat Sheet

Compressed from Lesson 11•Print-friendly

Step 1: classify the failure

Transient → retryPermanent → DLQ now
Timeout, network blipMalformed / bad schema
Downstream 503 / rate limitBusiness-rule violation
DB deadlockHandler bug

Poison message

Head-of-line blocking

A message that always fails, retried in place, blocks everything behind it. Bound the retries, then move it to a DLQ to unblock the flow.

Retry strategy

  • Bounded attempts (3–5), then dead-letter. Never infinite.
  • Exponential backoff + jitter (avoid thundering herd).
  • Blocking retry = preserves order, risks HoL blocking. Non-blocking (retry topics) = keeps flow, breaks that message's order.

DLQ per broker

BrokerMechanism
SQSRedrive policy + maxReceiveCount; redrive back out
RabbitMQx-dead-letter-exchange (nack/TTL/length → DLX)
KafkaDeadLetterPublishingRecoverer / @RetryableTopic / Connect DLQ
PulsarRetry-letter + dead-letter topic

Never forget

  • DLQ = workflow: monitor · alarm · triage · replay (redrive). Store error + attempts. Watch for replay loops.
  • Retries ⇒ duplicates ⇒ consumer must be idempotent (L08).
  • Retries/DLQ break order (L09). Don't DLQ a FIFO queue if order is sacred.
// Kafka blocking retry + DLT
DefaultErrorHandler(DeadLetterPublishingRecoverer(template),
    ExponentialBackOffWithMaxRetries(3)).apply {
    addNotRetryableExceptions(IllegalArgumentException::class.java)   // permanent → DLT now
}
