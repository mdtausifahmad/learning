Async & Messaging · Reference 09

Ordering & Partitioning — Cheat Sheet

Compressed from Lesson 09•Print-friendly

The core truth

Memorize this

No global order — only per-partition order. Same key → same partition → strict per-key order. No key → round-robin → order lost. Design for per-entity order, not global.

Keys & routing

  • Partition = hash(key) % partitionCount. Same key ⇒ same partition ⇒ ordered.
  • No key ⇒ round-robin ⇒ a key's messages scatter ⇒ no order.
  • Choose the key = the smallest entity whose events must stay ordered (accountId, orderId).

The trade-off

Ordering ↔ parallelism

Parallelism ceiling = partition count. Ordering unit = key. Coarse key = tight order but low parallelism + hot partitions. Fine key = high parallelism, order only per entity.

How order breaks even with a key

  • Retries: max.in.flight > 1 + no idempotence can reorder → set enable.idempotence=true (or max.in.flight=1).
  • Repartitioning: changing partition count remaps hash % N → order breaks across the change.
  • Hot key: one dominant key overloads its partition.
  • Consumer-side: parallel processing within a partition, or requeue-on-fail, reorders. Process a partition sequentially.
kafkaTemplate.send("order.events", order.customerId, event)   // key = ordering boundary
producer.properties.enable.idempotence = true                 // order under retries
