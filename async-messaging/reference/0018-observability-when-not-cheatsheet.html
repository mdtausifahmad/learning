Three pillars for async

  • Tracing: propagate the W3C traceparent (trace id + span id) in message headers → producer/consumer spans stitch into one trace. Defeats the flow-visibility trap (L13).
  • Metrics: see below. Alert & autoscale on lag (KEDA), not CPU.
  • Logs: structured + the same correlation id as traces.

When NOT to use messaging

Choose sync / a DB instead when…

You need an immediate answer to continue · you need read-your-writes consistency now · simple CRUD / one service / low volume · you're querying/updating messages (that's a DB) · your "events" are disguised sync calls (distributed monolith) · ES/CQRS/saga on a simple domain.

Use messaging when…

You genuinely need decoupling in time, fan-out, load leveling, or outage resilience — AND can afford a broker + eventual consistency + the ops. Otherwise, choose boring.

Runbook (rehearse these)

  • Lag climbing → scale consumers / find stuck partition or hung txn.
  • DLQ filling → triage + redrive (L11).
  • Rebalance storm → static membership + cooperative rebalancing (L07).
  • Schema break → compatibility gate in CI (L16).
