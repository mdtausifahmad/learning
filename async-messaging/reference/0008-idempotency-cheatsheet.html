Idempotency & Deduplication — Cheat Sheet

Compressed from Lesson 08•Print-friendly

The decision order

Try these in order

1. Can the write be naturally idempotent (upsert / set / delete-by-id)? Use that.
2. If not → synthetic: stable key + dedup store, atomic with the side effect.
3. External side effect → push the key into the API's Idempotency-Key.

Natural vs not

Idempotent (replay-safe)Not (needs dedup)
SET status='PAID'balance = balance + 10
UPSERT by stable idINSERT new row
DELETE WHERE id = xappend / send email / charge / emit

Choosing the key

  • Best: producer-generated UUID, made once, carried in a header — stable across retries.
  • Good: business key (orderId), if one message per action.
  • Fragile: payload hash (timestamps/order break it).
  • Never: broker offset / delivery id (a retry gets a new one) or receipt time.

Dedup store rules

  • Record the key in the same transaction as the side effect.
  • Unique constraint on the key = race backstop (or INSERT … ON CONFLICT DO NOTHING).
  • Window must exceed worst-case redelivery: retries + DLQ replay + lag + retention.
@KafkaListener(topics=["payments"], groupId="ledger")
@Transactional
fun on(rec: ConsumerRecord<String, PaymentRequested>) {
    val key = String(rec.headers().lastHeader("idempotency-key").value())
    if (processed.existsById(key)) return          // skip duplicate
    ledger.credit(rec.value())                     // side effect
    processed.save(ProcessedMessage(key))          // remember, atomically
}

Remember

Native dedup = short safety net. Durable correctness = app-level idempotent consumer with a key you control. If the side effect emits another message, dedup that too (outbox).
