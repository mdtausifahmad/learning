Choreography vs Orchestration — Cheat Sheet

Compressed from Lesson 13•Print-friendly

The two styles

Core

Choreography: services publish events; others react. No coordinator; flow emerges.
Orchestration: a coordinator sends commands + awaits replies; flow is central.
(Choreography = events (L04); orchestration = commands.)

Trade-offs

ChoreographyOrchestration
CoordinationEvents, each service decidesCommands, coordinator decides
CouplingLoose runtime; diffuse processSimple services; coordinator knows all
Flow visibilityImplicit (traces only)Explicit (one place)
Add a stepSubscribe a consumerEdit the orchestrator
CompensationScatteredCentralized (sagas)
Main riskNobody sees the whole flowGod-orchestrator bottleneck
Fowler's trap

Choreography's flow "is not explicit in any program text… the only way to figure out this flow is from monitoring a live system." If you choreograph, invest in distributed tracing (correlation IDs) + an event catalog.

Choose

  • Choreography: simple, few steps, autonomous teams, frequent new reactions.
  • Orchestration: complex, ordered, conditional, needs visibility + compensation.
  • Hybrid: orchestrate the critical transaction, choreograph peripheral reactions.
  • Tools: broker + contracts (choreo) · Temporal / Step Functions / Camunda / Conductor (orch).

Next: a step must atomically update its DB and publish → transactional outbox; multi-step rollback → saga.
