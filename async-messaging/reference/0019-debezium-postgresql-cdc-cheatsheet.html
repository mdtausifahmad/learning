Debezium ⇄ PostgreSQL CDC — Cheat Sheet

Compressed from Lesson 19•Print-friendly
The whole mechanism in one line

Commit → WAL LSN → logical decoding → pgoutput/publication → logical slot → Debezium → sink/offset commit → flush LSN feedback → slot advances. Debezium tails PostgreSQL’s WAL; it does not poll tables or depend on triggers.

Position is the correctness currency

PositionMeaningWhy it matters
LSN64-bit monotonically increasing byte offset into WAL; displayed as hex X/XCommon position for WAL, slots, and Debezium source offsets
restart_lsnOldest WAL a slot might still requirePrevents recycling WAL before the connector can read it
confirmed_flush_lsnPosition the consumer has confirmed receivedMoves only after safe downstream delivery/offset commit feedback
Debezium offsetStored source LSN plus processing/commit fieldsLets a restart resume or safely replay records

Debezium PostgreSQL connector anatomy

Primary classes in the pinned source: PostgresConnector, PostgresConnectorTask, PostgresChangeEventSourceCoordinator, PostgresSnapshotChangeEventSource, PostgresStreamingChangeEventSource, PostgresReplicationConnection, PostgresOffsetContext, and SourceInfo.

  1. Kafka Connect starts the task; it validates/creates slot and publication.
  2. The coordinator performs pre-snapshot catch-up, snapshot, then streaming on a background executor.
  3. The snapshot source emits READ records; streaming opens START_REPLICATION SLOT … LOGICAL.
  4. JDBC PGReplicationStream.readPending() sends bytes to a pluggable decoder.
  5. Decoder handles BEGIN, COMMIT, RELATION, ORIGIN, MESSAGE, INSERT, UPDATE, DELETE, TRUNCATE.
  6. Records enter bounded ChangeEventQueue; Kafka Connect drains it via poll().
  7. After delivery and offset commit, flushLsn() sends standby-status feedback, advancing the slot.

Ordering and task count

The PostgreSQL connector creates one task because slot streaming is serial. That makes its source-task emission serial; topic keys then preserve Kafka ordering per key/partition, not as a global order across tables, topics, or keys. Do not attempt to scale a single slot by increasing tasks.max.

Snapshots

A new slot cannot see rows that existed beforehand. The initial snapshot opens a consistent transaction, captures the start LSN, scans rows as op: r, then streams WAL starting at that captured LSN. Changes made during the scan therefore appear in the subsequent live stream, not in a gap.

ModeMeaning
initialSnapshot only without prior offsets, then stream
initial_onlySnapshot then stop
alwaysSnapshot each start; useful after loss/failover re-baseline
no_dataDo not snapshot rows
when_neededSnapshot when offsets are missing or recorded WAL is unavailable
configuration_based / customFine-grained community configuration / custom Snapshotter SPI
  • New slots use exported snapshot + REPEATABLE READ; ACCESS SHARE blocks DDL, not writes.
  • Incremental snapshots are on-demand/resumable: signal table → PK-sorted chunks → low watermark → buffered READs → high watermark.
  • If a concurrent streamed change shares a key with a buffered READ, the streamed change wins and the READ is discarded.
  • Read-only incremental snapshots on PostgreSQL 13+ can use in-progress transaction IDs as watermarks.

Event contract

{
  "before": { "id": 42 },       // null for create; old key/row on update/delete
  "after":  { "id": 42, "status": "PAID" }, // null for delete
  "op": "u",                    // r / c / u / d / t / m
  "source": { "db": "…", "schema": "…", "table": "…", "txId": 7,
              "lsn": "16/B374D848", "snapshot": false, "sequence": "[…]" },
  "transaction": { "…": "…" },
  "ts_ms": 0                     // also ts_us / ts_ns
}
  • Key = primary key, or an equivalent unique identity; otherwise null.
  • DELETE emits op:d then, by default, a same-key null-value tombstone for compaction.
  • Primary-key update = DELETE + tombstone under old key, then CREATE under new key.
  • Under DEFAULT identity, unchanged TOAST values may become __debezium_unavailable_value.
  • Data mapping depends on decimal, time-precision, hstore, and related connector options.

Runtimes, transforms, topics, delivery

RuntimeOffsets / sinkResponsibility
Kafka ConnectInternal compacted Kafka topics / Kafka topicsRecommended for Kafka; workers redistribute on failure
Debezium ServerPluggable store (file default, or e.g. Redis/Iceberg) / chosen sinkStandalone Quarkus bridge for non-Kafka sinks
Embedded EngineApplication-owned / callbackApplication owns fault tolerance and operations
  • Normal promise: at-least-once. A crash after sink delivery but before offset flush replays records; deduplicate with source position / idempotent effects.
  • Kafka Connect optional exactly-once-source support is a separate, configured worker capability; do not assume it from ordinary CDC behavior.
  • Outbox Event Router maps outbox id/type/aggregate id/payload to headers, topic, key, and value; it ignores outbox DELETEs.
  • Extract New Record State unwraps after for sinks; retain fields such as op, table, LSN, and source time when needed.
  • Default topic form = topic.prefix.schema.table; prefix also scopes source name and transaction metadata topic.

  • heartbeat.interval.ms helps when captured tables are quiet in an otherwise active captured database.
  • For a cross-database idle captured DB, use heartbeat.action.query to write a heartbeat inside it, and include that table in the publication.
  • Restart normally resumes from stored LSN if the slot and WAL remain. If unavailable, when_needed / always re-snapshots.
  • Retry controls include retriable.restart.connector.wait.ms, errors.max.retries, slot.max.retries, slot.retry.delay.ms, status.update.interval.ms, and offset.mismatch.strategy.
  • PostgreSQL ≤15 logical slots are not natively propagated on failover. PG 17+ failover slots, managed services, and Patroni permanent-slot workflows have different recovery designs.

Outbox and Zalando FES case study

Transactional outbox: write business state and an outbox row in one local transaction; Debezium tails the committed outbox WAL record; the relay may duplicate only on crash recovery, so consumers remain idempotent. A same-transaction INSERT then DELETE can leave the outbox table empty while WAL still preserves the INSERT; Debezium’s Outbox Event Router ignores the DELETE.

The supplied report describes Zalando FES as: service/outbox → wal_level=logical + pgoutput/publication/permanent slot → fes-debezium-connector → jq or PostgresWalToGenericNakadiEvent transform → Nakadi event type, with SQS/Nakadi DLQ on failure. The report names customs-data-checker as a concrete internal instance (fes_cdc slot, replication user, named publication, jq transform, SQS DLQ) and says the customs meta-repo itself contains no Debezium implementation. Those are internal, deployment-specific claims.

Version and evidence note

The source lesson was based on a pinned PostgreSQL development commit / current PostgreSQL docs and a Debezium 3.7.0-SNAPSHOT-era commit. Plugin defaults, legacy snapshot mode names, metrics, and failover capabilities can drift. Recheck the official documentation against the exact version you deploy.
