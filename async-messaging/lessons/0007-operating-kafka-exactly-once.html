Operating Kafka Exactly-Once — Lag, transactional.id & the Commit Dial

◷ ~15 min read • Level: Staff / Operations • Deepens: Lesson 06

Lesson 06 explained how EOS works. This one is about running it at 3 a.m. when something’s wrong — the three things that actually bite teams in production: a stuck transaction masquerading as consumer lag, getting transactional.id wrong, and the throughput hit from committing too often. This is the difference between enabling exactly-once and owning it.

1. Why a hung transaction looks like consumer lag

Recall from Lesson 06: a read_committed consumer may not advance past an open transaction — the broker holds its read position at the Last Stable Offset (LSO). So if a producer opens a transaction and then hangs (GC pause, stuck RPC, a bug between beginTransaction and commitTransaction), the LSO freezes while new records pile up behind it.

How to read the metrics

The consumer’s records-lag-max rises steadily, yet there are no processing errors and throughput is near zero — the consumer isn’t slow, it’s blocked. Confirm by comparing the partition’s log-end-offset to its LSO: a wide, growing gap means an open transaction, not a backlog. Real lag (slow consumer / high produce rate) looks different: throughput is high and lag tracks load. A stuck-transaction lag clears in a single step when the producer commits/aborts or the transaction times out.

The safety net is transaction.timeout.ms (producer-side; the coordinator aborts a transaction open longer than this), capped by the broker’s transaction.max.timeout.ms. Set it tight enough that a wedged producer self-heals quickly, but longer than your worst legitimate transaction — or you’ll abort healthy work.

Watch it: the phantom lag of a hung transaction

Step through it (← / → keys work). The consumer’s read cursor stays pinned at the LSO while the log keeps growing — so lag climbs with the consumer perfectly healthy — until the timeout clears it in one jump.

2. Choosing transactional.id correctly

The id has two hard requirements, both rooted in zombie fencing (Lesson 06):

  • Stable across restarts — a restarted instance must re-register the same id so it bumps the epoch and fences its own zombie predecessor. A random id per start defeats fencing (the old zombie is never fenced).
  • Not shared by two concurrently-active producers — same id means one fences the other, so they’d repeatedly kill each other.

Historically that forced a subtle rule: Confluent’s guidance was that “the input topics and partitions in the read-process-write cycle is always the same for a given transactional.id” — i.e. one id per input partition, statically encoded (which is exactly what Kafka Streams does with applicationId + task). Otherwise a partition could move from id T0 to T1 with no fencing between them, and messages leak through.

The modern rule (EOSMode.V2 / Spring 3.0+)

Since Kafka 2.5 (KIP-447), fencing uses consumer-group metadata instead of the id-per-partition trick. Spring for Apache Kafka states it plainly: the per-partition id is “not necessary anymore, with EOSMode.V2 being the only option starting with 3.0” — you just need a transactionIdPrefix that is unique per application instance. Spring appends a counter to build each producer’s transactional.id. 

spring:
  kafka:
    producer:
      transaction-id-prefix: ${HOSTNAME}-tx-   # MUST be unique per instance (EOSMode.V2)
      properties:
        transaction.timeout.ms: 60000          # coordinator aborts a txn open longer than this
    consumer:
      isolation-level: read_committed           # or you silently lose exactly-once (Lesson 06)
Two operational gotchas

(a) Idle producer fencing. A transactional producer that sits idle past the broker’s transactional.id.expiration.ms (default 7 days) can get a ProducerFencedException with no rebalance. Spring’s fix: set the producer factory’s maxAge below that expiration so it refreshes the producer. (b) Coordinator mapping. Every transactional.id hashes to one __transaction_state partition, so exactly one broker (coordinator) owns it — a non-unique prefix quietly serializes or fences instances you meant to run in parallel.

3. The commit-interval dial: throughput vs latency

The single most important tuning insight for transactional throughput: transaction overhead is per-commit, not per-record. Each commit pays for registering partitions with the coordinator, writing a commit marker to every partition in the transaction, and 2–3 writes to the transaction log. That cost is fixed regardless of how many records the transaction carried. Therefore:

Confluent’s benchmark

“The overhead is independent of the number of messages written as part of a transaction. So the key to having higher throughput is to include a larger number of messages per transaction.” In practice, for 1 KB records at max throughput, committing every 100 ms yields only a ~3% throughput hit. Smaller messages or shorter commit intervals degrade more.

Commit intervalThroughputEnd-to-end latencyReprocessed on crash
Short (few records/txn)Low — per-commit overhead dominatesLow — consumers see data soonerLittle — small unit of work
Long (many records/txn)High — overhead amortizedHigh — read_committed waits for the commitMore — a whole transaction re-done

Note the asymmetry from Lesson 06: the consumer side has essentially no throughput penalty for read_committed (zero-copy is preserved; it simply isn’t allowed past the LSO). So the dial trades producer throughput against end-to-end latency — not consumer CPU.

The Spring trap: a transaction per record

A record-based transactional listener can wrap each record in its own transaction — the worst case for the “records per commit” rule. To amortize, process in batches (batch listeners / larger max.poll.records) so one transaction carries many records. That single change often recovers most of the throughput. Kafka Streams, for reference, defaults to a 100 ms commit interval under EOS precisely to balance this dial.
