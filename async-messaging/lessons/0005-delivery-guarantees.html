Async & Messaging · Lesson 05

Delivery Guarantees — At-Most, At-Least, Exactly-Once

◷ ~16 min read • Level: Core → Staff • Builds on: Lesson 03 (offsets)

This is the lesson that earns you credibility in a design review. In Lesson 03 you learned that a consumer records progress by committing an offset. Delivery guarantees are entirely about one question: do you commit that offset before or after you do the work? Get precise here and you’ll stop saying “we use a queue” and start saying “this path is at-least-once with an idempotent consumer.”

1. The root cause: the acknowledgement can be lost

Every message flow has two separate actions: (A) do the work (process the message / write the side effect) and (B) record that it’s done (commit the offset, or ack). In a distributed system these touch two different systems — your app and the broker’s offset store — and you cannot make them atomic for free. A crash can land between them.

As Confluent’s Neha Narkhede puts it: a producer that gets no ack “is forced to assume that the message was not written successfully and to retry it” — and if the broker had actually written it, that retry duplicates the message. The ack’s ambiguity is unavoidable. So you must choose which failure you tolerate. That choice is the delivery guarantee.

2. The two ordinary options (and their crash windows)

  • At-most-once — commit/ack first, then process (or fire-and-forget). A crash in the gap means the work is skipped. No duplicates, possible loss.
  • At-least-once — process first, then commit. A crash in the gap means redelivery. No loss, possible duplicates. This is the sane default and what most systems run.
This applies on both sides

The same fork exists producer→broker (retry after a lost ack → duplicate write; or don’t retry → possible loss) and broker→consumer (commit ordering, as above). A robust design reasons about both hops, not just the consumer.

4. Exactly-once, honestly

Everyone wants a third option: process each message exactly once. The uncomfortable truth, which you should be able to state plainly at staff level:

The staff one-liner

Exactly-once delivery is essentially impossible; exactly-once processing (“effectively-once”) is achievable — but only with cooperation between the messaging system and your application. As Narkhede notes, it “requires a cooperation between the messaging system itself and the application producing and consuming the messages.” You never get it for free; you pay in idempotency logic or transactional coordination.

There are exactly two legitimate routes to effectively-once:

Route A — At-least-once + idempotent consumer (the general answer)

Whenever your side effect touches an external system (a database, an email provider, a payment API), this is the route. Accept that delivery duplicates, and make processing duplicate-proof. Richardson’s Idempotent Consumer pattern: record processed message IDs, and skip anything you’ve seen. 

@Component
class PaymentListener(
    private val processed: ProcessedMessageRepository,   // PK = (groupId, messageId)
    private val payments: PaymentService,
) {
    // Manual ack = at-least-once: advance the offset only AFTER the work succeeds.
    @KafkaListener(topics = ["order.events"], groupId = "payments")
    @Transactional                                       // ONE db tx: dedup mark + side effect
    fun on(rec: ConsumerRecord<String, OrderPlaced>, ack: Acknowledgment) {
        val id = ProcessedId("payments", rec.key())      // a stable, unique message id
        if (processed.existsById(id)) { ack.acknowledge(); return }   // duplicate -> skip

        payments.charge(rec.value())                     // the real, non-idempotent side effect
        processed.save(ProcessedMessage(id))             // mark done, atomically with the charge
        ack.acknowledge()                                // now safe to advance the offset
    }
}
Why this actually works (the subtlety)

The charge and the mark-done commit together in one database transaction. The Kafka offset commit (ack) is separate. If you crash after the DB commit but before the ack, the message is redelivered — but now existsById finds the id and you skip. The unique primary key on the processed-messages table is the backstop against two concurrent deliveries racing the check. The dedup record exists precisely because you can’t put the side effect and the offset in one atomic step.

Often you don’t even need a separate table: a naturally idempotent side effect — an UPSERT keyed by order id, or SET status = 'PAID' — is duplicate-proof by construction. Prefer that when you can.

Route B — Kafka EOS (only for read-process-write inside Kafka)

When your input and output are both Kafka, Kafka’s own exactly-once semantics (added in 0.11) do the cooperation for you, via two mechanisms:

  • Idempotent producer — each producer gets a PID + per-partition sequence numbers, so the broker silently drops retried duplicates. Turn on with enable.idempotence=true, acks=all.
  • Transactions — the produced output and the consumed input’s offset commit are written in one atomic transaction; consumers with isolation.level=read_committed never see aborted output. This is what keeps “consumed offsets in sync with produced output.”
# application.yml — Kafka EOS for a read-process-write stage
spring:
  kafka:
    producer:
      acks: all
      transaction-id-prefix: tx-enrich-     # enables Kafka transactions
      properties: { enable.idempotence: true }
    consumer:
      isolation-level: read_committed        # ignore uncommitted/aborted records
// With a KafkaTransactionManager, the send + offset commit are atomic.
@KafkaListener(topics = ["orders"], groupId = "enrich")
@Transactional
fun enrich(order: Order) {
    kafkaTemplate.send("orders.enriched", order.id, enrich(order))  // atomic with the input offset
}
The boundary that trips people up

Kafka EOS is exactly-once within Kafka. The moment your consumer calls an external API (charge a card, send an email), you are back to at-least-once + idempotency — a Kafka transaction cannot roll back a real-world credit-card charge. Don’t let “we enabled exactly-once” lull you into skipping idempotency at external boundaries.

5. Pros, cons, and when to pick each

SemanticFails byCost you payChoose when
At-most-onceLosing messagesCheapest, simplestLoss is acceptable: metrics, logs, live telemetry
At-least-onceDuplicatesYou must make processing idempotentThe default for almost everything
Exactly-once
(effectively)		Complexity / throughputDedup logic (Route A) or tx coordination + latency (Route B)Money, inventory, anything where a dup is a real bug
The heuristic to carry

External side effects → at-least-once + idempotency, always. Kafka→Kafka stream processing → EOS. At-most-once → only when a dropped message is cheaper than a duplicate. There is no free exactly-once — you pay in dedup logic or in transactional throughput.
