Async & Messaging · Lesson 01

Why Async? The Problem Messaging Solves

◷ ~10 min read • Level: Foundations • Prereq: you can build a synchronous service

You’ve lived in synchronous request/response land. This lesson gives you the one mental shift the rest of your journey to staff-level rests on: why we put a message between two components in the first place. Everything later — delivery guarantees, ordering, sagas — is a consequence of this single move.

1. Start where you are: the synchronous baseline

Here is a shape you know well. An order service, when it takes an order, also needs to send a confirmation email. The obvious way — the way you’ve probably always written it — is a direct call: 

@Service
class OrderService(
    private val orderRepository: OrderRepository,
    private val emailClient: EmailClient,          // e.g. a Feign / RestClient call
) {
    fun placeOrder(order: Order): String {
        orderRepository.save(order)
        emailClient.sendConfirmation(order)        // ← blocks until Email replies
        return "OK"
    }
}

This is synchronous communication: the caller sends a request and waits, holding its thread, until the callee answers. Simple, direct, easy to reason about. And for a lot of code, exactly right.

But notice what you’ve quietly assumed: that the Email service is up right now, fast enough right now, and able to keep up right now. That assumption is called temporal coupling — the two services must be healthy at the very same instant for the request to succeed.

2. Where the synchronous model hurts

Temporal coupling is fine until it isn’t. Four cracks appear as systems grow:

When……the synchronous call
Email is down Your order fails too — even though the order itself was fine. Failure cascades from a non-critical dependency into a critical path.
Email is slow Your caller’s latency = its own work plus the slowest thing it calls. Waits stack up and threads pile on.
Traffic spikes A burst of orders becomes an identical burst hammering Email in real time. There is no shock absorber; the weakest downstream buckles.
You add a 3rd, 4th consumer Analytics, inventory, loyalty… the order service must now know about, call, and wait for every one of them. Coupling grows with each addition.

The root issue isn’t any single failure — it’s that the sender’s fate is tied to the receiver’s, in real time.

3. The move: put a durable buffer in between

Asynchronous messaging makes one structural change. Instead of calling the consumer directly, the producer hands a message to a message broker — a piece of infrastructure whose whole job is to durably hold that message and deliver it to a consumer when the consumer is ready.

The code barely changes shape, but its meaning changes completely:

@Service
class OrderService(
    private val orderRepository: OrderRepository,
    private val kafkaTemplate: KafkaTemplate<String, OrderPlaced>,
) {
    fun placeOrder(order: Order): String {
        orderRepository.save(order)
        kafkaTemplate.send("order.placed", OrderPlaced.from(order))  // ← returns at once; no waiting on Email
        return "OK"
    }
}
The core idea

Async isn’t primarily about being faster. It’s about decoupling in time: the producer no longer waits for — or depends on the liveness of — the consumer. A durable message, held by a broker, is the primitive that buys you that decoupling.

4. What that one move buys you

Chris Richardson’s catalog frames the payoff crisply. Async messaging gives you:

  • Loose runtime coupling. Sender and consumer don’t need to know each other or be alive together. Add a fifth consumer without touching the producer.
  • Improved availability. The broker buffers messages until the consumer can handle them, so a downstream outage degrades gracefully instead of cascading.
  • Load leveling. A spike becomes a queue depth, not a stampede. The consumer drains at its own sustainable pace — the buffer absorbs the shock.
  • Many communication styles. One published message can fan out to notifications, pub/sub subscribers, and async request/reply — not just one caller.
There is no free lunch

A staff engineer names the cost in the same breath as the benefit. Introducing a broker means: a new piece of critical infrastructure to run and keep highly available; eventual rather than immediate results; no easy return value (request/reply gets harder); and brand-new failure modes you’ll spend the next lessons taming — duplicates, reordering, and delay. You are trading simplicity for decoupling. Sometimes that trade is wrong.

5. So when do you not reach for it?

The honest heuristic, and the start of real design judgment: use synchronous when the caller genuinely needs the answer to continue — “is this card valid so I can show the next screen?” Use asynchronous when the work must happen soon, but not necessarily now, and the caller shouldn’t be held hostage to it — sending email, updating analytics, rebuilding a search index, notifying other services.

“Now vs. soon” is a first cut, not the final word — we’ll sharpen it as you learn about delivery guarantees and consistency. But it will already make you sound more deliberate in a design review than “let’s just put a queue in front of it.”
