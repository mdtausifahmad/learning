Retries, Dead-Letter Queues & Poison Messages

◷ ~16 min read · interactive • Level: Core → Staff • Uses: L08, L09

Messages fail. The staff-level question isn’t whether to retry — it’s which failures to retry, how, and where the ones you can’t handle go so they don’t take the whole pipeline down with them. Get this wrong and a single bad message becomes a 3 a.m. outage. Get it right and failures become a tidy queue you triage on Monday.

1. Two kinds of failure — classify first

Transient (retry it)Permanent (don’t retry — DLQ it)
Network blip, timeoutMalformed / unparseable message
Downstream 503 / rate limitBusiness-rule violation (will never pass)
DB deadlock, brief lock contentionA bug in the handler

Retrying a transient failure usually succeeds. Retrying a permanent one just burns CPU forever and blocks everything behind it. So the first move is always: classify the exception, and treat the two paths differently.

2. The poison message & head-of-line blocking

A poison message is one that consistently fails. If you retry it in place forever, it becomes a plug: nothing behind it in the partition/queue can be processed — head-of-line blocking. One bad message stalls the whole consumer. The cure is a bounded retry, then move it aside to a dead-letter queue.

3. Retry strategies that don’t make it worse

  • Bounded attempts. Always cap retries (e.g. 3–5), then dead-letter. Infinite retry = an infinite outage.
  • Exponential backoff. 0.5s, 1s, 2s, 4s… — don’t hammer a struggling downstream.
  • Add jitter. Randomize the delay so many failed consumers don’t retry in lockstep (a thundering herd that re-kills the recovering dependency).
  • Blocking vs non-blocking. Blocking retry (retry in place, pausing the partition) preserves order but risks head-of-line blocking. Non-blocking retry ships the failed message to a separate retry topic/queue so the main flow keeps moving — at the cost of that message’s order.
// Spring Kafka — blocking retry with backoff, then publish to <topic>.DLT
@Bean
fun errorHandler(template: KafkaTemplate<Any, Any>): DefaultErrorHandler {
    val recoverer = DeadLetterPublishingRecoverer(template)          // routes exhausted records to the DLT
    val backOff = ExponentialBackOffWithMaxRetries(3).apply { initialInterval = 500; multiplier = 2.0 }
    return DefaultErrorHandler(recoverer, backOff).apply {
        addNotRetryableExceptions(IllegalArgumentException::class.java)   // permanent → straight to DLT
    }
}
// Non-blocking retries: separate retry topics + a DLT, so the main topic never stalls
@RetryableTopic(attempts = "4", backoff = Backoff(delay = 1000, multiplier = 2.0))
@KafkaListener(topics = ["orders"], groupId = "fulfillment")
fun handle(order: Order) { /* ... */ }

@DltHandler
fun dead(order: Order) { /* park, alert, await triage */ }

4. Dead-letter queues, per broker

The Dead Letter Channel is a canonical pattern: “When a messaging system determines that it cannot or should not deliver a message, it may … move the message to a Dead Letter Channel,” recording where it died and its original destination. Each broker gives you this differently:

BrokerDLQ mechanism
SQSNative redrive policy: after maxReceiveCount failed receives (visibility timeout = the retry delay), the message moves to the DLQ. Redrive back out to reprocess.
RabbitMQNative dead-letter exchange (x-dead-letter-exchange): messages rejected (nack, requeue=false), TTL-expired, or over a length limit route to the DLX → a DLQ. TTL+DLX gives delayed retry.
KafkaNo native DLQ — build it: Spring’s DeadLetterPublishingRecoverer / @RetryableTopic, or Kafka Connect’s errors.deadletterqueue.topic.name.
PulsarNative retry-letter topic + dead-letter topic per subscription.

5. Three things staff engineers never forget

A DLQ is a workflow, not a graveyard

Messages in a DLQ need monitoring, alarms, triage, and replay (AWS: alarm on any message entering the DLQ; use redrive to move them back). Store the failure reason, stack trace, and attempt count with each one. A silently-filling DLQ is data loss with extra steps — and beware replay loops (a message that fails, dead-letters, is replayed, and fails again).

Retries demand idempotency (Lesson 08)

A retry may re-run a side effect that partially succeeded — so a retried consumer will process some messages more than once. Retries and at-least-once are the same coin: your consumer must be idempotent, or retries manufacture duplicates.

Retries and DLQs disturb order (Lesson 09)

Non-blocking retry topics and DLQs pull a message out of line and reinsert it later — breaking per-key order. AWS explicitly warns: don’t use a DLQ with a FIFO queue if you need strict order. If order is sacred, prefer blocking retry (pause the partition) and accept the head-of-line risk, or design so a parked message doesn’t invalidate later ones.
