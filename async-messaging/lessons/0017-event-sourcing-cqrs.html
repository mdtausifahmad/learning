Event Sourcing & CQRS

◷ ~16 min read · interactive • Level: Staff / Architecture • Builds on: L12 (the log), L14

The most advanced event-driven patterns take the log idea to its conclusion: what if the stream of events is your database? Event sourcing and CQRS are powerful — and powerfully easy to over-apply. A staff engineer knows exactly what they buy, what they cost, and (most importantly) when to walk away from them.

1. Event sourcing: store the events, derive the state

Normal CRUD stores current state and mutates it — an UPDATE overwrites the old value and its history is gone. Event sourcing inverts this: it “persists the state of a business entity as a sequence of state-changing events” (microservices.io). The event log is the source of truth; current state is reconstructed by replaying the events. Fowler’s analogy: a version-control system — the commit log is the event store, the working copy is the derived state.

A quiet superpower: no dual write

Because “saving an event is a single operation, it is inherently atomic,” event sourcing sidesteps the dual-write problem (Lesson 14) entirely: the event is the state change, and the event store also acts as a broker others subscribe to. No separate outbox needed.

2. Watch it: events in, state & views out

Step through an account’s events becoming state and a read model (← / → keys work).

// Event sourcing: current state is a fold over the events
data class Account(val balance: Int = 0) {
    fun apply(e: AccountEvent) = when (e) {
        is Deposited -> copy(balance = balance + e.amount)
        is Withdrew  -> copy(balance = balance - e.amount)
    }
}
fun rebuild(events: List<AccountEvent>) = events.fold(Account()) { acc, e -> acc.apply(e) }

// A command: rebuild state → validate → APPEND a new event (never mutate)
fun withdraw(id: String, amount: Int) {
    val acct = rebuild(store.eventsFor(id))
    require(acct.balance >= amount) { "insufficient funds" }
    store.append(id, Withdrew(amount))
}

3. CQRS: separate the write model from the read model

CQRS (Command Query Responsibility Segregation, from Greg Young) is, in Fowler’s words, “the notion that you can use a different model to update information than the model you use to read information.” The write side enforces invariants; the read side(s) are denormalized and tuned per query. With event sourcing they pair naturally: the write side appends events; projections turn that stream into read models (a SQL view, a search index, a cache) — each eventually consistent. 

// A projection (@KafkaListener) builds and updates a read model from the event stream
@KafkaListener(topics = ["account.events"], groupId = "summary-projection")
fun project(e: AccountEvent) = summaryView.apply(e)   // separate query-optimized store
Eventual consistency, on purpose

Because the read model is updated after the write, a query right after a command may not see it yet. CQRS “raises the likelihood of using eventual consistency” (Fowler). You must design the UX for it — the same read-your-writes gap you meet all over async systems.

4. Benefits, costs — and the big caution

You gainYou pay
Complete audit trail & temporal queries (replay to any point)Querying current state means deriving it (snapshots needed)
Rebuild state / fix bugs by replaying; multiple read modelsEvent schema evolution is now critical (L16) — events live forever
No dual write; events are your integration streamReplay + external side effects = non-determinism; deletes (GDPR) are hard
Read and write scale independentlyEventual consistency + a lot more moving parts
Use judiciously — really

Fowler is blunt: “for most systems CQRS adds risky complexity.” Event sourcing is similar. These shine in complex, audit-heavy domains (finance, ledgers, compliance, trading) and specific bounded contexts — not as a default for a whole system. For ordinary CRUD, they are massive over-engineering. Reach for a snapshot to keep replays fast, and keep the pattern scoped to where it earns its cost.
