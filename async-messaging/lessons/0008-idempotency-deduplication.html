Idempotency & Deduplication in Depth

◷ ~16 min read · interactive • Level: Core → Staff • Builds on: Lesson 05 · broker-agnostic

Lesson 05 landed a verdict: for anything touching an external system you run at-least-once + idempotency. That was the “what.” This lesson is the “how” — the patterns that make processing duplicate-proof, the keys that make them work, and the windows that make them affordable. It applies to every broker you use: Kafka, RabbitMQ, SQS, Redis, Pulsar. Idempotency is the load-bearing wall of at-least-once systems.

1. What idempotency actually means

An operation is idempotent if performing it many times has the same effect as performing it once. A idempotent consumer is one whose handling of the same message repeatedly leaves the system in the same state as handling it once — as microservices.io puts it, “the outcome of processing the same message repeatedly must be the same as processing the message once.”

The distinction that matters: some operations are idempotent by nature; others you must make idempotent. Knowing which is which is the whole skill.

2. Naturally idempotent — or not

Naturally idempotent (replay = no-op)NOT idempotent (replay = bug)
SET status = 'PAID' (assignment)balance = balance + 10 (increment)
UPSERT keyed by a stable idINSERT a new row (duplicate rows)
DELETE WHERE id = xAppend to a log / list
Add to a set (SADD), PUT full documentSend an email · charge a card · emit an event
Design writes to be replay-safe by construction

The cheapest idempotency is the kind you never have to enforce. Before reaching for a dedup store, ask: can I reshape this write to be naturally idempotent? Replace “increment balance by 10” with “set balance to the value computed from a versioned source,” or a conditional/compare-and-set update. An UPSERT keyed by orderId makes a replay harmless for free — no extra table, no extra transaction.

3. Synthetic idempotency: a stable key + a dedup store

When the side effect genuinely can’t be natural (charge a card, increment a counter, send a notification), you make the consumer idempotent: remember what you’ve processed and skip repeats. Two things make or break this — the key, and the atomicity.

Pick a stable idempotency key

  • Best: a producer-generated id (a V4 UUID) created once for the logical action and carried in a message header. It stays identical across every retry.
  • Good: a business key (orderId) — if there is exactly one message per business action.
  • Fragile: a payload hash — breaks when non-meaningful fields vary (timestamps, field ordering).
  • Never: the broker’s delivery id / Kafka offset. A producer retry produces a new offset for the same logical message (recall Lesson 06 — the app-level id is stable, the broker position is not). Dedup on the app id, not the wire id.
// PRODUCER: generate the key ONCE for this action, reuse it on every retry
val idemKey = UUID.randomUUID().toString()          // not regenerated per send attempt!
val record = ProducerRecord("payments", order.id, PaymentRequested(order.id, order.total))
record.headers().add("idempotency-key", idemKey.toByteArray())
kafkaTemplate.send(record)

Dedup atomically with the side effect

Record the key in the same transaction as the side effect, guarded by a unique constraint so two concurrent deliveries can’t both slip through: 

@KafkaListener(topics = ["payments"], groupId = "ledger")
@Transactional                                        // dedup mark + side effect commit together
fun on(rec: ConsumerRecord<String, PaymentRequested>) {
    val key = rec.headers().lastHeader("idempotency-key")
        ?.let { String(it.value()) } ?: error("missing idempotency key")

    if (processed.existsById(key)) return             // already handled → skip (unique PK is the backstop)
    ledger.credit(rec.value())                        // the non-idempotent side effect, now guarded
    processed.save(ProcessedMessage(key))             // remembered, atomically with the credit
}

Prefer an insert-first form — INSERT … ON CONFLICT DO NOTHING and check the affected row count — when you want to avoid a read-then-write race entirely. Either way, the processed-key row and the side effect must land together (the offset commit lives outside, so the dedup record is what keeps a post-commit crash from re-charging).

4. The hard case: the side effect is in another system

Your dedup store is Postgres, but the charge is a call to Stripe. You can’t put an external HTTP call inside your database transaction, so the check-and-record trick doesn’t cover it. The answer: push the idempotency key through to the external API and let it dedup.

This is exactly what payment APIs are built for. Stripe: “A client generates an idempotency key … the server uses [it] to recognize subsequent retries … saving the resulting status code and body of the first request … Subsequent requests with the same key return the same result.” 

// Reuse the SAME key you carried on the message → the external system charges once
fun charge(req: PaymentRequested, idemKey: String): ChargeResult =
    stripeClient.post("/v1/charges", req) {
        header("Idempotency-Key", idemKey)     // retry with the same key ⇒ Stripe returns the first result
    }
The key travels end-to-end

One stable key, generated at the producer, rides the message, keys your dedup store, and goes into the Idempotency-Key header of the downstream call. That single identity is what makes an at-least-once chain behave as effectively-once from end to end.

5. Dedup windows & broker-native dedup

You can’t remember every processed key forever, so a dedup store is bounded — by time or size. That creates a rule:

Size the window to the worst-case redelivery

If a duplicate can arrive after your window expires, it will be reprocessed. So the retention must exceed the worst-case gap between the first delivery and the last possible redelivery: retry horizon + DLQ replay + consumer lag + broker retention. Stripe prunes idempotency keys after 24 hours; size yours for how late a dup could realistically show up.

Brokers offer their own dedup — but always with a narrow window, so treat it as a bonus, not the plan:

BrokerNative dedup
SQS FIFOMessageDeduplicationId / content-based — only within a 5-minute window
KafkaIdempotent producer dedups producer retries per partition (Lesson 06) — not your app-level duplicates
RabbitMQNo native dedup (a community plugin exists) → rely on consumer idempotency
GCP Pub/SubExactly-once delivery dedups within the ack deadline; exposes a stable message_id
RedisRoll your own: SET key val NX EX ttl as a dedup store

The lesson: broker-native dedup is a short-lived safety net. Durable correctness comes from an application-level idempotent consumer with a key you control — the one pattern that works identically across all five.

Beware cascading duplicates

If your consumer’s side effect is to emit another message, a duplicate can cascade downstream. The emission must itself be deduplicated — carry the idempotency key forward, and produce through a transactional outbox (its own lesson) so the emit is tied to the same transaction as the state change.
