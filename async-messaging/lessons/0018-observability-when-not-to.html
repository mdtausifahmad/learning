Async & Messaging · Lesson 18 · Finale

Observability, Operations & When Not to Use Messaging

◷ ~17 min read · interactive • Level: Staff / Judgment • The capstone — ties the whole course together

You can now design almost any async system. The last two things that separate a good engineer from a staff one: being able to operate what you built when it misbehaves at 3 a.m., and the wisdom to not build it when a boring synchronous call would do. This lesson is about running these systems in production — and knowing when the right answer is “no broker.”

1. Why async systems are hard to observe

A synchronous request has a call stack: one trace, one latency number, one place to look. An async flow has none of that. The work happens later, in another service, possibly retried and reordered, fanned out to consumers you didn’t write. There is no stack that spans the hops — which is exactly the flow-visibility trap from Lesson 13. So you have to build visibility in, deliberately, with the three pillars.

2. Pillar 1 — distributed tracing across the hops

The fix is context propagation: carry a trace id (and the current span id) through the message, so the consumer’s work becomes a child span of the producer’s. OpenTelemetry’s default is the W3C traceparent header (<version>-<trace-id>-<parent-id>-<flags>) — the same id rides producer → broker → consumer → next producer, and a backend like Jaeger stitches them into one trace.

Watch it: one trace across producer, broker, and consumers

Step through a trace id stitching an async flow into a single waterfall (← / → keys work).

// Spring Boot + Micrometer Tracing auto-injects/extracts W3C traceparent via Kafka headers
kafkaTemplate.setObservationEnabled(true)
containerFactory.containerProperties.observationEnabled = true

Keep a runbook

Operating messaging is mostly a handful of rehearsed responses: lag climbing (scale consumers or find the stuck partition / hung transaction), DLQ filling (triage & redrive, L11), rebalance storm (static membership / cooperative rebalancing, L07), schema break (compatibility gate in CI, L16), poison message (bounded retry → DLQ, L11). Write them down before you need them.

4. The wisdom: when not to use messaging

Every capability in this course came with a cost — a broker to run and keep highly available, eventual consistency, duplicates, reordering, lag, and harder debugging. Async is a deliberate trade (Lesson 01), not a default. The staff move is often to not reach for it.

Signs you should NOT use a broker

You need an immediate answer to continue → synchronous REST/gRPC (don’t fake sync over async). You need strong, read-your-writes consistency now → a database transaction is simpler. Simple CRUD, one service, low volume → a direct call or a DB; a broker is pure overhead. You’re querying/updating messages → that’s a database, not a queue. Your “events” are really synchronous calls in disguise (the passive-aggressive command, L04) → you’ve built a distributed monolith, the worst of both worlds. And event sourcing / CQRS / sagas on a simple domain → over-engineering (L15, L17).

The decision, in one breath

Reach for async messaging when you genuinely need decoupling in time, fan-out, load leveling, or resilience to downstream outages — and you can afford a broker plus eventual consistency plus the operational weight. Otherwise, choose the boring, synchronous, single thing that works. The best architects add complexity reluctantly, and can always say why.
