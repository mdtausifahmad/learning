Inside Kafka Exactly-Once — Sequence Numbers & read_committed

◷ ~17 min read · interactive • Level: Depth / Staff • Deepens: Lesson 05 (Route B)

In Lesson 05 you turned on Kafka EOS with three configs and trusted it. This deep dive opens the hood on the two questions you asked: how does the idempotent producer actually stop duplicates, and why does read_committed matter? Knowing the mechanism is what lets you reason about its costs and failure modes — the staff difference between “we enabled exactly-once” and “here’s exactly what it does and doesn’t buy us.”

1. The idempotent producer: TCP for your writes

The problem (from Lesson 05): a producer that loses an ack must retry, and if the broker had actually written the message, the retry duplicates it. Kafka’s fix, in Confluent’s own words, “works in a way similar to TCP: each batch of messages sent to Kafka will contain a sequence number that the broker will use to dedupe any duplicate send.”

Concretely, under the hood:

  • The broker assigns each producer a Producer ID (PID) on start-up.
  • Every batch carries the PID and a monotonically increasing sequence number, maintained per partition.
  • The partition leader remembers the highest sequence number it has accepted for each (PID, partition).
  • A resend arrives with the same sequence number → the broker sees it’s a duplicate, drops it, and still returns success. A number with a gap → it rejects with OutOfOrderSequenceException.
What this does — and doesn’t — buy you

Idempotence gives “exactly-once, in order, per partition” for one producer’s retries, at the cost of “just a few extra numeric fields per batch.” It does not dedupe application-level duplicates (you sent the same order twice on purpose), nor duplicates across a full producer restart unless you also use a transactional.id. It’s the first layer, not the whole story. (Default-on since Kafka 3.0; needs acks=all and max.in.flight.requests.per.connection ≤ 5.)

2. Transactions: making the read-process-write atomic

Idempotence stops producer-retry duplicates on one partition. But a stream processor that reads A, computes B = F(A), and writes B can still double-produce if it crashes after writing B but before marking A consumed. Transactions close that gap with one elegant realization:

The key trick

In Kafka, committing a consumer offset is just another write to a topic (the internal offsets topic). So the write of B and the commit of A’s offset can be placed in the same transaction — and Kafka’s atomic multi-partition write makes them all-or-nothing. A is consumed if and only if B is produced.

Two supporting mechanisms make it safe:

  • Zombie fencing. A transactional producer registers a transactional.id; registering it bumps an producer epoch. Any older-epoch producer with the same id is a “zombie” and its writes are rejected. This kills the duplicate-instance problem.
  • Control markers. A transaction coordinator tracks state in an internal log and writes a commit or abort marker (a control message) into each partition the transaction touched. Those markers are how consumers later know the transaction’s fate.

3. Why read_committed matters

Here is the subtlety that makes the isolation level essential: a transaction’s messages are appended to the partition log as they are produced — before the commit or abort decision exists. So the log physically contains messages that may belong to a transaction that ends up aborted.

  • read_uncommitted (the default!) reads everything in offset order, immediately — including messages from transactions that later abort. Your downstream sees data that “never happened.”
  • read_committed only delivers committed transactional messages. It reads up to the Last Stable Offset (LSO) — the offset just before the first still-open transaction — withholding anything beyond it, and uses the commit/abort markers to filter out aborted messages entirely.
The cost, and the gotcha

read_committed buys correctness but adds read latency: a consumer cannot advance past an open transaction, so a long-running or hung transaction stalls all read_committed consumers at the LSO until it commits, aborts, or times out (transaction.timeout.ms). And note the default is read_uncommitted — if you built a transactional pipeline but forgot to set the consumer’s isolation level, you silently get dirty reads and no exactly-once. This one line is easy to miss.
