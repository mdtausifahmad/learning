Async & Messaging · Lesson 16

Schema Evolution & Contracts

◷ ~15 min read · interactive • Level: Staff / Design • Builds on: L12 (retained logs), L04

Every event you publish is a contract — and unlike a function signature, you can’t change it and recompile the callers. Consumers you’ve never met deploy on their own schedule, and (on a log) they replay events you wrote months ago. Change a schema carelessly and you break them silently, in production, at a distance. This lesson is how events change safely forever.

1. Why event schemas are hard to change

An event schema is a public API with three properties that make it unforgiving:

  • Independent deploys. Producer and consumer versions overlap in time — you can’t upgrade them atomically, so both versions must interoperate.
  • Retained history (Lesson 12). A log keeps old events; a consumer reading history sees every past schema version. Old and new must both be readable.
  • Unknown consumers. With pub/sub you may not even know who subscribes. You can’t call them to coordinate a change.

2. Compatibility: the rules that keep you safe

Confluent’s Schema Registry frames evolution as compatibility types (default: BACKWARD):

  • Backward — the new schema can read data written with the old one. “Consumers using the new schema can read data produced with the last schema.” → upgrade consumers first. The common default.
  • Forward — the old schema can read data written with the new one. → upgrade producers first; old consumers keep working.
  • Full — both backward and forward. Transitive variants check against all prior versions, not just the last.

Watch it: an additive change stays compatible — a rename breaks

The golden rules

Add fields as optional, with a default. Never remove or rename a required field (deprecate instead). Never change a field’s type (add a new field). Never reuse a field’s tag/number (Protobuf) or position. Keep every change additive and old readers keep working.

3. Formats & the Schema Registry

FormatEvolution story
AvroBuilt for evolution: reader + writer schemas resolved via defaults & aliases. Compact binary. The Schema Registry default.
ProtobufField numbers; add fields with new numbers, never reuse them; unknown fields preserved. Best practice: BACKWARD_TRANSITIVE.
JSON (+ JSON Schema)Human-readable, flexible; no enforced schema unless you add JSON Schema. Easy to add fields, but no compile-time safety and larger payloads.

A schema registry stores schemas per subject, enforces your compatibility rule at registration (rejecting an incompatible schema before it ever ships), and lets messages carry a small schema ID instead of the whole schema. It turns “don’t break consumers” from a hope into a build-time guarantee. 

// Spring Kafka + Confluent Schema Registry (Avro): compatibility enforced on register
spring:
  kafka:
    producer:
      value-serializer: io.confluent.kafka.serializers.KafkaAvroSerializer
      properties:
        schema.registry.url: http://schema-registry:8081

// Avro field added compatibly — optional with a default
{ "name": "phone", "type": ["null", "string"], "default": null }

// JSON tolerant reader (forward compat): ignore fields you don't know
@JsonIgnoreProperties(ignoreUnknown = true)
data class OrderPlaced(val id: String, val email: String)

4. Strategy & staff judgment

  • Pick a compatibility mode (usually BACKWARD) and enforce it in CI via the registry — a schema change that would break consumers fails the build.
  • Evolve additively. Optional, defaulted fields only. Treat the schema as a reviewed, versioned artifact (like an API).
  • When a breaking change is unavoidable — a new major version: publish to a new topic (or add a version field), dual-publish old+new during migration, move consumers over, then retire the old one. Never break in place.
  • Be a tolerant reader (Postel’s law): ignore unknown fields, don’t over-validate. It buys you forward compatibility for free.
