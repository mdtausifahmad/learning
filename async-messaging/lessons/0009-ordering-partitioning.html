Async & Messaging · Lesson 09

Ordering & Partitioning

◷ ~15 min read · interactive • Level: Core → Staff • Builds on: L02, L03

“Messages arrive in order” is the assumption that quietly wrecks the most systems. This lesson makes ordering precise: what a broker actually guarantees, how message keys give you the order you need, and why ordering and parallelism pull in opposite directions. It deepens the key→partition thread from Lessons 02–03 into a staff-level design lever.

1. There is no global order — only per-partition order

The instinct is to imagine one ordered stream. But partitioning splits a topic’s log into pieces, and as Confluent states plainly: “we don’t have global ordering, at least not a strict guarantee of global order within a partitioned topic. We only have that within each partition.”

Reframe the requirement

You almost never actually need global order — you need per-entity order: a single account’s transactions in order, a single order’s state changes in order. Global order forces a single partition (no parallelism) and is rarely worth it. Per-entity order is cheap — if you pick the right key.

2. How a key creates per-key order

Kafka decides a message’s partition from its key:

  • No key → messages are spread round-robin across partitions. Confluent’s example: readings from “thermostat 42” land on different partitions — “they’re not in order… I don’t have a guarantee of order.”
  • With a key → the key is run through hash(key) % partitionCount to pick the partition. The same key always lands on the same partition, giving “strict ordering for any messages of the same partition key.” Different keys go wherever the hash sends them — independently.
// The key IS the ordering boundary. All of one customer's events share a
// partition and stay strictly ordered; different customers run in parallel.
kafkaTemplate.send("order.events", order.customerId, OrderPlaced(order.id, order.customerId))

3. The tension: ordering vs parallelism

Here is the trade-off that makes this a staff-level lever. Per-partition order plus the rule from Lesson 03 — one consumer per partition per group — means a key’s events are processed by exactly one consumer, sequentially. You cannot parallelize within a key’s order.

The dial

Your parallelism ceiling is the number of partitions; your ordering unit is the key. Tight ordering (few keys, or a coarse key like region) throttles parallelism and invites hot partitions. Fine-grained keys (customerId) give lots of parallelism but only guarantee order per customer. Choose the key as the smallest entity whose events must stay ordered — no coarser.

4. How “we have a key” still loses order

  • Producer retries. With max.in.flight.requests.per.connection > 1 and no idempotence, a later batch can be written before an earlier one that is being retried → reordering on the partition. Fix: enable.idempotence=true (its sequence numbers preserve order even with in-flight up to 5), or set max.in.flight…=1.
  • Repartitioning. Change the partition count and hash(key) % N changes — a key’s future messages may land on a different partition than its history, breaking order across the change. Provision partitions up front.
  • Hot keys. One dominant key (a whale account) overloads its partition — a hotspot and a single slow consumer (Lesson 03).
  • Consumer-side. Hand a partition’s records to a parallel thread pool and you reorder them yourself. Retrying a failed message by re-queueing lets newer messages pass it. Process a partition sequentially; for in-order retries, pause the partition.
# Keep per-partition order under producer retries
spring:
  kafka:
    producer:
      acks: all
      properties:
        enable.idempotence: true          # preserves order with retries (in-flight ≤ 5)
        # without idempotence, use: max.in.flight.requests.per.connection: 1

5. The same idea in other brokers

BrokerOrdering model
KafkaStrict within a partition; key → partition. Order unit = key.
SQS FIFOStrict within a MessageGroupId — “processed one at a time, in strict order.” Order unit = message group (the key analog); parallelism across groups.
SQS StandardBest-effort only — no ordering guarantee.
RabbitMQOne queue + one consumer = order; competing consumers or requeue-on-nack can reorder. Consistent-hash exchange for per-key routing.
PulsarKey_Shared subscription keeps per-key order with multiple consumers.

The recurring shape: order is guaranteed only within an ordering unit — a partition, a message group, a key — and you trade parallelism for how coarse that unit is. Learn it once.
