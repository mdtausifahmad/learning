Log vs Queue Brokers — the One Difference That Explains Everything

◷ ~16 min read · interactive • Level: Staff / Synthesis • Ties together: L02, L03, L05–L11

You’ve met Kafka, RabbitMQ, and SQS behaving differently at every turn — fan-out, ordering, replay, offsets, DLQs. This lesson reveals the single structural choice underneath all of it. Once you see it, you can predict how any broker behaves and pick the right one without memorizing a feature matrix. This is the mental model a staff engineer reaches for first.

1. The one difference: delete-on-read vs retain

Confluent says it bluntly: “Kafka does not have queues. A topic is not a queue, it’s a log. The difference is: when I read from a queue, I’ve taken that item out — nobody else can read it, it’s gone. In a log, when I read a message it’s still there. I can read it again. Someone else can read it.”

  • Queue-based (RabbitMQ, SQS, JMS/AMQP): a message is delivered, acknowledged, and deleted. The broker tracks per-message state (unacked / acked). The queue holds pending work.
  • Log-based (Kafka, Pulsar): messages are appended to an immutable, ordered log and retained (by time/size), independent of who read them. Each consumer tracks its own offset. Reading never deletes.

The predictive power

You never need to memorize these rows. Ask one question — does reading delete the message? — and every row follows. Retained data ⇒ replay, free fan-out, offsets, intrinsic order. Deleted-on-ack ⇒ per-message state, native DLQ/priority, easy scaling, no replay.

3. Inside each model

The log (Kafka)

  • Append-only, immutable segments on disk (data + an offset index). Confluent: messages are “immutable — once written, you can’t change them… you don’t get to rewrite history.” That immutability is what makes replay possible.
  • Sequential I/O + OS page cache + zero-copy → very high throughput.
  • Retention by time or size; or log compaction (cleanup.policy=compact) which keeps only the latest value per key — a durable “current state” changelog.

The queue (RabbitMQ / SQS)

  • The broker tracks per-message delivery state: delivered-but-unacked messages are redelivered after a nack or a timeout (RabbitMQ requeue; SQS visibility timeout). On ack, the message is removed.
  • Because it owns each message individually, a queue can offer per-message priority, TTL, selective consumption, and native DLQs — things a whole-topic log can’t.
  • HA via replicated/quorum queues (RabbitMQ) or a managed distributed store (SQS).

4. Choosing — the staff heuristic

The one-line test

A stream of events others may want to replay → log. A queue of tasks to be done once and discarded → queue. (It rhymes with Lesson 04: events lean log, commands/tasks lean queue.)

Reach for a LOG when…Reach for a QUEUE when…
Multiple independent consumers of the same dataDistributing tasks to competing workers
Replay / reprocessing / event sourcing / stream processingPer-message workflows, priority, TTL, request/reply
Very high throughput, ordered per keyFlexible consumer scaling beyond a partition count
An audit trail / source of truth of eventsComplex routing (RabbitMQ exchanges) & native DLQs

Hybrids blur the line: Pulsar stores a log (Apache BookKeeper) but offers queue-like subscription modes; AWS pairs Kinesis (log) with SQS (queue); Redis Streams is log-shaped. Knowing the underlying model tells you what each can and can’t do — regardless of the marketing.
