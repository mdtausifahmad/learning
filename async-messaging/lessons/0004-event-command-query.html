Async & Messaging · Lesson 04

Event vs Command vs Query — Naming What Flows

◷ ~13 min read • Level: Foundations → Design • Builds on: Lesson 02

Lesson 01 gave you the broker; Lesson 02 gave you the topology. But two messages with identical bytes can mean completely different things. This lesson is about intent — and why naming a message honestly is one of the highest-leverage design decisions you’ll make. Get it wrong and you build hidden coupling while congratulating yourself on being decoupled.

1. Three intents, one envelope

Every message you send carries one of three intentions:

  • Command — “do this.” A directed request to perform an action. EIP frames it as using a message to invoke a procedure in another application. Named imperatively: ShipOrder. One logical owner. The sender expects it to be carried out.
  • Event — “this happened.” A notification of a fact that already occurred. Named in the past tense: OrderPlaced. The publisher, in Fowler’s words, “doesn’t really care much about the response.” Zero, one, or many consumers may react.
  • Query — “tell me this.” A request for information that expects a reply. Named interrogatively: GetOrderStatus. Almost always synchronous request/reply — fire-and-forget messaging is the wrong tool when you need the answer to continue (recall the Lesson 01 test).

2. The crux: who owns the decision?

The intents differ in which side decides what happens — and that decides which way the coupling points.

Why this is the whole game

That inversion is the engine of extensibility. To add a loyalty-points reaction to a command system, someone must change the sender to also command Loyalty. To add it to an event system, Loyalty just subscribes — the producer never changes. Events let you grow behavior at the edges without editing the center.

3. Naming is design

The tense of a name encodes its intent. Enforce this and half your design arguments evaporate, because everyone can see what a message is just by reading it. In Kotlin, model each as a small immutable data class: 

// COMMAND — imperative; one owner; expresses intent to act
data class ShipOrder(val orderId: String, val address: Address)

// EVENT — past tense; a fact that already happened; publisher indifferent to reactors
data class OrderPlaced(val orderId: String, val customerId: String, val total: Money)

// QUERY — interrogative; asks for data and expects a reply
data class GetOrderStatus(val orderId: String)

Command: sent to one owner, expected to act

kafkaTemplate.send("shipping.commands", order.id, ShipOrder(order.id, order.address))

@Component
class ShippingCommandListener(private val shipping: ShippingService) {
    @KafkaListener(topics = ["shipping.commands"], groupId = "shipping")
    fun handle(cmd: ShipOrder) = shipping.dispatch(cmd)   // the one owner carries it out
}

Event: announced; each consumer chooses its own reaction

kafkaTemplate.send("order.events", order.id, OrderPlaced(order.id, order.customerId, order.total))

@KafkaListener(topics = ["order.events"], groupId = "email")
fun confirm(e: OrderPlaced) = email.sendConfirmation(e)

// Added months later. The Order Service was never touched. (Different groupId = fan-out, Lesson 02.)
@KafkaListener(topics = ["order.events"], groupId = "loyalty")
fun award(e: OrderPlaced) = loyalty.awardPoints(e.customerId, e.total)

Query: usually synchronous — the caller needs the answer

@GetMapping("/orders/{id}/status")
fun status(@PathVariable id: String): OrderStatus =
    orderQueryService.status(id)   // fire-and-forget messaging is the wrong tool here

4. The trap that fakes decoupling

Fowler: the “passive-aggressive command”

“An event used as a passive-aggressive command … the source system expects the recipient to carry out an action, and ought to use a command message to show that intention, but styles the message as an event instead.”

If OrderPlaced exists only so that Shipping ships — and the Order team gets paged when shipping breaks — then it is a command wearing an event costume. You’ve coupled the two services while pretending you haven’t, and made ownership ambiguous. Name the intent honestly: if you depend on a specific thing being done, send a command.

The opposite trap (flag for later)

Pure event notification hides the end-to-end business flow: as Fowler warns, “the only way to figure out this flow is from monitoring a live system.” Lots of tiny events can be too decoupled to reason about. That tension — choreography vs orchestration — gets its own lesson. And “how much data an event carries” (notification vs event-carried state transfer) is a second axis we’ll return to.

Try it in your own system

Take the message you sketched after Lesson 02. Name it out loud. Is it imperative (command), past tense (event), or interrogative (query)? Then ask the honesty test: do I depend on a specific thing being done? If yes, it’s a command — even if you were about to call it an event. Bring your verdict.
