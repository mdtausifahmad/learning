PostgreSQL CDC with Debezium — an Animated Atlas

◷ ~35 min · eight replayable scenes • Level: Staff / Internals • Builds on Lesson 14

An outbox fixes the dual write only once something can reliably relay the committed row. This lesson opens that relay up: PostgreSQL writes a durable log; Debezium follows it without polling tables; offsets flow back to PostgreSQL; and a downstream event becomes safe to consume. The goal is the staff-level version of “we use Debezium”: you can predict what happens during snapshots, restarts, idle databases, and failover.

Scene 01 · End to end

1. Follow one committed write all the way out

CDC is not a query loop and it is not a database trigger. The application commits normally; PostgreSQL records the change in its write-ahead log (WAL); logical decoding turns that internal record into a row change; and Debezium turns it into a source record. Then the direction reverses: after Kafka Connect has committed the record, Debezium confirms an LSN back to PostgreSQL so the slot can eventually release old WAL.

WAL

Durable physical log. Its LSN is the position CDC follows.

Logical decoding

Reconstructs committed row changes from WAL records.

Replication slot

Stores position and retains necessary WAL for this reader.

Debezium offset

Records the source LSN so recovery can restart safely.

Scene 02 · PostgreSQL under the hood

2. What PostgreSQL must provide before Debezium can work

Debezium relies on native PostgreSQL machinery. This matters because it tells you which database knobs change correctness, latency, WAL volume, and recovery behavior. The connector consumes what PostgreSQL makes visible; it does not magically reconstruct data PostgreSQL did not log.

Scene 03 · Debezium as a Kafka Connect source

3. The connector is a single ordered reader with two loops

The connector is a Kafka Connect SourceConnector/SourceTask. Its streaming reader runs in the background; Connect drains a queue through poll(). That deliberate separation is why you can reason about backpressure and why the connector’s offset acknowledgement occurs only after Connect has made progress.

Connector propertyMaps to / controlsProduction reading

Version-specific source caveat

The source report verified a surprising code default of plugin.name=decoderbufs at its pinned Debezium snapshot, while pgoutput is the practical modern standard. Treat defaults as versioned configuration, inspect your deployed connector, and set the plugin explicitly.

The report’s pinned LogicalDecoder supports PGOUTPUT and DECODERBUFS. The decoder also processes relation metadata so it can turn compact wire tuples into named columns. Treat both the supported plugin set and defaults as deployment-version facts.

Scene 04 · Snapshot then stream

4. An initial snapshot gives history without losing concurrent changes

A logical slot only receives changes that commit after the slot exists. Debezium’s initial snapshot supplies existing rows as READ events, but it must also join the live WAL stream at the right LSN. The point is not merely a consistent query; it is a handoff with no blind spot.

Snapshot strategyUse whenCost / caveat
initialFirst deployment needs current state and live changesOne initial table scan
when_neededRecorded offset may no longer be retained in WALSelf-heals by re-snapshotting; downstream must tolerate READs
alwaysDeliberately re-baselining after loss or failoverRe-emits current state at every start
IncrementalLarge / ad-hoc backfill alongside live trafficSignalling and watermarking complexity; needs an identity key
Read-only incremental snapshots

On PostgreSQL 13+, the source report notes a read-only incremental option that uses in-progress transaction IDs as watermarks rather than a signalling-table write. It keeps the same principle: streamed changes win over buffered snapshot reads.

Scene 05 · The record a consumer receives

5. Read Debezium events as a contract, not as opaque JSON

A change event is an envelope around a row transition. The envelope keeps the data state separate from source position and operation type—so a consumer can distinguish a snapshot READ from a new insert, reconstruct a delete, and deduplicate a replay without guessing from the payload.

Source contract

Use lsn / source position for replay-aware deduplication, not broker offset.

Type mapping

Review decimal, time precision, and hstore handling modes before consumers rely on a schema.

Delete contract

Model both the delete event and tombstone; compacted topics need the latter.

Identity contract

before is limited by PostgreSQL’s logged old tuple, not just a connector setting.

Scene 06 · Runtime and delivery

6. Pick a runtime, then design for recovery duplicates

Kafka Connect, Debezium Server, and the Embedded Engine use the same source connector mechanics. They differ in who owns the offset store and where records go. Regardless of runtime, normal delivery is at-least-once: a crash after an event reaches its sink but before an offset flush can cause a replay.

Scene 07 · Operate the slot, not just the connector

7. The dominant production failure is a slot that cannot advance

A logical slot is a promise: PostgreSQL retains the log until the consumer confirms it. That is exactly what makes a restart reliable—and exactly what makes a stalled connector a disk incident. The response is to monitor the right LSNs and arrange safe progress even when captured tables are quiet.

Production ruleWhyAction
One connector, one slot, one publicationSharing a slot advances one reader past data another has not consumedGive each source a unique, persistent name
Keep slot.drop.on.stop=falseDropping the slot loses recovery historyOnly drop deliberately when decommissioning the capture
Monitor retained WALSlot lag is database disk pressure, not merely connector lagInspect pg_replication_slots plus source lag
Size the queue for large transactionsLogical decoding and Connect buffer data before it reaches the sinkReview max queue size, batch size, bytes, and capacity metric

Scene 08 · The practical reason teams adopt it

8. Transactional outbox becomes a durable event stream—and FES packages it

CDC is especially valuable as the relay in the transactional outbox pattern. A service writes business state and an outbox row in one database transaction. Debezium sees the committed WAL record regardless of a later process crash. The supplied source report describes Zalando’s FES (Fabric Event Stream) as a platform version of this pattern: a managed PostgreSQL logical-replication bridge into Nakadi.

Evidence boundary

The FES/customs material in the supplied Markdown is attributed to internal manifests and repositories. This lesson presents it as a useful deployment case study, while PostgreSQL and Debezium mechanics are independently linked to their public primary documentation below.

The report’s internal code search found roughly 59 FabricEventStream hits across 26+ Zalando Logistics repositories. It calls out a pick-broker-reservation-handler README/ADR as a public style reference for the same slot-retention trade-off, while noting that the customs meta-repository itself is documentation/tooling rather than a Debezium implementation.

9. The design-review checklist

  • Does PostgreSQL run with wal_level=logical, enough replication slots, and an intentional WAL-retention guard?
  • Does every connector have its own named slot and publication, with slot.drop.on.stop=false in production?
  • Do UPDATE and DELETE tables have the right REPLICA IDENTITY for the before contract and TOAST behavior you promise?
  • Can consumers tolerate an op: r snapshot and recovery duplicates, and can they deduplicate source positions?
  • Do dashboards alert on source lag, retained WAL, queue capacity, filtered records, and snapshot progress?
  • Does the heartbeat strategy include an in-captured-database write for the cross-database idle case?
  • Does the failover plan account for your PostgreSQL version, managed service, Patroni policy, and snapshot fallback?
  • For business events, does an outbox write occur in the same transaction as the business state change?
