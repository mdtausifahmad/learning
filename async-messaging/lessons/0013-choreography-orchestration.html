Async & Messaging · Lesson 13

Event-Driven Architecture — Choreography vs Orchestration

◷ ~15 min read · interactive • Level: Staff / Design • Builds on: L04 (event vs command)

A single business process — place an order, reserve stock, charge the card, arrange shipping — spans many services, each with its own database. Who decides what happens next? There are exactly two answers, and choosing between them is one of the most consequential architecture decisions you’ll make. This is where “I use events” matures into “I designed the coordination.”

1. The coordination problem

When each service owns its own data (no shared database), a multi-step business flow can’t be one ACID transaction. You must coordinate a sequence of local steps across services. Chris Richardson names the two ways to coordinate them:

  • Choreography — “each local transaction publishes domain events that trigger local transactions in other services.” No conductor; the flow emerges from services reacting to each other’s events.
  • Orchestration — “an orchestrator tells the participants what local transactions to execute.” A central coordinator sends commands and awaits replies, deciding each next step.

It maps cleanly onto Lesson 04: choreography runs on events (“this happened, react if you care”); orchestration runs on commands (“do this”, directed, with a reply).

2. See both styles drive the same flow

Step through one order flow, first choreographed, then orchestrated (← / → keys work).

In code

// CHOREOGRAPHY — each service reacts to an event and emits the next one
@KafkaListener(topics = ["order.events"], groupId = "inventory")
fun onOrderPlaced(e: OrderPlaced) {
    inventory.reserve(e.orderId, e.items)
    kafkaTemplate.send("inventory.events", e.orderId, InventoryReserved(e.orderId))   // no idea who's next
}
// ORCHESTRATION — the coordinator sends commands and reacts to replies, holding the flow's state
@KafkaListener(topics = ["order.events"], groupId = "orchestrator")
fun onOrderPlaced(e: OrderPlaced) =
    commands.send("inventory.commands", ReserveInventory(e.orderId, e.items))

@KafkaListener(topics = ["inventory.replies"], groupId = "orchestrator")
fun onInventoryReserved(r: InventoryReserved) =
    commands.send("payment.commands", ChargePayment(r.orderId))          // the orchestrator decides step 2

3. The trade-offs that decide it

ChoreographyOrchestration
CoordinationEvents; each service decides its reactionCommands; a coordinator decides
CouplingLoose runtime coupling; process knowledge is diffuseServices stay simple; coordinator couples to all of them
Flow visibilityImplicit — reconstruct from traces/logsExplicit — one place holds the flow
Add a step / reactionJust subscribe a new consumerEdit the orchestrator
Error handling / compensationScattered across servicesCentralized (natural home for sagas)
Main riskNobody understands the whole flowA god-orchestrator bottleneck
Fowler’s flow-visibility trap

Choreography’s danger, in Fowler’s words: “it can be hard to see such a flow as it’s not explicit in any program text. Often the only way to figure out this flow is from monitoring a live system.” It’s easy to build nicely decoupled systems “without realizing that you’re losing sight of that larger-scale flow” — and set up trouble in future years. If you choreograph, invest in distributed tracing (correlation IDs) and a documented event catalog.

4. Choosing — the staff heuristic

Rule of thumb

Simple flows, few steps, autonomous teams reacting to events → choreography. Complex, multi-step flows with ordering, conditionals, and compensation that you must see and control → orchestration. Many systems do both: orchestrate the critical transaction, choreograph the peripheral reactions (email, analytics, search indexing).

  • Choreography tooling: just your broker + solid event contracts/schemas.
  • Orchestration tooling: a workflow engine — Temporal, AWS Step Functions, Camunda/Zeebe, Netflix Conductor — or a hand-written stateful orchestrator service.
  • Either way, the next lesson’s problem bites: a step must atomically update its DB and publish its event/command — the transactional outbox. And multi-step flows with rollback are sagas. Both are coming up.
