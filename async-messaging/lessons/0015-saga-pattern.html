Async & Messaging · Lesson 15

The Saga Pattern & Distributed Workflows

◷ ~16 min read · interactive • Level: Staff / Design • Capstone of L08, L13, L14

This is where it all comes together. A business transaction spans several services, each with its own database — so there’s no single ACID transaction to keep them consistent. The saga is the pattern that gets you consistency anyway, using the outbox to publish reliably, choreography or orchestration to coordinate, and idempotency to survive retries. It’s also the pattern most people implement subtly wrong — so we’ll spend real time on the traps.

1. The problem & the shape of the answer

With a database per service, “reserve inventory, charge the card, confirm the order” can’t be one transaction (2PC is off the table, Lesson 14). A saga replaces it with a sequence of local transactions: each service does its own local commit and publishes an event/command that triggers the next. And crucially — if a step fails, the saga runs compensating transactions that undo the earlier steps.

Compensation ≠ rollback

You can’t roll back a committed local transaction. A compensating transaction is a new transaction that semantically reverses it: ReserveCredit → ReleaseCredit, ReserveInventory → ReleaseInventory, ChargePayment → RefundPayment. Undo is a real business action, and it must be reliable and idempotent like any other step.

3. Choreography or orchestration (Lesson 13, applied)

  • Choreography-based saga: each service listens for events and reacts, emitting the next event — or a failure event that triggers others to compensate. Decentralized; great for short sagas.
  • Orchestration-based saga: a central orchestrator holds the saga’s state machine, sends commands, and on failure sends compensation commands. Explicit and visible — the usual choice for longer, branchier flows.
// Orchestration saga — a state machine that drives steps and compensations
fun on(reply: SagaReply) = when (reply) {
    is InventoryReserved -> commands.send("payment.commands", ChargePayment(reply.sagaId))
    is PaymentFailed     -> commands.send("inventory.commands", ReleaseInventory(reply.sagaId))  // compensate
    is PaymentCharged    -> confirmOrder(reply.sagaId)                                            // pivot: commit the saga
    is InventoryReleased -> rejectOrder(reply.sagaId)
    else -> {}
}

4. The hard truths (what a saga gives up)

No isolation — the subtlest trap

A saga is not isolated (no “I” in ACID). microservices.io: “the lack of isolation means there’s a risk that the concurrent execution of multiple sagas… can [cause] data anomalies” — dirty reads, lost updates. You must add countermeasures. The everyday one is a semantic lock: a PENDING/*_PENDING state flag (like our order) that tells concurrent work “this isn’t final yet.” Others: commutative updates, re-reading a value before writing, and versioning.

  • No automatic rollback — you design every compensation by hand (and test the failure paths, which is where bugs hide).
  • Eventual consistency — the system is temporarily inconsistent mid-saga. Design the UX for it (“order processing…”).
  • The pivot transaction — order your steps: compensatable steps first (can be undone), then the pivot (the commit point, e.g. confirm the order), then retriable steps that must eventually succeed (e.g. send the receipt). You compensate before the pivot; you retry-forward after it.

5. The building blocks & when to reach for it

  • Each step uses the outbox (L14) to atomically commit its state and publish its event/command — reliable saga steps.
  • Every handler is idempotent (L08) — messages redeliver; compensations may re-run.
  • A correlation / saga id ties the steps together (for ordering, tracing, and matching replies to state).
  • Consider a workflow engine — Temporal, Step Functions, Camunda — which give you saga state, retries, timers, and compensation natively, so you don’t hand-roll the state machine.
  • When NOT to saga: if the transaction fits in one service, keep it a local ACID transaction. Sagas are for consistency that genuinely spans services — don’t pay their complexity tax otherwise.
