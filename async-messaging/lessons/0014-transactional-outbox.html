The Transactional Outbox & the Dual-Write Problem

◷ ~15 min read · interactive • Level: Staff / Design • Fixes a bug under L05, L08, L13

Every “update the database, then publish an event” you’ve written has a silent bug. The two writes go to two systems with no shared transaction, so a crash at the wrong moment either loses the event or invents one. This lesson names that bug — the dual-write problem — and gives you the one pattern that actually fixes it. It’s the missing reliability piece the last few lessons kept pointing at.

1. The dual-write problem

A command usually must do two things: update its database and publish a message. microservices.io states the problem exactly: “How to atomically update the database and send messages to a message broker?” You can’t — not naively — because they’re separate systems:

  • DB commits, then you crash before publishing → the state changed but the event is lost. Downstream never learns.
  • You publish, then the DB rolls back → a phantom event for something that never happened.
Why the obvious fixes don’t work

Wrapping both in @Transactional is a mirage — the broker send isn’t part of the database transaction, so it can fire even when the DB rolls back (or vanish when it doesn’t). And a distributed transaction (2PC/XA) across DB + broker is, per microservices.io, “not viable”: Kafka doesn’t support it, it’s slow and fragile, and it couples your service to both systems. There is no ordering of two independent writes that is crash-safe.

2. The fix: write to an outbox in the same transaction

The transactional outbox turns two writes into one. Instead of publishing to the broker, the service inserts the message into an OUTBOX table in its own database, in the same local ACID transaction as the business change. Now they’re atomic — both commit or neither. A separate message relay then reads the outbox and publishes to the broker. Result (microservices.io): “Messages are guaranteed to be sent if and only if the database transaction commits.”

Watch it: the bug, then the outbox fix

Step through the dual-write failure and the outbox solution (← / → keys work).

In code

// ✗ DUAL WRITE — broken: the send is not part of the DB transaction
@Transactional
fun pay(orderId: String) {
    orders.markPaid(orderId)                                   // DB write (in the tx)
    kafkaTemplate.send("order.events", OrderPaid(orderId))     // separate system — may send on rollback, or be lost on crash
}
// ✓ OUTBOX — the event is written atomically with the state, in ONE transaction
@Transactional
fun pay(orderId: String) {
    orders.markPaid(orderId)
    outbox.save(OutboxEvent(                                   // same DB, same tx → atomic
        id = UUID.randomUUID().toString(),                     // stable idempotency key for consumers (L08)
        topic = "order.events", key = orderId, payload = OrderPaid(orderId),
    ))
}

3. Relaying the outbox: two ways

Polling publisherTransaction log tailing (CDC)
HowA job SELECTs unsent rows, publishes, marks sentA tool (Debezium) tails the DB’s WAL/binlog and streams outbox inserts to Kafka
ProsDead simple, no extra infraLow latency, no polling load, no publish code
ConsPolling lag + DB load; must ORDER BY to keep orderMore infra (Debezium/Connect); log-format coupling
 
// Polling publisher — order preserved via ORDER BY id
@Scheduled(fixedDelay = 500)
@Transactional
fun relay() {
    outbox.findUnsentOrderById(limit = 100).forEach { e ->
        kafkaTemplate.send(e.topic, e.key, e.payload)
        e.markSent()                                           // or delete the row
    }
}
Why order matters here

microservices.io: events must be published “in the order they were sent by the service” (T1→E1 before T2→E2). A polling relay preserves this with ORDER BY (per aggregate/key); CDC preserves it because the transaction log is ordered. This is the L09 ordering guarantee, upheld at the publish boundary.

4. What the outbox does & doesn’t give you

  • Guarantees: the event is published iff the state was committed — no lost events, no phantom events. Reliable event publishing, at last.
  • At-least-once, not exactly-once: the relay can publish then crash before marking sent → a duplicate. So consumers must be idempotent (Lesson 08) — which they already should be. Outbox (reliable produce) + idempotent consumer (reliable consume) = effectively-once end to end.
  • Not a workflow engine: the outbox reliably emits one event per transaction. Coordinating a multi-step, compensatable flow is the saga — next lesson — which uses the outbox as its reliable publish mechanism.
  • Housekeeping: prune sent rows (delete-on-publish or a retention job) so the outbox table doesn’t grow forever.
