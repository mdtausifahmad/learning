Why Consumers ≤ Partitions — Kafka’s Consumer Group Machinery

◷ ~43 min read • Level: Depth / Staff • Deepens: Lesson 02 §3

You asked exactly the right question: in Lesson 02 we said a group can’t have more active consumers than the topic has partitions, and extras go idle. Why? This deep dive answers it three ways — the rule, the mechanism that enforces it, and the design trade-off behind it — so you can defend Kafka’s model in a staff design review, not just recite it.

1. The rule, stated precisely

The Confluent architecture course puts it in one sentence:

The invariant

“The unit of parallelism is the partition. For a given consumer group, consumers can process more than one partition but a partition can only be processed by one consumer… We could add a fifth but it would sit idle since partitions cannot be shared.”

So the maximum useful parallelism of a group equals the topic’s partition count. A consumer may own several partitions; a partition is never split across consumers of the same group. Four partitions, six consumers → four work, two stand by:

2. Why one consumer per partition? (the design reason)

The single-owner rule is not arbitrary. It buys two guarantees that Kafka’s whole model rests on:

  • Ordering. Kafka only promises order within a partition. A partition is an append-only log read sequentially by one cursor. Allow two consumers to read the same partition and “in order” becomes meaningless — they’d interleave unpredictably.
  • Offset ownership. Progress is tracked as a single committed offset per (group, partition), stored in the internal __consumer_offsets topic. One owner ⇒ one writer ⇒ one unambiguous “we’ve processed up to here.” Two owners would race on that commit and cause reprocessing or skips.
The mental model

A partition behaves like a queue with a single bookmark. Sharing the bookmark between two readers is incoherent, so Kafka assigns each partition to one reader per group. Parallelism then has to be capped at the number of partitions — the idle consumer is a direct, honest consequence of the ordering + offset guarantees, not a limitation someone forgot to fix.

3. How it’s enforced under the hood

No broker “load-balances” partitions onto consumers. In the classic consumer-group protocol used by CooperativeStickyAssignor, the group instead runs a little embedded protocol. Crucially, per the Confluent rebalancing paper, “group membership is all the broker/coordinator knows about the group” — the actual assignment is computed by the clients themselves. Kafka’s newer consumer protocol can perform assignment coordinator-side; this lesson deliberately animates the classic protocol:

  1. Find the coordinator. A consumer sends FindCoordinator(group.id). The broker hashes the group.id modulo the __consumer_offsets partition count; the broker leading that partition becomes this group’s group coordinator.
  2. Join & elect a leader. Consumers send JoinGroup with their subscriptions. The coordinator picks one (usually the first) as the group leader, hands every consumer a memberId, and hands the leader the full member + subscription list.
  3. Assign, client-side. The leader runs the configured partition assignment strategy to map partitions → members, then sends the plan to the coordinator via SyncGroup. Everyone else sends an empty SyncGroup and receives their slice back. This is the step where the 5th and 6th consumers get nothing.
  4. Heartbeat & consume. Members send periodic heartbeats. Miss session.timeout.ms and the coordinator declares you dead and triggers a rebalance — your partitions are reassigned to a survivor. That is also how an idle standby gets promoted after the timeout (or sooner after a graceful leave).
Rebalances: two costs, three complementary fixes

The classic (“eager”) protocol is stop-the-world: on any membership change every consumer revokes all partitions, then everyone gets a fresh assignment — a processing pause proportional to the load. That creates two distinct costs: needless local-state rebuilds when a partition returns to the same consumer, and needless paused processing while everyone waits for the new assignment. StickyAssignor addresses the first by preserving prior ownership where it can. CooperativeStickyAssignor addresses the second with a revoke-only round followed by an assignment round. Static membership (group.instance.id) is separate: for a short, planned restart, it can avoid starting a rebalance at all when the same stable member returns before session.timeout.ms.

4. Assignment strategies (the pluggable part)

StrategyBehaviour & when to pick it
RangeAssignor (default)Per-topic ranges. Enables co-partitioned joins: same key lands on the same-indexed partition across topics → same consumer. Can skew load with few partitions.
RoundRobinAssignorSpreads all partitions evenly across members. Better balance; loses the co-partition-join property.
StickyAssignorEven and tries to preserve prior assignment across rebalances (less churn).
CooperativeStickyAssignorSticky + incremental/cooperative rebalancing. The modern default choice for large or frequently-scaled groups.

Animation E · RangeAssignor — co-partitioned, but can skew

RangeAssignor sorts partitions and consumers alphabetically, then divides each topic's partitions into contiguous ranges. The key property: the same partition index goes to the same consumer across topics, enabling co-partitioned joins. The cost: with an uneven count, the first consumer always absorbs the extra partition on every topic.

Animation F · RoundRobinAssignor — even spread, no co-partition

RoundRobinAssignor flattens all topic-partitions into a single sorted list, then distributes them round-robin across consumers. Load is as even as possible, but same-index partitions from different topics can end up on different consumers, breaking co-partitioned joins.

Animation G · StickyAssignor — balance + churn minimisation

StickyAssignor targets two goals in order: (1) produce a balanced assignment, (2) move as few partitions as possible from the previous assignment. It keeps local state alive where it doesn't need to move. The underlying rebalance is still eager (stop-the-world); stability is the gain, not reduced pause time.

Animation H · CooperativeStickyAssignor — sticky + no group-wide pause

CooperativeStickyAssignor adds an incremental two-round protocol on top of Sticky's assignment algorithm. Only the partition that must move is revoked in round 1; it is assigned to its new owner in round 2. Unaffected partitions keep processing throughout.

5. Pros & cons of the whole design

Why Kafka chose this — the wins

Brokers stay dumb and scale. They only store the log and track group membership + offsets; all coordination is client-side. This is a big reason a Kafka cluster can host tens of thousands of consumer groups. Strong per-partition ordering and clean, single-writer offsets fall out for free. Automatic failover: a dead consumer’s partitions are reassigned to survivors (idle standbys become useful instantly). Elastic scaling up to the partition count with no code change — just add instances.

What you pay — the trade-offs

Parallelism is capped by partition count, decided largely up front — under-partition and you can’t scale out later without pain. Idle consumers waste money if you over-provision instances. But over-partitioning isn’t free either: more partitions mean more open file handles and memory on brokers, longer leader elections and failover, higher end-to-end latency, and slower rebalances. For normal keyed routing, changing partition count reshuffles key→partition mapping, which can break historical per-key ordering and co-partitioning. Hot partitions (key skew) overload one consumer while others idle. And rebalances pause processing unless you adopt cooperative rebalancing + static membership.

Rule of thumb for partition count

Pick partitions for your target peak throughput and parallelism, with headroom — it’s far easier to run fewer consumers than partitions than to add partitions later. A common heuristic: partitions = max(target_throughput / per-consumer_throughput, desired_max_consumers), then round up for growth. Avoid the reflex to set it to thousands “just in case.”

6. Increasing partitions in production: a routing change, not a resize

Kafka does let you increase a topic’s partition count; it does not let you decrease it. The difficult part is not the command. Adding partitions changes the topology that producers, consumers, and stream processors use. It does not take the data already in the topic and spread it over more workers. Apache Kafka’s topic-operation documentation calls out both consequences: existing data is not automatically redistributed, and keyed records can be mapped differently after the count changes.

The production mental model

An in-place increase is a future-routing migration, not a resize of yesterday’s workload. New partitions start empty. Old records, old lag, and a hot key’s old history stay in their original partitions. Future records may follow a different route.

What changes, and what does not

After 4 → 6 partitionsProduction consequence
Only P4 and P5 are createdP0–P3 are not split. Historic records and any backlog remain where they were, so an existing hot partition is not repaired.
Future keyed routing can changeWith the usual keyed hash/modulo route, the same key can move to a new partition. Kafka still orders each individual partition, but the key now has two independent histories.
Clients discover new metadataA subscribed group must coordinate a fresh assignment before P4/P5 have owners. With no committed offset on a new partition, auto.offset.reset=latest can skip records written before that group begins reading it.
Potential parallelism growsActual processing capacity grows only when consumer capacity is available. With the same number of consumers, they simply own more partitions.
Topology assumptions changeCo-partitioned topics, Kafka Streams joins, explicit partition numbers, monitoring/alert thresholds, and capacity plans need review. A Streams equi-join requires matching partition counts and partitioning.

Staff-level decision checklist

Before an in-place increase, make the boundary explicit: (1) which keys need strict historical order, (2) whether any streams/join inputs must remain co-partitioned, (3) how every consumer initializes new-partition offsets, (4) which consumers will absorb the added partitions, and (5) how you will watch assignment churn, skipped-record risk, consumer lag, and broker capacity. If those answers are not safe, create a versioned topic, cut each key over only after old work drains (or merge with a sequence), and migrate co-partitioned inputs together.

7. In your stack: Spring Kafka knobs

In spring-kafka, the concurrency on a listener container is how many consumer threads that app instance runs in the group. Total consumers = (instances × concurrency) — and anything beyond the partition count sits idle. 

@Bean
fun kafkaListenerContainerFactory(
    cf: ConsumerFactory<String, OrderPlaced>,
): ConcurrentKafkaListenerContainerFactory<String, OrderPlaced> =
    ConcurrentKafkaListenerContainerFactory<String, OrderPlaced>().apply {
        consumerFactory = cf
        setConcurrency(4)   // 4 consumer threads; give the topic ≥ 4 partitions or some idle
    }
# application.yml — the levers this lesson explained
spring:
  kafka:
    consumer:
      group-id: fulfillment
      properties:
        partition.assignment.strategy: org.apache.kafka.clients.consumer.CooperativeStickyAssignor
        session.timeout.ms: 45000          # miss heartbeats this long -> declared dead -> rebalance
        max.poll.interval.ms: 300000       # too-slow processing also triggers a rebalance
        group.instance.id: ${STABLE_MEMBER_ID}  # e.g. StatefulSet slot; preserve a transient restart
The most common real-world bug this explains

“We scaled to 20 pods but throughput flatlined.” The topic had 8 partitions — so 12 pods were idle. More partitions may be the capacity fix, but treat the increase as a controlled routing change before applying it. Now you know exactly why.
