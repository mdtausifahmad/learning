Queues vs Topics — One Consumer, or Many?

◷ ~12 min read • Level: Foundations • Builds on: Lesson 01

In Lesson 01 you put a durable broker between producer and consumer. The very next question a designer must answer — and the one interviewers and design reviews probe first — is: when a message lands in the broker, does it go to exactly one consumer, or to everyone who cares? That single choice has its own name, its own tooling, and its own failure modes.

1. Two channels, two intentions

Messaging systems give you two fundamental kinds of channel. The Enterprise Integration Patterns catalog names them precisely:

  • Point-to-point channel (a queue). Guarantees that exactly one receiver consumes each message. Use it when a piece of work must be done once: charge this payment, ship this order.
  • Publish-subscribe channel (a topic). Delivers a copy of each message to every subscriber. Use it to announce that something happened, so any number of interested parties can react independently.

2. Scaling a queue: competing consumers

A queue is not limited to one consumer process. Put several consumers on the same queue and they become competing consumers — they race for messages, and the broker hands each message to exactly one winner. This is how you scale throughput horizontally: add more consumers, drain the queue faster, still process each message once.

The trap that catches everyone

Competing consumers only works on a queue. As EIP puts it bluntly: putting multiple consumers on a publish-subscribe channel just creates more copies of every message. Ten subscribers on a topic = ten full copies, not shared work. Mixing these up is the classic “why is every email being sent ten times?” incident.

3. The unifier: how Kafka gives you both

Here is the model that makes Kafka click. A Kafka topic is consumed by consumer groups:

  • Within one group — the group’s members are competing consumers. Kafka splits the topic’s partitions across them, so each message is handled by exactly one member. That is point-to-point.
  • Across many groups — each group independently receives every message. That is publish-subscribe fan-out.

So “one consumer or many?” in Kafka becomes “same group, or different groups?” — the single most useful lever in spring-kafka: 

// SAME groupId on every instance → competing consumers.
// Run 3 pods; Kafka shares the partitions; each order handled once.
@Component
class FulfillmentListener(private val fulfillment: FulfillmentService) {
    @KafkaListener(topics = ["order.placed"], groupId = "fulfillment")
    fun handle(event: OrderPlaced) = fulfillment.reserveStock(event)
}
// DIFFERENT groupIds → publish-subscribe fan-out.
// Email and Analytics each receive their OWN copy of every order.
@Component
class EmailListener(private val email: EmailService) {
    @KafkaListener(topics = ["order.placed"], groupId = "email")
    fun handle(event: OrderPlaced) = email.sendConfirmation(event)
}

@Component
class AnalyticsListener(private val analytics: AnalyticsService) {
    @KafkaListener(topics = ["order.placed"], groupId = "analytics")
    fun handle(event: OrderPlaced) = analytics.record(event)
}
Staff-level nuance

Partitions cap your competing-consumer parallelism: a group can have at most as many active consumers as the topic has partitions — extra consumers sit idle. And ordering is only guaranteed within a partition, which is chosen by the message key. Pick customerId as the key and all of one customer’s events stay ordered on one partition. We’ll go deep on this in the ordering lesson — just plant the flag now: partitions = the unit of both parallelism and ordering.

4. Same idea, every broker in your stack

BrokerPoint-to-point (handled once)Pub/sub fan-out (all get a copy)
KafkaOne consumer group on a topicMultiple consumer groups on a topic
RabbitMQConsumers on one queueFanout/topic exchange → many queues
AWSAn SQS queueAn SNS topic → many SQS/HTTP
RedisStream + consumer group (XREADGROUP)Pub/Sub, or multiple stream groups
PulsarShared / Key_Shared subscriptionMultiple subscriptions on a topic

Notice the recurring shape: a queue-like thing for shared work, a topic-like thing that fans out, and a “group/subscription” concept that lets you get one from the other. Learn the shape once; the product names are just dialects.
