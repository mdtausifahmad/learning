Async & Messaging · Capstone Project

Build an Event-Driven Order Saga

Kotlin · Spring Boot 4 · Kafka · Postgres • Orchestration-based saga • 7 milestones · per-milestone review

This is where knowledge and skills become wisdom. You’ll build a real, running event-driven pipeline in your daily stack — and every pattern from the course shows up as code you write yourself. The scaffold (in ./order-saga/) hands you the infrastructure and plumbing; you fill in the pattern logic at the TODO(Mx) markers, one milestone at a time. I review each milestone against its acceptance criteria before you move on.

What you’re building

A customer places an order. A saga orchestrator drives it across three services — each with its own tables — reserving inventory, charging payment, and confirming (or, on failure, compensating and cancelling). Every event is published reliably via a transactional outbox, every consumer is idempotent, failures land in a DLQ, and the whole flow is one distributed trace.

How the review loop works

You picked per-milestone review. For each milestone: implement its TODO(Mx)s, verify against the acceptance criteria, then come back and paste the code you wrote (or push to a repo and share) plus what you observed. I’ll review it against the criteria and the relevant lessons — catching bugs, missed edge cases, and design issues — before you move to the next. Bring questions any time; that’s the point.

The milestones

M0 · Boot the stack (setup)

Goal

Get everything running before you write logic.

  • Do: podman compose up -d; ./gradlew bootRun.
  • Acceptance: app starts; curl localhost:8080/actuator/health is UP; the 6 topics appear in Kafka UI (localhost:8080); Jaeger UI loads (localhost:16686). (The listeners log but do nothing yet — expected.)

M1 · Transactional outbox (Lessons 14, 09)

  • Build: OrderService.placeOrder (create Order(PENDING) + insert an OutboxEvent(OrderCreated) in one @Transactional); OutboxRelay.publishPending (poll unsent rows in order, publish keyed by orderId, mark sent).
  • Acceptance: POST an order → an OrderCreated lands on order.created in Kafka UI, and the outbox row flips to sent=true. Crash test: throw right after the DB commit but before the relay runs (or stop the app) → on restart the event still publishes. No lost, no phantom events.

M2 · Idempotent inventory consumer (Lessons 08, 05)

  • Build: InventoryListener.onReserve — dedup on messageId via processed_messages, reserve stock, and reply InventoryReserved/InventoryFailed — all atomically.
  • Acceptance: hand-produce the same ReserveInventory twice (Kafka UI can produce) → stock is reserved once; the second is skipped. A reply appears on inventory.replies.

M3 · Saga happy path (Lessons 13, 15)

  • Build: the orchestrator handlers (OrderCreated → ReserveInventory; InventoryReserved → ChargePayment; PaymentCharged → confirm) and PaymentListener.onCharge (idempotent charge; reply). Persist SagaInstance state; keep transitions idempotent.
  • Acceptance: POST an order with amount ≤ 1000 → within a moment GET /orders/{id} is CONFIRMED, inventory reserved, a payment row exists, and an OrderConfirmed is on order.events.

M4 · Compensation (Lesson 15)

  • Build: failure handlers — PaymentFailed → send ReleaseInventory then cancel; InventoryFailed → cancel; InventoryListener.onRelease (idempotent compensation).
  • Acceptance: POST an order with amount > 1000 (simulated decline) → order ends CANCELLED, the reservation is released (inventory back to where it started), no charge. A consistent end state — no partial mess.

M5 · Retries, backoff & DLQ (Lesson 11)

  • Build: in KafkaConfig.errorHandler, a DefaultErrorHandler with ExponentialBackOffWithMaxRetries + DeadLetterPublishingRecoverer; mark a parse/validation error non-retryable; add ErrorHandlingDeserializer in application.yml.
  • Acceptance: produce a malformed/poison message to a command topic → after N bounded retries it lands on <topic>.DLT without blocking the partition (later valid messages still process). A transient failure retries then succeeds.

M6 · Guarantees & ordering (Lessons 05, 06, 09)

  • Build: confirm enable.idempotence=true, acks=all; ensure every send is keyed by orderId. (Stretch: wrap the read-process-write in Kafka transactions with read_committed.)
  • Acceptance: fire many concurrent orders → each order’s events stay in order on its partition; no duplicate side effects (your idempotency + producer idempotence hold).

M7 · Observability & load (Lessons 10, 18)

  • Build: tracing is pre-wired — confirm a single trace spans Order → relay → orchestrator → inventory/payment in Jaeger. Watch consumer lag (Kafka UI / actuator metrics). Drive a burst of orders and observe lag rise then drain.
  • Acceptance: one Jaeger trace shows the whole async flow as a waterfall; under a load spike, lag climbs then recovers (load leveling), with no lost work.
Definition of done

An order either fully completes (confirmed, stock reserved, charged) or fully compensates (cancelled, stock released, no charge) — reliably, idempotently, in order, with poison messages quarantined to a DLQ and the whole flow visible as one trace. When you can demo that end to end, you’ve built a staff-grade event-driven system.

Stretch goals (if you’re hungry)

Publish orchestrator commands via their own outboxes (reliable everywhere) · add a CQRS read model projecting order.events into an order-summary view (Lesson 17) · add a schema registry + Avro and evolve an event compatibly (Lesson 16) · split the single app into真 separate deployable services.

Ready when you are. Do M0 first (get it booting), then tell me “M0 done” (or share any startup errors) and I’ll confirm you’re green before M1. Stuck on setup, podman, or an SB4 quirk? Just ask.
