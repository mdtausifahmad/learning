System Design · Reference 05

Asynchronism & Messaging

Compressed from Lesson 05•Print-friendly
Mindset

Async buys decoupling, absorption of spikes and independent scaling, and costs you eventual consistency and harder debugging. Assume at-least-once delivery and make every consumer idempotent.

When to go async

  • The caller doesn’t need the result right now (email, thumbnails, analytics, fan-out).
  • Work is slow or bursty and should be levelled by a buffer.
  • Producers and consumers should scale and fail independently.
  • Several downstream systems react to one fact (pub/sub).
  • Stay sync when the user needs an immediate answer (auth, price, stock check).

Queue vs pub/sub vs log

Work queuePub/subLog (Kafka)
DeliveryEach message to one consumerEach message to every subscriberEach consumer group reads every message
RetentionDeleted on ackUsually transientKept for a time/size window; replayable
ExamplesSQS, RabbitMQSNS, Redis pub/subKafka, Kinesis, Pulsar
Use forTask distributionNotifications, fan-outEvent streams, CDC, replay, analytics

Back-pressure & poison messages

  • Bounded queues; when full, reject (429/503), block or shed — never grow without limit.
  • Alert on queue depth and consumer lag, not just errors.
  • After N failed attempts, move the message to a dead-letter queue with context; alert and replay after the fix.

Delivery semantics

GuaranteeMeaningCost
At-most-onceMay be lost, never duplicatedAck before processing
At-least-once (default)Never lost, may be duplicatedConsumer must be idempotent
Exactly-onceOnce, effectivelyOnly inside a closed system (Kafka transactions) or via at-least-once + idempotency

Idempotency techniques: processed-message-ID table (dedupe in the same transaction as the effect), natural keys with upserts, conditional writes (version / compare-and-set), Idempotency-Key on APIs.

The dual-write problem

// BROKEN: DB commit succeeds, publish fails (or the reverse)
db.save(order); broker.publish(OrderPlaced)

// FIX 1 — transactional outbox
tx { db.save(order); db.insert(outbox, OrderPlaced) }  // relay publishes later
// FIX 2 — CDC: tail the DB log (Debezium) and emit changes

Kafka in one screen

  • Topic → partitions (ordered, append-only); offset = position. Order is per partition only — key by entity ID.
  • Consumer group: each partition read by one member; max parallelism = partition count.
  • Durability: replication factor 3, acks=all, min.insync.replicas=2; the ISR is the in-sync replica set.
  • Fast because of sequential disk I/O, page cache, zero-copy and batching.
  • Unlike a queue, messages stay after consumption → replay, multiple independent readers.

Review questions

  • Does the caller truly need the result synchronously?
  • Queue, pub/sub or log — and why? Is replay needed?
  • Is every consumer idempotent? What happens on a redelivery?
  • How do DB state and published events stay consistent (outbox / CDC)?
  • Where is the DLQ, who is alerted, and how is it replayed?
  • What ordering is required, and does the partition key give it?
Traps
  • Unbounded queues — latency grows silently until memory runs out.
  • Assuming exactly-once — duplicates will arrive.
  • Dual writes to DB and broker without an outbox or CDC.
  • Global ordering demands that kill parallelism — order per key instead.
  • Async everything — a simple request becomes an untraceable distributed workflow.
