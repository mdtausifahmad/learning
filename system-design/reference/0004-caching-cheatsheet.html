Caching

Compressed from Lesson 04•Print-friendly
Mindset

A cache is an optimisation, never the source of truth: the system must be correct, if slower, with the cache empty. Design for stampede, hot keys and penetration up front — they only appear under load.

Eviction & invalidation

  • TTL — simplest freshness control; combine with everything.
  • LRU — most common; temporal locality. LFU — stable popularity. FIFO, random — cheap.
  • Explicit invalidation — delete/update keys on write, ideally driven by a CDC stream (Lesson 05).
  • Versioned keys — user:123:v7; a new version bypasses old entries.

Failure modes → fixes

FailureWhat happensFix
Stampede (thundering herd)Hot key expires; thousands miss and hit the DB at onceSingle-flight / coalescing, lock per key, TTL jitter, early refresh
Hot keyOne key saturates one cache nodeReplicate the key, local in-process cache in front, split the value
PenetrationRequests for keys that don’t exist always reach the DBCache “not found” with a short TTL; Bloom filter
AvalancheMany keys expire together (e.g. after restart)TTL jitter; warm the cache on startup

Review questions

  • Which layer caches this, and what is the invalidation path for each layer?
  • Why this write pattern — what consistency, latency and durability do we need?
  • What happens when the hottest key expires at peak?
  • What happens with the cache empty or down: slower, or wrong?
  • What is the hit ratio, and is it measured per cache?
Traps
  • No TTL or invalidation plan — permanent staleness.
  • App depends on the cache for correctness — an outage should cost latency, not correctness.
  • No stampede protection — the cache causes the outage it was meant to prevent.
  • Caching personalised data with low hit rates — all cost, no benefit.
  • No hit-ratio metrics — you can’t tune what you don’t measure.
