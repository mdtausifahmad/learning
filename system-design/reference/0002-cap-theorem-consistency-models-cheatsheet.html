System Design · Reference 02

CAP Theorem & Consistency Models

Compressed from Lesson 02•Print-friendly
Mindset

Partitions will happen, so the real choice is CP or AP — made per data type, from the business need. When the network is healthy you still pay: latency or consistency (PACELC).

CP vs AP

CP (consistency)AP (availability)
During a partitionRejects or blocks on the minority sideAccepts everywhere, reconciles later
Use forMoney, inventory, bookings, uniquenessFeeds, likes, carts, presence, metrics
ExamplesZooKeeper, etcd, HBase, Spanner, RDBMS with sync replicationCassandra, DynamoDB (default), Riak, DNS
User feels“Try again later”“Slightly old data”
PACELC labelsSpanner: PC/ECCassandra, DynamoDB: PA/EL

There is no CA distributed system. A single node is “CA” only because it isn’t distributed. CAP’s C is linearizability, not ACID’s C (invariants inside a transaction).

The consistency spectrum (strong → weak)

ModelGuaranteeCost
LinearizableActs like one copy; a read returns the latest committed writeCoordination / consensus; highest latency
SequentialEveryone sees the same order, not necessarily real-time orderHigh
CausalCause before effect for everyone (reply after post); concurrent ops in any orderModerate — no global coordination
EventualIf writes stop, replicas converge; reads may be stale meanwhileCheapest, most available
  • Read-your-writes — you always see your own latest write. The usual UX fix on eventual stores.
  • Monotonic reads — time never goes backwards for one client.
  • Practitioner lens — weak (VoIP, games) · eventual (DNS, email) · strong (RDBMS, file systems).

Quorums: N, W, R

N = replicas   W = acks per write   R = replies per read
W + R > N   → read and write sets overlap → strong reads
W + R ≤ N  → eventual, higher availability, lower latency
ConfigPropertyUse when
W=N, R=1Fast reads; slow, fragile writesRead-heavy, rarely written
W=1, R=NFast writes, slow readsWrite-heavy ingest
N=3, W=2, R=2Strong; tolerates one node downThe usual default
W+R ≤ NEventual, max availabilityAP systems

Topologies: single-leader → multi-leader → leaderless. More leaders = more availability, harder conflict resolution (last-write-wins, version vectors, CRDTs).

Consensus

  • Paxos / Raft — elect a leader, replicate an ordered log; a value commits once a majority persists it.
  • Use, don’t build — etcd, ZooKeeper for leader election, config and locks.
  • Need it for coordination, uniqueness and ordering — not for every piece of data.

Review questions

  • For each stateful component: what happens during a partition? CP or AP, and why is that right for this data?
  • Which reads need read-your-writes or monotonic reads? How are they routed?
  • What is replication lag at peak (not idle)? What does the UX do while lagging?
  • What are N/W/R per table, and is W + R > N where it must be?
  • With multiple leaders: what is the conflict strategy?
Traps
  • “Eventual” = a few ms — under load or partition, lag runs to seconds or minutes.
  • CAP’s C confused with ACID’s C.
  • “We picked CA” — no: you picked CP or AP and haven’t had a partition yet.
  • Multi-leader without a conflict strategy — silent lost updates.
