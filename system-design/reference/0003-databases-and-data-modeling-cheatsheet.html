System Design · Reference 03

Databases & Data Modeling

Compressed from Lesson 03•Print-friendly
Mindset

Apply the cheapest fix that meets the numbers, and choose stores from the access pattern, not fashion. Shard keys and isolation levels are the decisions that are hardest to undo.

The scaling ladder (stop at the first rung that works)

#StepBuys youCosts you
1Indexes & query tuning (EXPLAIN)Highest ROI: ms instead of full scansWrite overhead per index
2Read replicasRead scale (most apps are read-heavy)Replication lag → stale reads
3Cache (Lesson 04)Offloads hot readsInvalidation
4Federation (split by function)Smaller DBs, more write throughputCross-DB joins move to the app
5Sharding (split by data)Write and data-volume scaleCross-shard joins/transactions, rebalancing
6DenormalisationAvoids expensive joinsWrite complexity, drift without an update plan

Replication

TopologyWritesTrade-off
Single-leaderOne primary; reads from followersSimple; strong if you read the leader. Failover risks split-brain and lost async writes.
Multi-leaderSeveral (e.g. one per region)Write locality and availability; needs conflict resolution (LWW, version vectors, CRDTs)
Leaderless (Dynamo)Any replica, quorum W + R > NHigh availability; tunable consistency (Cassandra, DynamoDB, Riak)

Sync replication: no loss on failover, slower writes. Async: fast, can lose the last writes. Most run async or semi-sync.

Sharding strategies

StrategyProCon
RangeEfficient range scansHotspots on skewed data
Hash hash(k) % NEven spreadRange queries scatter; changing N reshuffles almost everything
Consistent hashAdding a node moves ~K/N keysMore complex
Directory / lookupFlexible rebalancingLookup is a SPOF / bottleneck
GeoLocality, complianceCross-region queries are costly

Shard key: high cardinality, evenly accessed. Bad keys (e.g. country) create permanent skew. Split celebrity keys with a compound key. Consistent hashing with 100–200 virtual nodes per machine: a 4th node joining 3 moves ~25% of keys, not ~100%.

SQL vs NoSQL

Choose SQL when…Choose NoSQL when…
Relational data, stable schemaFluid schema per record
Multi-row ACID transactionsMassive horizontal write scale
Ad-hoc queries and joinsKnown, simple access by key
Consistency over raw availabilityAvailability and latency over strict consistency
  • Key–value (Redis, DynamoDB) — sessions, caches, flags.
  • Document (MongoDB, Couchbase) — catalogues, profiles, nested content.
  • Wide-column (Cassandra, HBase, Bigtable) — huge write volume, time series, range scans per partition key.
  • Graph (Neo4j, Neptune) — social graphs, recommendations, fraud rings.
  • Blur: Postgres JSONB; NewSQL (Spanner, CockroachDB, YugabyteDB) = SQL + ACID + horizontal scale.

ACID (atomic, consistent, isolated, durable) = correctness first. BASE (basically available, soft state, eventual) = availability first.

Isolation levels

LevelDirty readNon-repeatablePhantom
Read Uncommittedpossiblepossiblepossible
Read Committed (Postgres, Oracle default)preventedpossiblepossible
Repeatable Readpreventedpreventedpossible*
Serializable (often SSI)preventedpreventedprevented

* InnoDB prevents most phantoms at Repeatable Read via next-key locks. Lost update / write skew: two read-modify-writes clobber each other, or two decisions on the same read break an invariant. Escalate the specific transaction (SELECT … FOR UPDATE, serializable) rather than serialising everything.

Review questions

  • Which rung of the ladder do the current numbers justify? Were the cheaper rungs exhausted?
  • Why SQL or this NoSQL family — which access pattern drove it?
  • What is the shard key’s cardinality and skew? Which queries go cross-shard?
  • What is the default isolation level, and which invariant could an anomaly break?
  • Who reads from async replicas, and is read-your-writes handled?
  • Is the engine (B-Tree vs LSM) matched to a read- or write-heavy workload?
Traps
  • Sharding too early — loses joins and transactions, multiplies ops.
  • Skewed shard key — permanent hotspots, fixable only by migration.
  • Stale reads from async replicas with no read-your-writes routing.
  • Denormalising without an update strategy — copies drift.
  • Assuming ACID across services — use sagas or the outbox (Lesson 05).
