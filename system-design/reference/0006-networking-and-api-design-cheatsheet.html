System Design · Reference 06

Networking & API Design

Compressed from Lesson 06•Print-friendly
Mindset

Pick the communication style per boundary, and treat the API contract as the hardest thing to change later: make it idempotent, paginated, versioned and rate-limited from day one.

Transport & HTTP

TCPUDP
ConnectionHandshakeNone
ReliabilityDelivery and order guaranteedBest-effort
UseCorrectness matters (web, DBs)Speed over perfection (streaming, DNS, games)
  • HTTP/1.1 — one request at a time per connection → head-of-line (HOL) blocking; browsers open ~6 connections.
  • HTTP/2 — multiplexed streams, binary framing, HPACK. Fixes application HOL, but one lost TCP packet still stalls every stream.
  • HTTP/3 — QUIC over UDP: independent streams, 0-RTT handshakes, connection migration.

Load balancers, proxies, gateways

L4 (transport)L7 (application)
SeesIP + portURL, headers, cookies
Routes byConnectionContent (path, host, header)
Can doFast, even distributionPath routing, sticky sessions, TLS termination, canary
  • Algorithms: round-robin, weighted, least connections, least response time, IP / consistent hash (sticky).
  • Reverse proxy (Nginx, Envoy, Varnish) — TLS, caching, compression, hides topology. A load balancer is a specialised one.
  • API gateway — the front door: authN, rate limiting, routing, aggregation, protocol translation, once instead of in every service.

DNS & CDN — the outermost layers

  • Records: A, AAAA, CNAME, MX, NS, TXT. Low TTL = faster failover, more lookups.
  • DNS is the first load balancer: round-robin, GeoDNS, latency/health-based routing.
  • Pull CDN — edge fetches on first request; easy, first hit slow. Push CDN — you publish to the edge; more control.

API design checklist

  • Nouns, not verbs: GET /users/123/orders, not /getUserOrders.
  • Methods and status codes used meaningfully: 201, 204, 400, 404, 409, 422, 429, 503.
  • Idempotency: GET/PUT/DELETE idempotent; POST via an Idempotency-Key header (payments).
  • Pagination: never unbounded; prefer cursor/keyset over offset for large or live data.
  • Versioning: /v1/… or an Accept header.
  • Rate limiting: 429 + Retry-After; token bucket allows bursts, leaky bucket smooths.
  • One error shape: { code, message, details }.
  • Security: HTTPS everywhere, OAuth2/JWT, input validation, least privilege.

Review questions

  • Why this style for this boundary (public vs internal vs aggregating client)?
  • Where does TLS terminate? Is the LB L4 or L7, and why?
  • Which endpoints are unsafe to retry, and do they take an Idempotency-Key?
  • Is every list paginated, and is every endpoint rate-limited?
  • How will v2 ship without breaking v1 clients?
Traps
  • Unbounded list endpoints — fine until the data grows.
  • No versioning — you can’t evolve without breaking clients.
  • Non-idempotent POSTs for payments and orders — retries create duplicates.
  • Chatty REST forcing N+1 calls — aggregate or consider GraphQL.
  • Verbs in URLs, misused status codes — uncacheable and unpredictable.
