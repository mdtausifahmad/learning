System Design · Reference 08

Resilience & Fault Tolerance

Compressed from Lesson 08•Print-friendly
Mindset

Assume every dependency will be slow or down. Bound the wait, cap the retries, contain the blast radius, and decide in advance what to sacrifice — no single pattern is enough on its own.

Timeouts & retries

  • Every network call has a timeout, set from the downstream’s p99 plus margin — not a round number.
  • Timeouts shrink down the call chain, so the outermost caller times out last.
  • Exponential backoff (base × 2^attempt) + jitter so clients don’t retry in lockstep.
  • Cap attempts with a retry budget; retry only idempotent operations.
  • Retry 503 and timeouts; never 400/404 — the request itself is wrong.

Circuit breaker

Without a breaker, one degraded dependency exhausts caller thread pools across the fleet. Always pair it with a fallback (cached value, default, degraded feature). Libraries: Resilience4j, Envoy/Istio.

The pattern toolbox

PatternProtects againstKey setting
TimeoutHung dependency holding threadsDownstream p99 + margin
Retry + backoff + jitterTransient blipsMax attempts, idempotent only

Health checks

ProbeQuestionOn failure
LivenessIs the process alive?Restart it
ReadinessCan it take traffic now?Remove from the load balancer, no restart

Don’t put dependency checks in liveness — a database blip would restart the whole fleet.

Defence in depth (A calling B)

Service A
  → Bulkhead       dedicated pool for B
  → Circuit breaker fail fast if B is unhealthy  → (open) fallback: cache / default / degrade
  → Timeout        bound the wait
  → Retry          backoff + jitter, idempotent only
  → Service B

Review questions

  • Does every outbound call have an explicit timeout, and do they shrink down the chain?
  • Are retries bounded, jittered and limited to idempotent, retryable errors?
  • Which dependencies have a breaker, and what is each fallback?
  • Are pools isolated per dependency?
  • What is shed first under overload, and who can flip the kill switch?
  • Do liveness and readiness probes ask different questions?
Traps
  • No timeout — one hung dependency exhausts every caller.
  • Naive retries — a blip becomes a self-inflicted retry storm.
  • Retrying non-idempotent operations — duplicate charges and emails.
  • Shared pools across dependencies — one slow call starves all traffic.
  • Breaker with no fallback — fail fast still shows the user an error.
