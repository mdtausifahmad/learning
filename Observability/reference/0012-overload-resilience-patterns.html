Overload & Cascading Failure — Patterns

Compressed from Lesson 11•Print-friendly
The mechanism

The initial fault is small; feedback loops amplify it. Retries pile onto an overloaded backend (100 → 200 → 300 failing QPS); crashed servers shove load onto survivors. A service that cascades at 11k QPS may need to shed to ~1k to recover.

Retries, done right

  • Exponential backoff + jitter (randomise the wait).
  • Retry budget — stop when retries exceed a small fraction of requests.
  • Retry at one level only (they multiply across layers: 3×3 = 27×).
  • Only retry idempotent operations.
  • Send a clear “don’t retry / retry-after” signal when shedding.

Load shedding

Return 503 once > N in flight; do as much useful work as you can. Swap FIFO → LIFO / CoDel to drop stale requests the user already abandoned.

Prevent, don’t just react

Load-test to your breaking point (which resource fails, and how), then capacity-plan with headroom (N+2). Saturation (Ref 08) turned into a design decision.
