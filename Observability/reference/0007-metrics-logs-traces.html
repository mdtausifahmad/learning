Reliability & SRE · Reference 07

Metrics vs Logs vs Traces

Compressed from Lesson 06•Print-friendly
Monitoring vs observability

Monitoring watches known signals for known failures (known-unknowns) — tells you that it’s wrong. Observability answers questions you didn’t pre-plan (unknown-unknowns) — lets you find why, without shipping new code to do it.

The three signals

SignalIsBest atWeak atAnswers
Metricsnumeric time seriestrends, dashboards, alerts, SLIs; cheapone request; low-cardinality onlythat
Tracesa request’s spans across serviceslocalising the slow/failing hop; causalitysampling; context propagationwhere
Logstimestamped event recordsrich per-event detail & forensicsvolume/cost; aggregation; not request-linkedwhy

The 3 a.m. flow

metric/SLO alert  →  trace  →  logs
   (THAT + which)   (WHERE)    (WHY)

Correlation is the glue: metric exemplars link a spike to example traces; a trace_id on structured logs links traces ↔ logs. Without it, you have three silos, not observability.

OpenTelemetry model

  • One vendor-neutral API/SDK emits traces + metrics + logs with shared context.
  • Semantic conventions = standard attribute names (http.response.status_code).
  • The Collector exports to any backend (Prometheus/Grafana, Tempo/Jaeger, Loki).
  • Instrument once · own your data · no lock-in.
Cardinality rule

Low-cardinality dimensions → metrics. High-cardinality detail (user_id, request_id) → traces & logs (or wide events). A raw user_id label mints one time series per user — an explosion.

Pillars ≠ observability

Three data types in silos isn’t observability. The test: can you slice by any dimension to answer a question you didn’t anticipate (“p99 for Android × Brazil × checkout-v3”)? That needs high-cardinality context + correlation.
