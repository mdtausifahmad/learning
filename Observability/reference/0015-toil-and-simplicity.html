Toil & Simplicity

Compressed from Lesson 14•Print-friendly

Toil = running-a-service work that is…

Manualhands-on human time
Repetitivedone over and over
Automatableno essential human judgment
Tacticalinterrupt-driven, reactive
No enduring valueservice unchanged afterward
O(n) with growthscales with size / traffic / users

Not toil: novel debugging · building automation · improving an SLO · overhead (meetings/HR) · grungy-but-lasting cleanup.

Toil budget

Keep toil < 50%; spend the rest on engineering that reduces future toil. Measure it; breaching the cap = the trigger to automate / self-heal / fix the product / redesign. A cap that drives investment (like an error budget).

Automate carefully

Automating a bad process makes failure faster; automation is itself a system. Ladder: manual → runbook → human-triggered → self-healing. Keep humans where judgment matters.

Simplicity is a reliability control

“The price of reliability is the pursuit of the utmost simplicity.” — Hoare

  • Essential vs accidental complexity — keep the first, cut the second.
  • Boring is a virtue — surprises in production are the enemy.
  • Delete dead code — don’t comment out or leave behind a stale flag (Knight Capital: $440M).
  • Every line of code is a liability; negative lines of code is a win.
Does it pay rent?

For any new component: removes more complexity than it adds? reduces blast radius? clear owner? can on-call explain it at 03:00? If not, it’s a liability, however clever.
