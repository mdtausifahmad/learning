Blameless Postmortem — Template

Compressed from Lesson 10•Fill-in · print-friendly
The commitment

Ask how the system allowed it, not who erred. Assume good intent. You can’t fix people; you can fix systems. “Human error” is a symptom, never a root cause.

Triggers (agree before the incident)

  • User-visible downtime/degradation beyond a threshold · data loss of any kind
  • On-call intervention (rollback, rerouting) · resolution time over a threshold
  • Monitoring failure (a human found it first) · any stakeholder requests one
  • >20% of the error budget in one incident (error-budget policy) → mandatory + a P0 item

Template

Postmortem — incident title / date

Impact. Who, how badly, how long; budget spent.

Detection. How found; was it late? alert or human?

Timeline. Key events, signals, decisions (with times).

Contributing factors. Technical + process + org + knowledge. No people.

What went well. Defences that worked.

What went poorly. Defences that failed or were missing.

Action items. Specific · owned · prioritised · verified.

The action-item test

Theater (weak)Risk reduction (strong)
“be more careful”add a confirmation guard / dry-run default
“train people”automate the check; reduce blast radius
“add more monitoring”the specific alert that catches it sooner

Prefer: change a default · automate a check · shrink blast radius · make failure visible sooner. Each item owned + prioritised + tracked to done. An unowned item is a wish.

Culture

  • Review — a senior engineer checks depth & priorities. Unreviewed = never existed.
  • Share widely into a searchable repo — others learn without living it.
  • Reward surfacing problems; never stigmatise frequent postmortems.
