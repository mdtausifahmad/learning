Reliability & SRE · Reference 08

Golden Signals · RED · USE

Compressed from Lesson 07•Print-friendly
Frame

Monitoring answers what’s broken (symptom) and why (cause). Page on symptoms, debug with causes.

The four golden signals (user-facing service)

SignalMeasuresWatch out
Latencytime to serve a requesttrack success & error latency separately
Trafficdemand (req/s, sessions, txns/s)pick one high-level, service-specific metric
Errorsfailure rate: explicit / implicit / by-policy200-but-wrong-content is still an error
Saturationhow full the most-constrained resource isdegrades before 100%; p99 latency = early signal; predictive

The two lenses

LensScopeSignals
RED (Wilkie)per request-driven serviceRate · Errors · Duration
USE (Gregg)per resource (CPU, mem, disk, net)Utilisation · Saturation · Errors

RED = user symptoms (≈ golden signals − saturation). USE = resource causes. Golden ≈ RED + saturation.

Low utilisation ≠ no saturation

A resource can average 70% and still saturate in bursts (100% for seconds → queues → latency). Averages hide it — use short-window p99 and queue depth.

Designing the telemetry

  • Name with OTel semantic conventions (http.server.request.duration).
  • Bound cardinality: labels = method, route (templated), status_class. Never user_id / raw paths / timestamps.
  • Histogram latency (exponential buckets, ~×3); never the mean.
  • Right resolution: per-minute CPU misses second-long spikes — sample internally.

It connects back

SLIs are golden signals (availability = Errors, latency SLI = Latency). Alert on symptoms via burn rate (Ref 06); keep saturation/USE for debugging & capacity, not paging on every wiggle.
