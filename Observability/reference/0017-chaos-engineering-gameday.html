Reliability & SRE · Reference 17

Chaos Engineering & GameDays

Compressed from Lesson 16•Print-friendly
Definition

“Experimenting on a system to build confidence in its capability to withstand turbulent conditions in production.” A controlled experiment — not random breakage.

The experiment — 4 steps

  1. Steady state — a measurable, user-facing output = your SLIs (not CPU).
  2. Hypothesise it holds in control & experimental groups.
  3. Inject real-world events (crash, latency, severed network, dep failure, resource exhaustion).
  4. Try to disprove — did steady state diverge? Harder to break = more confidence; a weakness = a fix target.

Advanced principles

  • Hypothesise on the output, not internals (verify it works, not how).
  • Vary real events, prioritised by impact × frequency.
  • Run in production eventually (start in staging).
  • Automate to run continuously (Chaos Monkey).
  • Minimise blast radius + keep an abort switch.
Prerequisites — don’t skip

Need observability (see impact) + SLOs (steady state) + mitigation/rollback (stop it). Chaos on an un-observed, un-resilient system is just an outage. Tell on-call first.

GameDay run-sheet

1. Steady state    1–2 SLIs, current values
2. Failure         one realistic event (kill instance / +300ms dep / block downstream)
3. Hypothesis      "tolerated because <resilience pattern L11–12>"
4. Blast radius    smallest useful; ABORT condition = SLO breach
5. Run (staging → prod), observe, note surprises
6. Write up        postmortem-style; file fix action items

Tools: Chaos Monkey · Gremlin · AWS FIS · chaos-mesh / LitmusChaos (k8s).
