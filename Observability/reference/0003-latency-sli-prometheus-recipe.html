Latency & Availability SLIs in Prometheus

Worked recipe · supports Lesson 02•Print-friendly

Two ways to use a histogram — pick the right one

A classic Prometheus histogram foo exposes three series: cumulative buckets foo_bucket{le="…"} (each counts observations ≤ that bound), plus foo_count and foo_sum. The le="+Inf" bucket equals foo_count. Two very different questions:

You want…UseShape
The SLI — “what % were fast enough?”Bucket ratio0–100% · composes with error budget
A dashboard line — “what is my p99?”histogram_quantile()a latency value (seconds), estimated
The rule

For an SLO, use the bucket-ratio form — it’s a good÷valid ratio. Reserve histogram_quantile() for graphs; it interpolates a value inside a bucket and isn’t a 0–100% ratio.

The latency SLI (ratio form)

# Proportion of requests served faster than 300 ms, over 28 days
sum(rate(http_request_duration_seconds_bucket{job="checkout", le="0.3"}[28d]))
  /
sum(rate(http_request_duration_seconds_count{job="checkout"}[28d]))
The bucket gotcha

The ratio form can only test thresholds that exist as a bucket boundary (le). If your SLO is “99% < 400 ms”, you must have an le="0.4" bucket. Define custom buckets around your target thresholds at instrumentation time — the defaults rarely line up.

Don’t measure the latency of errors

A 500 that fails in 5 ms is fast but not good. Ideally the latency SLI counts successful requests only. But a histogram usually has no status label (adding code would explode cardinality). Options, cheapest first:

  • Instrument the histogram to observe only successful requests; or
  • Add a low-cardinality label like outcome="success|error"; or
  • Measure latency across all requests and let the availability SLI catch the errors.
# With a low-cardinality outcome label — successful AND fast:
sum(rate(http_request_duration_seconds_bucket{job="checkout", outcome="success", le="0.3"}[28d]))
  /
sum(rate(http_request_duration_seconds_count{job="checkout", outcome="success"}[28d]))

p99 for a dashboard (aggregate buckets first!)

histogram_quantile(0.99,
  sum by (le) (rate(http_request_duration_seconds_bucket{job="checkout"}[5m])))

Always sum by (le) to aggregate replicas before the quantile. Never average pre-computed p99s — percentiles don’t average. (Histograms aggregate; summaries can’t, which is why histograms win for multi-replica services.)

The availability SLI — what counts as “valid”?

Principle: valid = events your service is accountable for; good = valid events that did their job. Map status codes to that intent — don’t just bucket them.

StatusVerdictWhy
2xx, 3xxgood (valid)Service did its job.
5xxbad (valid)Server failure — your fault.
429bad (valid)You shed load; the user was refused.
Other 4xx
400/401/403/404/422		excludedClient’s bad request — not your reliability.
Health checks, bots, syntheticsexcludedNot real user events.
 
# Refined availability: good = 2xx/3xx ; valid = good + server-side failures (5xx, 429)
sum(rate(http_requests_total{job="checkout", code=~"2..|3.."}[28d]))
  /
sum(rate(http_requests_total{job="checkout", code=~"2..|3..|5..|429"}[28d]))

# Simpler default (good = anything but 5xx). Beware: this scores 429 as "good".
sum(rate(http_requests_total{job="checkout", code!~"5.."}[28d]))
  / sum(rate(http_requests_total{job="checkout"}[28d]))
Status codes are a proxy

If your bug makes valid requests return 400 or 404, a code-based SLI hides it. Exclude 4xx by default, but watch for 4xx spikes that are really your fault (routing bugs, auth outages). The truest SLI is semantic (“did the user get what they came for?”) — codes are the pragmatic 80/20.

Recording rules — precompute the SLI

28-day queries over raw buckets are expensive, and you’ll reuse the SLI for dashboards, budgets, and burn-rate alerts (Lesson 04). Precompute short-window good/valid rates, then divide. Follow the level:metric:operation naming convention. 

groups:
- name: checkout_slo
  interval: 30s
  rules:
  - record: job:http_req_duration:good_le300ms:rate5m
    expr: sum(rate(http_request_duration_seconds_bucket{job="checkout", outcome="success", le="0.3"}[5m]))
  - record: job:http_req_duration:valid:rate5m
    expr: sum(rate(http_request_duration_seconds_count{job="checkout", outcome="success"}[5m]))
  - record: job:slo_latency_300ms:ratio_rate5m
    expr: |
      job:http_req_duration:good_le300ms:rate5m
      /
      job:http_req_duration:valid:rate5m
  • Record the same ratio at several windows (5m, 30m, 1h, 6h) — multi-window burn-rate alerting needs them (Lesson 04).
  • For the 28-day error budget, compute over the window with increase() on the good and valid counters (not a 28d rate).
  • Validate rule files with promtool check rules file.yml.
  • Generators like Sloth can emit these recording + alerting rules from a short SLO spec — worth adopting once you’ve done it by hand once.

Modern direction

Native histograms (and OpenTelemetry exponential histograms, which map to them) remove the fixed-bucket problem — dynamic resolution, any threshold. Support is still rolling out; classic le buckets remain the mainstream today. If you control instrumentation, keep an eye on native histograms.

One-line takeaways

SLI → bucket ratio, not histogram_quantile. · Threshold must be a bucket boundary. · Don’t time your errors. · valid = your fault to serve; exclude client 4xx, keep 429/5xx. · Precompute with recording rules.
