Reliability & SRE · Reference 10

Incident Response — Roles, Severity, Lifecycle

Compressed from Lesson 09•Print-friendly
The one move

Separate command (coordinating) from firefighting (fixing). Clear roles give more autonomy, not less.

Roles (scale up as the incident grows)

RoleOwnsRule
Incident Commanderstate, decisions, delegation, single source of truthnot a resolver
Ops Leadhands-on investigation & mitigationonly one who changes the system
Comms Leadstakeholder updates; incident doc; status pageshields responders
Planning Leadbugs, handoffs, tracking changes to revertfrees Ops

Small incident = one person wears all hats. Split out as it grows.

Severity — by impact, not panic

SevImpactResponse
SEV1broad outage / data lossall-hands, exec comms, ~30-min updates
SEV2significant / partial degradationon-call team + IC, ~hourly updates
SEV3minor / limitedsingle team, next business day

Lifecycle

Detect → Triage (severity) → Assign roles → MITIGATE → Resolve → Postmortem
                        └──────── Communicate, continuously ────────┘
Mitigate before you diagnose

Stop the bleeding first — rollback, failover, shed load, feature flag — then root-cause. Users care that it works, not why it broke.

Communication

  • Steady cadence — even “no change, next update in 30 min”.
  • One source of truth: living incident doc (not on the system you’re fixing) + status page.
  • Declare early — declaring is cheap, heroic silence is expensive.
  • Hand off the IC role explicitly, with state.

Sustainable on-call

Actionable pages (not noise) · runbooks · humane rotation · authority to fix what pages you. Alert quality (Ref 06) is how you keep responders sharp.
