Overload & Cascading Failure

◷ ~12 min read • Level: Judgment • Prereq: Lesson 07 — saturation

You can respond to and learn from failure (Lessons 9–10). Now prevent the worst kind: the local hiccup that becomes a global outage. Overload and cascading failure is how one slow dependency takes down everything — and the patterns here are the difference between a blip and a company-wide incident. This is core staff-level design judgment.

1. How a 1% blip becomes a total outage

The danger is never the initial fault — it’s the feedback loops that amplify it. Google’s canonical example: a backend caps at 10,000 QPS. The frontend sends 10,100 — just 1% over. The backend rejects 100; naive clients retry them; now it’s 10,200, of which 200 fail; the retries snowball 100 → 200 → 300 QPS… until the backend melts down.

Recovery is brutal

A service healthy at 10k QPS that cascades at 11k will not recover by dropping to 9k — you’re now serving increased demand with crash-looping capacity. You might have to shed all the way down to ~1k QPS before it stabilises. Far better to never enter the spiral.

2. Load shedding — fail early and cheaply

When a server approaches overload, it should reject excess work fast (e.g. return 503 once more than N requests are in flight) rather than accept everything and collapse. Shed the least valuable work first, and do as much useful work as you can. A fast rejection beats a slow collapse.

Smarter queues help too: switch FIFO → LIFO or CoDel to drop stale requests the user already abandoned — if a request has queued 10 seconds, the user has refreshed and it’s pointless to serve.

3. Retries — necessary, and dangerous

Retries caused the spiral above. Do them right:

  • Exponential backoff — wait longer after each failure.
  • Jitter — randomise the wait so clients don’t retry in a synchronised wave (a self-inflicted thundering herd).
  • Retry budget — cap retries to a small fraction of requests (say 10%); when exceeded, stop.
  • Retry at one level only — retries at every layer multiply (3 layers × 3 tries = 27×).
  • Only retry idempotent operations — or you duplicate effects.
Why jitter matters

Plain backoff still lets thousands of clients retry in lockstep — they all failed at the same instant, so they all wait the same interval and hit the recovering dependency together. Adding randomness spreads them out, so recovery isn’t crushed by a synchronised retry wave.

4. Circuit breaker — stop hammering a failing dependency

When a dependency is failing, calling it harder makes things worse. A circuit breaker tracks failures and, after a threshold, opens — failing fast without calling the dependency — giving it room to recover. Periodically it half-opens to test with one request; if that succeeds, it closes and resumes. Watch your thresholds, or the breaker oscillates.

5. Bulkhead — isolate the blast radius

Named after a ship’s watertight compartments: give each dependency (or tenant, or feature) its own resource pool — separate thread pools, connection pools. Then one saturated dependency can’t consume every thread and sink the whole service. The cost: over-partitioning wastes capacity, so isolate what matters.

7. You can’t tune what you haven’t measured

None of this works without knowing your breaking point. Load-test to find the QPS where the service fails and how it fails, then capacity-plan with headroom (e.g. N+2). This is saturation (Lesson 07) turned into a design decision.
