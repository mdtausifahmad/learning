Graceful Degradation & the Thundering Herd

◷ ~11 min read • Level: Judgment • Prereq: Lesson 11 — overload & load shedding

Lesson 11 stopped the cascade with load shedding and circuit breakers. Two more spike-survival moves finish the resilience toolkit: when you can’t serve full quality, serve something (graceful degradation); and stop your own clients and caches from stampeding in unison (the thundering herd).

1. Graceful degradation: do less, stay up

Load shedding drops requests; graceful degradation reduces the work per request. When overloaded, serve cheaper, lower-quality results instead of falling over:

  • Search a cached subset instead of the full on-disk database.
  • Use a faster, less-accurate ranking algorithm.
  • Serve slightly stale cached data.
  • Drop the recommendations carousel — but keep checkout working.
Protect the critical journey

The move is to preserve the critical user journey and shed quality on the non-critical. That requires product decisions made before the incident: which features are droppable? Decide it calm, not at 3 a.m. This is your SLO priorities (Lesson 03) turned into a degradation plan.

The code path you never use doesn’t work

Degraded mode should trigger rarely — which means it’s the least-tested code you own, and quietly rots. Keep it simple, exercise it regularly (run a few servers near overload), alert when servers enter it, and give yourself a kill switch.

2. The thundering herd: correlated clients

A thundering herd is what happens when many independent clients become synchronised — same trigger, same timer, same expiry — so a spike lands all at once. The family:

HerdWhat synchronises
Retry storm (L11)everyone fails together, so everyone retries together
Cache stampede (dogpile)a hot key expires — every request misses and recomputes the same value at once
Cold-cache restarta fleet restart / cache flush drops hit rate to ~0, hammering the backend
Synchronised timersa midnight cron, a reconnect storm after a blip, TTLs all expiring together

3. The cache trap: latency cache vs capacity cache

Know which cache you have

A latency cache just speeds you up — the service still handles expected load with an empty cache. A capacity cache is a hard dependency: the service cannot serve normal load cold. Caches added “for performance” silently become capacity caches — and then a routine restart becomes an outage. Keep caches as latency caches, or engineer them to survive cold.

4. Taming the herd

  • Jitter & stagger. Randomise retry waits, cache TTLs (so keys don’t all expire together), cron times, and reconnect delays.
  • Request coalescing (single-flight). When many requests want the same missing key, let one compute it and the rest wait for that result — the backend does the work once.
  • Refresh early / serve-stale-while-revalidate. Recompute a hot key before it expires, or serve stale during the recompute, so expiry never causes a miss storm.
  • Gradual warmup / slow start. After a restart, ramp traffic slowly to warm the cache; don’t send full load to a cold server. Keep clusters warm.
  • Rate limit / token bucket. Smooth bursts into a steady flow.
One principle underneath them all

Herds happen because independent things became correlated. Nearly every fix is one of three moves: add randomness (jitter), dedupe (coalesce), or ramp (slow start). Even config pushes: rolling out to every task at once is a self-inflicted herd — push gradually, off-peak.
