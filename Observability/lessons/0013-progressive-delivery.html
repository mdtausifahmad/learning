Reliability & SRE · Lesson 13

Progressive Delivery: Canary, Flags & Rollback

◷ ~12 min read • Level: Practical → Judgment • Prereq: L04 budget · L07 signals

A majority of incidents are triggered by binary or config pushes. So the highest-leverage reliability work isn’t heroics — it’s making change safe. Progressive delivery exposes a change gradually and gives you an escape hatch. For a builder who ships features, this is where reliability meets your daily workflow.

1. The foundation: separate deploy from release

DeployRelease
Get the new code onto production servers — dark, with no user impact. Expose the new behaviour to users.
Why decoupling is the master move

Feature flags let you deploy safely anytime, then release gradually and disable instantly — with no redeploy. Deploy becomes low-risk; release becomes a dial you control. Everything else in this lesson builds on that split.

2. Canary: prove it on a small slice of real traffic

A canary is a partial, time-limited deployment of a change plus its evaluation. The subset that gets the change is the canary; the rest is the control. You compare the canary’s SLIs — errors and latency, your golden signals — against the control, on the same real traffic. It’s A/B testing for safety.

Widen gradually — internal → 1% → 10% → 50% → 100% — with bake time at each step, and gate promotion on your SLOs / error budget (Lessons 3–5). Tests are never 100% like production; a canary catches what only real traffic reveals.

3. Feature flags: the escape hatch

Flags do more than gate releases — and different kinds are managed differently:

Toggle typePurpose
Releasehide a half-built feature; short-lived, dev-owned.
ExperimentA/B test for impact; product-owned.
Opsthe kill switch — disable a feature under load (e.g. “use the simplistic recommendation algorithm”).
The Ops toggle is graceful degradation

That kill switch is exactly Lesson 12’s degraded mode, made operable. Best practices: expose the current flag state to operators, give each flag a human-readable description (priceless mid-incident), and pay down flag debt — delete toggles once they’ve served their purpose.

4. Rollback is a reliability feature

Fast, tested rollback beats fast diagnosis (Lesson 09: mitigate first). But a rollback is only safe if you’ve engineered for it:

  • Tested — practised and automated, not improvised at 3 a.m.
  • Schema-safe — database changes are backward-compatible, so the old code still works against the new schema.
  • Mixed-version safe — during a rollout, old and new run together; both must cope.

Small, self-contained deployments make rollback cheap. If a change is irreversible (a destructive migration), the rollout needs extra safeguards — you’ve given up your escape hatch.

Expand / contract for stateful changes

Make schema and API changes in compatible steps: expand (add the new, both old and new work) → migrate → contract (remove the old). At every step old and new coexist, so canary and rollback stay safe. Skip this and a “simple” column rename can make rollback impossible.

Try it in your own system
