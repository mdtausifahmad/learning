Reliability & SRE · Lesson 08

Instrumentation Lab: Prometheus + OpenTelemetry

◷ ~20 min hands-on • Level: Practical • Prereq: L07 golden signals · Docker installed

You’ve designed telemetry on paper (Lesson 07). Now make it real: stand up a local observability stack and watch a service’s golden signals and traces actually flow through it. This is the muscle memory that turns SRE concepts into instinct — and it’s the same shape of stack you’ll run in production.

1. The pipeline you’re building

2. Track A — see it working in 5 minutes

Fastest possible win: run the official OpenTelemetry Demo — a real microservices shop, fully instrumented, with Prometheus, Grafana (prebuilt dashboards), and Jaeger baked in. 

git clone https://github.com/open-telemetry/opentelemetry-demo.git
cd opentelemetry-demo
docker compose up -d          # first run pulls images — give it a few minutes

Then explore (the demo proxies everything through port 8080):

  • Web store — http://localhost:8080/ (a load generator is already driving traffic)
  • Grafana — http://localhost:8080/grafana/ → open a service dashboard and find the four golden signals
  • Jaeger — http://localhost:8080/jaeger/ui/ → pick a service, open a trace, watch it fan across services
Do this now

In Jaeger, open one checkout trace and find the slowest span. That’s the “where” from Lesson 06, on real data. Then in Grafana, find a latency panel and confirm it’s a percentile, not a mean (Lesson 07). docker compose down when done.

3. Track B — wire up your own service

The real skill. Use the minimal, transparent stack in this course’s lab folder (docker-compose.yml, collector config, prometheus.yml):

cd assets/lab
docker compose up -d
# Prometheus :9090   Grafana :3000   Jaeger :16686

Now add OpenTelemetry to a service you own — zero-code auto-instrumentation is the fast path. Pick your language:

# Python
pip install opentelemetry-distro opentelemetry-exporter-otlp
opentelemetry-bootstrap -a install
opentelemetry-instrument python app.py

# Node.js
npm i @opentelemetry/api @opentelemetry/auto-instrumentations-node
node --require @opentelemetry/auto-instrumentations-node/register app.js

# Java
java -javaagent:opentelemetry-javaagent.jar -jar app.jar

Point every one of them at the local Collector with two environment variables:

export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318
export OTEL_SERVICE_NAME=my-service

Generate some traffic, then open Prometheus (:9090) and query your golden signals (metric names vary by library — start typing http_ to discover them):

# Traffic — requests/sec
sum(rate(http_server_request_duration_seconds_count[5m]))

# Errors — 5xx ratio
sum(rate(http_server_request_duration_seconds_count{http_response_status_code=~"5.."}[5m]))
  / sum(rate(http_server_request_duration_seconds_count[5m]))

# Latency — p95
histogram_quantile(0.95,
  sum by (le) (rate(http_server_request_duration_seconds_bucket[5m])))
The full loop, closed

Those three queries are Lessons 02 and 07 on live data. Drop the availability and latency ratios into recording rules, add the burn-rate alert, and you’ve built the entire SLO stack — measure → target → budget → policy → alert — end to end, on your own service.

4. What the config actually says

The Collector config is three moving parts — a pipeline:

  • receivers — otlp on :4317 (gRPC) and :4318 (HTTP): where your app’s telemetry arrives.
  • processors — batch: buffers before export (efficiency).
  • exporters — prometheus (re-exposes metrics on :8889 for Prometheus to scrape) and otlp/jaeger (ships traces to Jaeger).

Prometheus then scrapes the Collector; Grafana queries Prometheus. That’s the whole dance.

Gotchas

Ports: SDKs default to OTLP gRPC (:4317); set OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf if you use :4318. Names: metric names differ by language/library — explore in Prometheus. Cardinality: auto-instrumentation can attach high-cardinality attributes (full URLs with IDs) — template or drop them (Lesson 07). Pin image versions for anything beyond a lab.
