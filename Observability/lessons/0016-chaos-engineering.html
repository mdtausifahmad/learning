Chaos Engineering: Verify, Don’t Hope

◷ ~11 min read • Level: Judgment (extension) • Prereq: L11–12 resilience · L6–8 observability

You built resilience patterns (Lessons 11–12) and an incident process (Lesson 9). But how do you know they work? “The code path you never exercise doesn’t work.” Chaos engineering verifies reliability empirically — deliberately injecting failure to find weaknesses before they find you at 3 a.m. It’s the experimental test of everything you’ve designed.

1. Why hope isn’t a strategy

Even when every individual service works, the interactions between them produce outcomes nobody predicted — and rare real-world events make distributed systems inherently chaotic. Staging won’t reveal it. You find these weaknesses one of two ways: by experiment, or by outage.

The weaknesses it hunts are the ones you’ve studied

The Principles of Chaos name them directly: retry storms from badly tuned timeouts (Lesson 11), cascading failure from a single point of failure (Lesson 11), outages when a downstream is overwhelmed (Lesson 12), broken fallbacks. Chaos surfaces these “unknown unknowns” (Lesson 6) on purpose, on your schedule.

2. What it is

The canonical definition: “Chaos Engineering is the discipline of experimenting on a system in order to build confidence in the system’s capability to withstand turbulent conditions in production.” It is a controlled experiment — not sabotage, not “break things randomly.”

3. The experiment: four steps

  1. Define steady state — a measurable, user-facing output that means “normal”. That’s your SLIs / golden signals (throughput, error rate, latency percentiles) — not CPU.
  2. Hypothesise steady state holds in both the control group and the experimental group — i.e. the system tolerates the failure.
  3. Inject real-world events — a server crashes, a disk fails, a network is severed, a dependency slows, a resource exhausts.
  4. Try to disprove it — did steady state diverge between control and experimental? If yes, you found a weakness before your users did.

4. Doing it well (advanced principles)

  • Hypothesise on the output, not internals — chaos verifies that the system works, not how it works.
  • Vary real-world events, prioritised by impact × frequency — hardware death, malformed responses, traffic spikes, scaling events.
  • Run in production (eventually) — only real traffic exercises the real request path. Start in staging to build confidence.
  • Automate so experiments run continuously — manual chaos is unsustainable (Netflix’s Chaos Monkey randomly kills prod instances).
  • Minimise the blast radius — the smallest experiment that teaches you something, contained, with an abort switch. Same discipline as a canary (Lesson 13).

5. Start with a GameDay

In practice, begin manual: a scheduled, low-blast-radius exercise where the team states a hypothesis, injects one failure (kill an instance; add 300 ms to a dependency), and watches the SLIs. A GameDay doubles as incident-response practice (Lesson 9) and produces a postmortem-style writeup (Lesson 10). Tools when you’re ready to automate: Chaos Monkey, Gremlin, AWS Fault Injection Service, or chaos-mesh / LitmusChaos on Kubernetes.

Prerequisites — don’t skip these

Chaos on an un-observed, un-resilient system is just a self-inflicted outage. You need observability (Lessons 6–8) to see the impact, SLOs to define steady state, and mitigation / rollback (Lessons 9, 13) to stop it. Chaos is the verification layer on top of everything you’ve built — and always tell on-call first.

Try it in your own system

Design a GameDay for one service:

  • Define steady state with 1–2 SLIs.
  • Pick one realistic failure (kill an instance / add 300 ms to a dependency / block a downstream).
  • Write the hypothesis (“the system tolerates it because…”) — name which resilience pattern (L11–12) should save you.
  • Set a small blast radius and an abort condition. Run it in staging first.

Bring the results — especially anything that surprised you. That surprise is the whole point.
