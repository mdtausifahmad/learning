Event Design Checklist

Compressed from Lesson 02•Print-friendly
Mindset

Events are your permanent public contract with the future. You can change code tomorrow; you can’t change what you wrote down yesterday.

Review checklist

  • Past tense, business language — a domain expert recognises the name (InvoiceIssued, not InvoiceUpdated).
  • Intent, not diff — could a consumer react to one reason but not another? Then they’re separate types.
  • Applicable without lookups — evolve needs no DB, clock, random or config.
  • Historical inputs captured — rates, prices, policy versions whose derivation can change.
  • No derived state whose derivation is stable (running balance) — fold it instead.
  • No CRUD events — no XUpdated{allFields}, no StatusChanged{from,to}.
  • One event per business fact; multiple facts from one command → one atomic append.
  • Payload vs metadata — business data in data; ids, trace, tenant, user in metadata.
  • Minimal PII — reference by id; encrypt or isolate personal data (Lesson 13).
  • Schema version set in the envelope from day one.

Envelope

public record EventEnvelope(
        UUID eventId, String streamId, long streamVersion, long globalPosition,
        String eventType, int schemaVersion, Instant occurredAt,
        Object data,                         // the business fact
        Map<String, String> metadata) {}     // correlationId, causationId, userId, tenantId, traceparent

Correlation & causation rule

When handling message M, every emitted message gets…Answers
correlationId = M.correlationId“Which business flow?” — group the whole story
causationId = M.messageId“What directly caused this?” — rebuild the causal tree
