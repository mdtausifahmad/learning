No dual writes

append (1 atomic write) → publisher subscription reads $all from checkpoint
  → produce(key = aggregateId) → ack → save checkpoint
crash after ack, before checkpoint ⇒ duplicates (OK) — never loss
at-least-once + consumer dedupe on eventId = effectively-once

Kafka as event store?

Great log for distribution, poor store for aggregates: no per-key conditional append, no cheap per-stream read, compaction keeps latest value not history. Works only by building your own (Kafka Streams + single writer per partition). Default: store → Kafka.

Coordinating across aggregates

ChoreographyProcess manager
event → command reactions; 2–3 steps; flow implicitStateful, event-sourced coordinator; branching, timeouts, “where is it stuck?”
  • Compensate, don’t roll back: ReleaseStock, RefundPayment.
  • Timeouts are events from a durable scheduler (PaymentTimeoutElapsed).
  • Idempotent steps: deterministic commandId; PM re-sends after crashes.
  • Enumerate late arrivals in terminal states (paid after cancel → refund).
  • PM tracks progress; aggregates own rules.

Set validation (uniqueness)

  1. Reservation stream (NoStream) or unique table in the same tx — strict.
  2. Read-model check + compensate rare races — ask how bad a duplicate really is.
  3. Single aggregate if the set is small (seats on one flight).
  4. DCB: query by tags/types, append with “fail if matching events after P”. Newer — spike before betting on it.
