Decide first

History a business requirement (or many evolving read models)? → behaviour-rich? → team & product accept eventual consistency + learning curve? All yes ⇒ event-source this bounded context. Otherwise: CRUD (+ outbox/CDC) or CRUD + audit/temporal tables.

ADR skeleton

# ADR-NNN: Use event sourcing for the <X> bounded context
## Status        Proposed — YYYY-MM-DD
## Context       business drivers + evidence (regulation, incidents, analytics asks); team reality
## Decision      scope (this context only); event store; ordering/concurrency; projections
                 (which inline); integration events & format; PII approach
## Consequences  + audit, temporal queries, backfillable views
                 − learning curve (plan), eventual consistency (SLO), upcasters + CI corpus
## Alternatives  CRUD + outbox + audit table; framework (Axon); dedicated store (KurrentDB) — why not
## Exit plan     projections materialise current state into CRUD tables; est. effort
## Success       projection lag p99, rehydration p99, parked events = 0,
## metrics       time-to-new-read-model, audit answered without engineers; review date

Migration from CRUD (strangler)

1 one context → 2 seed honest AccountImported → 3 route writes (single writer; shadow mode first) → 4 project back into legacy tables → 5 move readers one by one → 6 decommission. CDC change events ≠ domain events.

Organisational levers

  • Scope via ADR; buy-in from product (staleness) and compliance (GDPR).
  • Paved road: store client, decider types, projection runner, upcaster registry, test DSL.
  • Champions: Event Storming, pairing, “how we do ES here” guide.
  • Ownership: runbooks + on-call for projections and subscriptions.
  • Honest metrics: unused history after 6 months ⇒ propose simplifying.
  • Business language: “1–2 s staleness for regulator-grade history.”
