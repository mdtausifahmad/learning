Schema Evolution Decision Tree

Compressed from Lesson 12•Print-friendly

What changed? → strategy (cheapest first)

ChangeStrategyNotes
Added optional fieldTolerant readerDefault the missing field; no version bump. Never remove or repurpose fields.
Renamed / restructured, same meaningUpcasterRaw v1 → v2 on read; pure, one step per version; same chain everywhere.
Meaning genuinely differentNew event typeKeep handling the old type in evolve forever (or upcast if historically true).
History structurally wrong / aggregate splitCopy-and-transformLast resort; ADR, dry-run, archive the original read-only.
Business mistakeCompensating eventNot a schema problem. Never UPDATE events.

mapper.configure(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES, false);

    MoneyDeposited { if (channel == null) channel = "UNKNOWN"; }

Upcaster

interface Upcaster { boolean canUpcast(String type, int v); RawEvent upcast(RawEvent raw); }

Formats & registry modes

ModeGuaranteeAllowed (Avro)Upgrade first
BACKWARDnew reads olddelete fields; add with defaultconsumers
FORWARDold reads newadd fields; delete with defaultproducers
FULLbothadd/delete with default onlyany
*_TRANSITIVEagainst all versionsas above—

Common mix: JSON in the store, Avro/Protobuf on Kafka. The store replays every version ever written — think transitively. Protobuf: never reuse field numbers.

CI safety net

Keep a corpus of real historical samples (type × version, PII-scrubbed). On every build: upcast + deserialise each; replay a golden stream to an expected state; fail if any registered type/version has no sample. Catches record-component renames before prod.
