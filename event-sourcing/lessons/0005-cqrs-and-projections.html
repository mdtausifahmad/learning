Event Sourcing · Lesson 05

CQRS & Projections

◷ ~15 min read • Level 2 · The read side • Prereq: Lesson 04

Lessons 01–04 built a write side that is superb at one question: “give me everything about account-A1”. Your product manager will ask a different one on day two: “show me all accounts over €10k opened in Berlin last month”. The event store can’t answer that — projections can. Getting projections right (idempotent, checkpointed, rebuildable) is the difference between a read side you trust and one you “fix with a SQL script” every other week.

1. Why you need a read side

The write model is a set of streams keyed by aggregate id. It is optimised for readStream(id) and append(id, expectedVersion, events) — nothing else. Ask it “all orders over €500 placed in Berlin last week” and you’d have to replay every order stream, fold each one, then filter in memory. That’s a full table scan with extra steps.

QuestionWrite side (event streams)Read side (projection)
“State of order-123 right now”✓ rehydrate one stream✓ one row lookup
“Orders > €500 in Berlin last week”✗ replay everything✓ indexed table / search index
“Revenue per day this quarter”✗ replay everything✓ pre-aggregated table / OLAP store
“Full-text search over customer notes”✗ impossible in practice✓ OpenSearch / Elasticsearch index

CQRS (Command Query Responsibility Segregation) means using different models for writing and reading. It’s a separate pattern from event sourcing — you can do CQRS on a CRUD database — but with ES it is nearly mandatory, because the write model can’t serve arbitrary queries. The key consequence you must design for: reads are eventually consistent with writes, typically by milliseconds to seconds (Lesson 06 is all about living with that).

Mental model

A projection is just another fold — events.foldLeft(initial, evolve) — but over the global log instead of one stream, and into a database instead of memory. If you can write evolve, you can write a projection.

2. Writing a projection in Java

The read model and the checkpoint table (same Postgres database as the read model):

CREATE TABLE rm_account_balance (
    account_id     TEXT PRIMARY KEY,
    owner_id       TEXT    NOT NULL,
    balance        NUMERIC(19,2) NOT NULL,
    status         TEXT    NOT NULL DEFAULT 'OPEN',
    last_position  BIGINT  NOT NULL          -- idempotency guard, per row
);

CREATE TABLE projection_checkpoints (
    name      TEXT PRIMARY KEY,                -- e.g. 'account-balance-v1'
    position  BIGINT NOT NULL,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

The projection itself. Note the sealed-interface switch, the per-row guard and the checkpoint written inside the same @Transactional boundary:

public final class AccountBalanceProjection implements Projection {

    private final JdbcTemplate jdbc;

    public AccountBalanceProjection(JdbcTemplate jdbc) { this.jdbc = jdbc; }

    @Override public String name() { return "account-balance-v1"; }   // versioned name!

    @Override
    @Transactional   // read-model update + checkpoint in ONE transaction
    public void handle(EventEnvelope env) {
        long pos = env.globalPosition();
        switch (env.event()) {
            case AccountEvent.AccountOpened e -> jdbc.update("""
                INSERT INTO rm_account_balance (account_id, owner_id, balance, last_position)
                VALUES (?, ?, 0, ?)
                ON CONFLICT (account_id) DO NOTHING
                """, e.accountId(), e.ownerId(), pos);

            case AccountEvent.MoneyDeposited e -> jdbc.update("""
                UPDATE rm_account_balance
                   SET balance = balance + ?, last_position = ?
                 WHERE account_id = ? AND last_position < ?     -- idempotency guard
                """, e.amount(), pos, e.accountId(), pos);

            case AccountEvent.MoneyWithdrawn e -> jdbc.update("""
                UPDATE rm_account_balance
                   SET balance = balance - ?, last_position = ?
                 WHERE account_id = ? AND last_position < ?
                """, e.amount(), pos, e.accountId(), pos);

            case AccountEvent.AccountClosed e -> jdbc.update("""
                UPDATE rm_account_balance
                   SET status = 'CLOSED', last_position = ?
                 WHERE account_id = ? AND last_position < ?
                """, pos, e.accountId(), pos);

            default -> { /* ignore events this projection doesn't care about */ }
        }
        jdbc.update("""
            INSERT INTO projection_checkpoints (name, position) VALUES (?, ?)
            ON CONFLICT (name) DO UPDATE SET position = EXCLUDED.position, updated_at = now()
            """, name(), pos);
    }
}

And the runner that drives it — a polling catch-up loop (Lesson 08 covers subscriptions and the ordering trap hiding in readAll):

public void runOnce(Projection p) {
    long from = checkpoints.get(p.name()).orElse(0L);
    List<EventEnvelope> batch = store.readAll(from, 500);    // global_position > from
    for (EventEnvelope env : batch) {
        try {
            p.handle(env);                                       // own tx per event
        } catch (Exception ex) {
            retryOrPark(p, env, ex);                             // never silently skip
            return;
        }
    }
}
Two small details that bite

(1) The default branch still advances the checkpoint. A projection that only cares about 2% of events must still move past the other 98%, or it re-reads them forever. (2) One-transaction-per-event is correct but slow during catch-up. A common optimisation is to apply a batch of events and write the checkpoint once at the end of the batch — still one transaction, so the atomicity argument holds.

3. The three properties every projection must have

PropertyWhyHow
IdempotentDelivery is at-least-once. After a crash or redeploy you will see an event twice.Store last processed position per row (guard WHERE last_position < :pos) or per projection; UPSERT; dedupe on event_id.
CheckpointedResume from where you stopped, not from zero.Save globalPosition — ideally in the same transaction as the read-model write ⇒ exactly-once effect.
RebuildableBugs happen; requirements change.Must be able to start from position 0 into a fresh table. Never write to a read model from anywhere else.

Why do you need both the same-transaction checkpoint and the per-row guard? Because the read model is not always in the same database as the checkpoint. Writing to OpenSearch, Redis or a different Postgres cluster means you can’t share a transaction; then the idempotency guard is your only defence (store the position on the document and use a conditional/versioned write). Defence in depth is cheap here. Try it:

Do this sequence twice: with both safeguards off, click Process next twice, then crash before checkpoint, then Restart — the balance double-counts. Now enable only the guard, reset, and repeat: the redelivered event hits WHERE last_position < :pos and updates 0 rows. Then try only same-tx: the crash rolls back the whole unit of work, so the redelivery is the first application.

“Exactly-once” is about effects, not delivery

No subscription mechanism gives you exactly-once delivery across a crash. What you can build is exactly-once effect: at-least-once delivery + an idempotent, atomic apply. Say it this way in a design review — it signals you know where the guarantee actually comes from.

4. The projection lifecycle

A projection is a long-running process with a small, explicit state machine. Making these states observable (a status column next to the checkpoint, a gauge per state) is what lets on-call reason about it at 3 a.m.

StateWhat’s happeningWhat to watch
CatchingUpReading history from checkpoint (or 0) as fast as possible, in big batchesevents/sec, ETA to head
LiveAt head; handles each new event + checkpointlag in positions and seconds
FailedHandler threw; retrying with backoff. Does not skip.retry count, time in state
ParkedA poison event (bug, bad data) exhausted retries; projection halted & alertedparked count — should be 0
RebuildingA v2 replays from 0 into a fresh table beside v1progress %, rebuild duration
Never “log and continue”

Skipping a failing event silently corrupts the read model forever — and nobody knows which rows are wrong. For a per-entity projection you may choose to park just that entity and keep the rest flowing; for an aggregating projection (totals) you must stop. Either way, it’s a visible, alerting state, not a catch (Exception e) { log.warn(...) }.

The cross-stream join, done right

The tempting mistake is to call the Customer service (or query the customer table) from inside the Order projection. That makes the projection’s output depend on when you ran it — a rebuild produces different rows than the original run, so it isn’t deterministic and isn’t truly rebuildable. Instead, the projection consumes both streams’ events and keeps its own lookup: 

switch (env.event()) {
    case CustomerEvent.CustomerRegistered e -> lookup.upsert(e.customerId(), e.name(), pos);
    case CustomerEvent.CustomerRenamed e    -> {
        lookup.upsert(e.customerId(), e.newName(), pos);
        jdbc.update("UPDATE rm_orders SET customer_name = ? WHERE customer_id = ?",
                    e.newName(), e.customerId());                // fan-out the rename
    }
    case OrderEvent.OrderPlaced e -> jdbc.update("""
        INSERT INTO rm_orders (order_id, customer_id, customer_name, total, last_position)
        VALUES (?, ?, ?, ?, ?) ON CONFLICT (order_id) DO NOTHING
        """, e.orderId(), e.customerId(), lookup.name(e.customerId()), e.total(), pos);
    default -> { }
}

Because both event types arrive in global order, the lookup is always exactly as up to date as the order it’s joining — on the first run and on every rebuild.

Aggregating projections: store inputs, not just totals

revenue = revenue + amount is fine until a refund arrives for a day you’ve already “closed”, or a currency conversion rule changes. Keeping the per-event inputs (e.g. one row per order line with its day) and computing totals with a query or materialised view makes the projection idempotent by construction and cheaper to fix.
