Event Sourcing · Lesson 01

State vs History: the Mental Model

◷ ~12 min read • Level 0 · Foundations • Prereq: none

Almost every system you have built stores the current state and overwrites it on every change. Event sourcing flips that: you store the facts that happened, and treat every state as something you derive. Before any code, you need that inversion to feel natural — it answers most of the design questions you’ll meet later.

1. Two ways to remember a bank account

State-oriented (CRUD): one row, balance = 70. Every UPDATE destroys the previous value. Event-sourced: an append-only list of facts — AccountOpened, MoneyDeposited 100, MoneyWithdrawn 50, MoneyDeposited 20. Both say the balance is 70. Only one can tell you why, when, and what it was last Tuesday.

2. Play with it: replay & time travel

Notice three things while you play. (1) The slider never changes the events — it just folds fewer of them. (2) A rejected withdrawal appends nothing: commands can fail, events cannot. (3) The CRUD row can only ever answer questions about now.

3. The one equation

state     = events.foldLeft(initialState, evolve)   // evolve(state, event) → state   (pure)
newEvents = decide(command, state)                   // business rules; may reject

That’s the whole pattern. Everything else in this course — snapshots, projections, versioning, sagas — is engineering around these two functions. They answer two different questions:

LineQuestion it answersDirection
state = fold(…evolve)“Where are we now?”past events → current state (read)
newEvents = decide(…)“What should happen next?”request + current state → new events (write)

The three ingredients

  • initialState is the state before any event. It is not the first event. For an account it is “doesn’t exist yet, balance 0”. It’s the starting value, like sum = 0 before a loop.
  • evolve(state, event) → state answers: “given the state so far and one more fact, what is the state now?” It only applies facts. It never checks rules, because the event already happened and can’t be refused. It is pure: no DB, no clock, no I/O.
  • decide(command, state) → events holds the business rules. A command is a request (“withdraw 80”). decide checks it against the current state. If the rules pass, it returns the events to record. If they fail, it rejects the command: it throws or returns an error, and nothing is stored.

Worked example: account acc-42

The stored stream is [AccountOpened, MoneyDeposited(100), MoneyWithdrawn(30)]. foldLeft walks it left to right and carries the state along:

StepState beforeEventevolve returns
startinitialState = { open: false, balance: 0 }
1{ open: false, balance: 0 }AccountOpened{ open: true, balance: 0 }
2{ open: true, balance: 0 }MoneyDeposited(100){ open: true, balance: 100 }
3{ open: true, balance: 100 }MoneyWithdrawn(30){ open: true, balance: 70 }

Now two commands arrive, and decide sees state { open: true, balance: 70 }:

  • Withdraw(50): 50 ≤ 70, so it is accepted and returns [MoneyWithdrawn(50)]. That event is appended, and the next fold gives balance 20.
  • Withdraw(500): 500 > 70, so it is rejected with “insufficient funds”. It returns no events and the stream is unchanged. That is what “business rules; may reject” means.
// Java 21: the same thing as code
record Account(boolean open, long balance) {
  static final Account INITIAL = new Account(false, 0);       // initialState
}

static Account evolve(Account s, Event e) {                     // apply a fact; no rules
  return switch (e) {
    case AccountOpened o   -> new Account(true, s.balance());
    case MoneyDeposited d  -> new Account(s.open(), s.balance() + d.amount());
    case MoneyWithdrawn w  -> new Account(s.open(), s.balance() - w.amount());
  };
}

static List<Event> decide(Command c, Account s) {             // rules live here
  return switch (c) {
    case Withdraw w when !s.open()               -> throw new DomainException("account closed");
    case Withdraw w when w.amount() > s.balance() -> throw new DomainException("insufficient funds");
    case Withdraw w                              -> List.of(new MoneyWithdrawn(w.amount()));
    // … Open, Deposit
  };
}

// The full loop for one request:
Account state = events.stream().reduce(Account.INITIAL, Domain::evolve, (a, b) -> b); // 1. rebuild
List<Event> newEvents = decide(new Withdraw(50), state);                             // 2. decide
store.append("acc-42", expectedVersion, newEvents);                                   // 3. record
Why split them?

decide runs once, when the request arrives, and may say no. evolve runs every time state is rebuilt, possibly years later, and must always say yes. If you put a rule like “balance can’t go negative” in evolve, then changing that rule next year would make old history fail to load. Rules go in decide. evolve only records facts.

The accountant’s rule

Accountants have done event sourcing for 500 years: you never use an eraser on a ledger. A mistake is fixed with a new, compensating entry. Keep this image — “how do I fix bad data?”, “how do I undo?”, “can I edit an event?” all have the accountant’s answer.

The #1 failure mode

Applying event sourcing to a whole system. It is a per-bounded-context decision. Successful adopters event-source the 1–3 domains where history has business value (ledger, order lifecycle, claims) and use plain CRUD everywhere else.

6. What event sourcing is not

MisconceptionReality
“ES = using Kafka”Kafka distributes events well but lacks per-entity streams with optimistic concurrency. (Lesson 09.)
“ES = event-driven architecture”EDA is how services talk. ES is how one service stores its own state. Either works without the other.
“ES requires CQRS”ES practically needs read models, but CQRS is a separate pattern usable without ES.
“CDC rows are events”status 2→3 is a data diff. A domain event carries business meaning.
