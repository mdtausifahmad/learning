Event Sourcing · Lesson 12

Event Schema Evolution & Upcasting

◷ ~16 min read • Level 4 · Advanced • Prereq: Lesson 11 · Choosing & operating a store

Events are immutable and live forever. Your understanding of the domain does not stand still. Every event-sourced system eventually has to reconcile those two facts — and the first innocent “rename this record field” refactor is what bricks replay in production. This lesson gives you the full versioning toolkit, in order of preference, a decision tree you can apply in a design review, and the CI safety net that makes evolution boring. Greg Young’s Versioning in an Event Sourced System is the canonical reference; we follow its strategies.

1. The decision tree

Don’t start with “which tool?”. Start with “what actually changed?” The answer picks the cheapest strategy that is still honest about history.

2. Strategy 1 — Weak schema / tolerant reader

Store events as JSON, deserialise leniently, make new fields optional with defaults, and never remove or repurpose a field. This handles the bulk of real-world changes with zero ceremony. 

// Forward compatibility: old code can read events written by newer code (unknown fields ignored).
// (Spring Boot’s auto-configured ObjectMapper already disables this; plain Jackson does not.)
mapper.configure(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES, false);

// Backward compatibility: new code reads old events that lack the field.
record MoneyDeposited(String accountId, BigDecimal amount, Instant at, String channel) {
    MoneyDeposited {
        if (channel == null) channel = "UNKNOWN";          // default for pre-channel events
    }
}

// Decouple the wire name from the Java name, so a refactor can’t silently rename the JSON key.
record MoneyWithdrawn(@JsonProperty("accountId") String account,
                      @JsonProperty("amount")    BigDecimal amount,
                      @JsonProperty("at")        Instant at) {}
Safe (tolerant reader)Unsafe (needs another strategy)
Add an optional field with a sensible defaultRename a field (IDE refactor of a record component!)
Add a new enum value if readers handle unknown valuesChange a field’s type or unit (cents → euros)
Stop writing an optional field (readers default it)Reuse an old field name for a new meaning
Add a new event type that old readers ignoreMake an optional field required
Primitives hide missing data

A missing JSON field mapped to an int or boolean silently becomes 0/false — indistinguishable from a real zero. Use boxed types or explicit defaults in the compact constructor so “absent” is a decision, not an accident.

3. Strategy 2 — Upcasting

When the shape changes, transform old raw events into the current shape when reading, before deserialising into domain types. The stored rows never change; the domain only ever sees the latest version. Upcasters are small, pure, chainable functions on raw JSON. 

public record RawEvent(UUID eventId, String eventType, int schemaVersion, ObjectNode data, ObjectNode metadata) {
    RawEvent withData(ObjectNode d)       { return new RawEvent(eventId, eventType, schemaVersion, d, metadata); }
    RawEvent withSchemaVersion(int v)     { return new RawEvent(eventId, eventType, v, data, metadata); }
}

public interface Upcaster {
    boolean canUpcast(String eventType, int schemaVersion);
    RawEvent upcast(RawEvent raw);                 // returns the NEXT version (chainable)
}

/** V1: "amount": 50.00 (implicit EUR). V2: "amount": {"value": "50.00", "currency": "EUR"} */
public final class MoneyDepositedV1toV2 implements Upcaster {
    public boolean canUpcast(String type, int v) { return type.equals("MoneyDeposited") && v == 1; }
    public RawEvent upcast(RawEvent raw) {
        ObjectNode data = raw.data().deepCopy();
        var amount = data.remove("amount");
        data.putObject("amount").put("value", amount.asText()).put("currency", "EUR");
        return raw.withData(data).withSchemaVersion(2);
    }
}

/** V3 adds "channel"; historical events are explicitly marked UNKNOWN. */
public final class MoneyDepositedV2toV3 implements Upcaster {
    public boolean canUpcast(String type, int v) { return type.equals("MoneyDeposited") && v == 2; }
    public RawEvent upcast(RawEvent raw) {
        ObjectNode data = raw.data().deepCopy();
        data.put("channel", "UNKNOWN");
        return raw.withData(data).withSchemaVersion(3);
    }
}

public final class UpcasterChain {
    private final List<Upcaster> upcasters;
    public UpcasterChain(List<Upcaster> upcasters) { this.upcasters = List.copyOf(upcasters); }

    public RawEvent toLatest(RawEvent raw) {
        var current = raw;
        for (int guard = 0; guard < 64; guard++) {
            var e = current;
            var next = upcasters.stream().filter(u -> u.canUpcast(e.eventType(), e.schemaVersion())).findFirst();
            if (next.isEmpty()) return current;
            current = next.get().upcast(current);
        }
        throw new IllegalStateException("Upcaster cycle for " + raw.eventType());
    }
}

Upcaster rules of thumb

Pure and deterministic — no database lookups, no now(); a replay next year must produce the same bytes. One step per version (v1→v2, v2→v3), never “v1→latest”, so each upcaster is written once and never touched again. Same chain everywhere: aggregate loading, projections, rebuilds, and the integration publisher. Axon and Marten ship this mechanism built in; on DIY Postgres it lives in readStream/readAll.

Upcasting has a cost: every read pays the transform, and a long chain of old versions accumulates. When a version is truly dead (and your corpus test proves equivalence), a governed copy-and-transform can collapse it — but that’s a deliberate migration, not housekeeping.

4. Strategy 3 — New event type

If the meaning changed, no amount of field mapping is honest. OrderCancelled used to mean “customer cancelled”; now merchants can cancel too, with refunds and penalties that differ. That’s two new facts. 

sealed interface OrderEvent permits OrderPlaced, OrderCancelled,
        OrderCancelledByCustomer, OrderCancelledByMerchant /* … */ {}

@Deprecated // no longer written; handled forever because history contains it
record OrderCancelled(String orderId, Instant at) implements OrderEvent {}
record OrderCancelledByCustomer(String orderId, String reason, Instant at) implements OrderEvent {}
record OrderCancelledByMerchant(String orderId, String reason, Money penalty, Instant at) implements OrderEvent {}

static OrderState evolve(OrderState s, OrderEvent e) {
    return switch (e) {
        case OrderCancelled c           -> s.cancelled(c.at());            // legacy meaning, kept
        case OrderCancelledByCustomer c -> s.cancelled(c.at());
        case OrderCancelledByMerchant c -> s.cancelled(c.at()).withPenalty(c.penalty());
        // … other cases
    };
}

Alternatively, upcast OrderCancelled into OrderCancelledByCustomer — only if that is historically true. If you don’t actually know who cancelled old orders, don’t invent it: keep the legacy type, or upcast to reason = "UNKNOWN".

5. Strategy 4 — Copy-and-transform; and compensating events

Copy-and-transform (stream migration)Compensating event
ProblemHistory’s structure no longer fits (splitting an aggregate, merging streams, dead versions)A business fact was wrong (wrong amount, wrong customer)
MechanismRead all events, transform, write into a new store/streams, switch overAppend DepositCorrected / ChargeReversed
HistoryRewritten copy; original must be archived read-only for auditorsUntouched; the correction is itself auditable
RiskHigh — big-bang cut-over, projections rebuilt, consumers re-pointedLow — normal command path
GovernanceADR, dry-run on a prod copy, checksum of before/after state per streamNormal feature work
Never edit events in place

UPDATE events SET data = … to “fix” data destroys the audit trail, silently desynchronises every projection and downstream consumer, and breaks the promise that made event sourcing worth paying for. If copy-and-transform feels necessary, run it as a governed migration with the original archived — never as a hotfix.

6. Serialisation format & schema registries

FormatProsCons
JSON (JSONB)Human-readable; queryable in Postgres; weak-schema friendlyBigger; no enforced schema
Avro / Protobuf + Schema RegistryCompact; compatibility checked in CI and at registrationHarder to inspect and debug; the registry is a runtime dependency

The common mix: JSON in the event store (debuggability, flexibility, upcasters on raw JSON) and Avro or Protobuf for public integration events on Kafka (contract enforcement across teams — Lesson 09). Know the registry compatibility modes cold:

ModeGuaranteeAllowed changes (Avro)Upgrade order
BACKWARD (common default)New schema can read data written with the previous oneDelete fields; add fields with defaultsConsumers first
FORWARDPrevious schema can read data written with the new oneAdd fields; delete fields that had defaultsProducers first
FULLBoth directionsAdd/delete only fields with defaultsAny order
*_TRANSITIVESame, checked against all previous versions, not just the lastAs above—
NONENo checksAnything (don’t, for public contracts)—
 
{ "type": "record", "name": "OrderSubmittedV1", "namespace": "com.acme.orders.public",
  "fields": [
    { "name": "orderId",     "type": "string" },
    { "name": "totalAmount", "type": "string" },
    { "name": "currency",    "type": "string" },
    { "name": "channel",     "type": ["null", "string"], "default": null }
  ] }

The channel field was added later; because it declares a default, the change passes a BACKWARD check — new readers fill null when reading older records.

Why event stores want *_TRANSITIVE thinking

A Kafka consumer usually reads recent data, so “compatible with the previous version” is often enough. An event store replays every version ever written. Your internal compatibility bar is effectively transitive: today’s code must read 2019’s events. For Protobuf, the equivalent discipline is: never reuse a field number; reserved removed ones.

7. The Staff safety net: a historical-event corpus in CI

Unit tests construct events with today’s classes, so they can’t catch a change that breaks yesterday’s bytes. Keep a corpus of real historical samples — one per event type × schema version, scrubbed of PII — and replay it on every build. 

src/test/resources/event-corpus/
  MoneyDeposited/v1.json   MoneyDeposited/v2.json   MoneyDeposited/v3.json
  OrderCancelled/v1.json   OrderCancelledByCustomer/v1.json
  streams/account-golden.jsonl   +  account-golden.expected.json
class HistoricalEventCorpusTest {

    static Stream<Path> samples() throws IOException {
        return Files.walk(Path.of("src/test/resources/event-corpus"))
                    .filter(p -> p.toString().endsWith(".json") && !p.toString().contains("streams"));
    }

    @ParameterizedTest @MethodSource("samples")
    void every_historical_event_upcasts_and_deserialises(Path sample) throws IOException {
        RawEvent raw    = Corpus.read(sample);                       // {type, schemaVersion, data}
        RawEvent latest = chain.toLatest(raw);
        assertThatNoException().isThrownBy(() -> serializer.deserialize(latest));
    }

    @Test
    void golden_stream_replays_to_the_same_state() throws IOException {
        var events = Corpus.readStream("streams/account-golden.jsonl").stream()
                           .map(chain::toLatest).map(serializer::deserialize).toList();
        var state  = events.stream().reduce(Account.initial(), Account::evolve, (a, b) -> b);
        assertThat(json(state)).isEqualTo(Corpus.text("streams/account-golden.expected.json"));
    }

    @Test
    void every_registered_event_type_has_a_sample() {
        assertThat(Corpus.typesCovered()).containsAll(EventTypeRegistry.allTypesAndVersions());
    }
}

The third test is the one people forget: it forces whoever introduces a new event type or version to commit a sample, so the corpus grows with the system. This catches “harmless” refactors — renaming a record component, changing BigDecimal to long, tightening a null check — before they brick replay in production.

Try it in your own system
  • Take three changes from your last quarter’s Kafka/DB migrations and run each through the decision tree. Which branch would each land on?
  • Export one real sample per event type × version from a running system (scrub PII) into src/test/resources/event-corpus.
  • Check your registry: are public topics BACKWARD or FULL? Is any subject on NONE?
  • Write the UpcasterChain and wire it into readStream before you need it — the first upcaster is easier with the hook already in place.
