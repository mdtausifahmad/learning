Event Sourcing · Lesson 15

Migrating from CRUD & Event Storming

◷ ~14 min read • Level 4 · Advanced • Prereq: Lesson 14 · Testing event-sourced systems

You will almost never get a greenfield event-sourced system. You’ll get a ten-year-old accounts table with forty readers, and a product team that can’t stop shipping while you rebuild the foundations. This lesson is the safe path: a strangler-fig migration, honest import events, shadow mode — and the workshop techniques (Event Storming, Event Modeling) you use to discover the right events with the business before writing a line of code.

2. Honest import events

You know the account’s balance today. You do not know the 3,000 deposits that produced it — and even if an old audit table hints at them, it’s probably incomplete. Don’t fabricate a fake history; name the event for what actually happened: we imported it.

public sealed interface AccountEvent permits
        AccountEvent.AccountImported, AccountEvent.AccountOpened,
        AccountEvent.MoneyDeposited, AccountEvent.MoneyWithdrawn, AccountEvent.AccountClosed {

    /** Honest migration event: "this is what the legacy system said on import". */
    record AccountImported(String accountId, String ownerId, String currency,
                           BigDecimal balance, String legacyStatus,
                           Instant legacyCreatedAt,      // as reported by legacy, not trusted as fact
                           String importBatchId, Instant at) implements AccountEvent {}
    // ...
}

// evolve: an imported account starts life with its migrated balance
case AccountImported e -> switch (e.legacyStatus()) {
    case "CLOSED" -> new AccountState.Closed(e.accountId());
    default       -> new AccountState.Open(e.accountId(), e.balance());
};
-- One-off seeding job: idempotent per account (expected version 0 = stream must not exist)

FROM   accounts
WHERE  id > :last_id
ORDER  BY id

Single writer, or you’ll corrupt both

Once writes go through aggregates, nothing else may write the legacy tables for that context — no batch job, no admin UI, no “quick SQL fix”. Hunt down every writer before step 3 (grep, pg_stat_statements, revoke UPDATE on the tables). A second writer means the legacy projection silently overwrites someone else’s change.

3. Project back into the legacy tables

/** The old schema becomes just another read model.
 *  Assumes a `version` column added to the legacy table and set to 1 by the seeding job. */
public final class LegacyAccountsProjection implements Projection<AccountEvent> {
    public void apply(EventEnvelope<AccountEvent> env, JdbcTemplate tx) {
        switch (env.event()) {
            case AccountImported e -> { /* rows already exist: nothing to write */ }
            case AccountOpened e   -> tx.update("""
                    INSERT INTO accounts(id, owner_id, currency, balance, status)
                    VALUES (?, ?, ?, 0, 'OPEN') ON CONFLICT (id) DO NOTHING""",
                    e.accountId(), e.ownerId(), e.currency());
            case MoneyDeposited e  -> tx.update(
                    "UPDATE accounts SET balance = balance + ?, version = ? WHERE id = ? AND version < ?",
                    e.amount(), env.streamVersion(), e.accountId(), env.streamVersion());
            case MoneyWithdrawn e  -> tx.update(
                    "UPDATE accounts SET balance = balance - ?, version = ? WHERE id = ? AND version < ?",
                    e.amount(), env.streamVersion(), e.accountId(), env.streamVersion());
            case AccountClosed e   -> tx.update(
                    "UPDATE accounts SET status = 'CLOSED', version = ? WHERE id = ? AND version < ?",
                    env.streamVersion(), e.accountId(), env.streamVersion());
        }
    }
}

The version < ? guard makes increments idempotent under redelivery — the same technique from Lesson 05, applied to a schema you didn’t design.

4. Shadow mode: prove it before you cut over

Before step 3 goes live, run both paths for every real command: the legacy CRUD code still owns the data; the event-sourced path runs alongside into a shadow store. A reconciler compares results continuously.

CompareHowA diff usually means
Accept/reject decisionlog both outcomes per request ida business rule the legacy code enforces implicitly (a trigger, a constraint)
Resulting statefolded shadow state vs legacy row, nightly + sampled liverounding, time-zones, an undocumented side path
Side effectsshadow path has reactors disabled— (never send emails twice)
Shadow mode is a discovery tool

Every diff is a rule nobody wrote down. Teams that skip shadow mode find those rules in production. Leave it running until the diff rate is zero across at least one full business cycle (month-end, year-end batch, renewal season).

5. CDC is not event sourcing

A tempting shortcut: point Debezium at the legacy database and call the change stream “our events”. It’s a genuinely useful integration step — but it isn’t event sourcing.

6. Discovering events: Event Storming

Alberto Brandolini’s Event Storming is a workshop: domain experts and engineers, a very long wall, and sticky notes. You start with chaotic exploration (everyone writes domain events, past tense, orange), then enforce a timeline, mark hotspots, find pivotal events that split the story into phases, and only then add commands, actors, policies, aggregates and read models. Boundaries between clusters become bounded-context candidates.

7. Designing slices: Event Modeling

Adam Dymitruk’s Event Modeling turns the storm into a blueprint: a single left-to-right timeline of screens (UI wireframes), commands, events and views. It has only four patterns — state change (UI → command → event), state view (events → view → UI), automation (view → processor → command) and translation (external events → our events). Each vertical slice is independently buildable and comes with its own Given/When/Then spec — exactly the tests from Lesson 14. 

Slice: "Place order"                      Slice: "Order status"
  Given  CartCheckedOut{cart: C1}            Given  OrderPlaced{O1}, StockReserved{O1}
  When   PlaceOrder{cart: C1}                Then   view OrderStatus{O1} = "Reserved"
  Then   OrderPlaced{order: O1, total: 80}

The Staff contribution

Staff engineers facilitate these workshops with product and domain experts. It’s often the highest-leverage thing you’ll do on an ES adoption: the code follows from a good model, and a bad model (OrderUpdated, StatusChanged) can’t be rescued by good code.
