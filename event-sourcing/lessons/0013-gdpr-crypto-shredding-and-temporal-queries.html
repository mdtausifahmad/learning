Event Sourcing · Lesson 13

GDPR, Crypto-Shredding & Temporal Queries

◷ ~15 min read • Level 4 · Advanced • Prereq: Lesson 12 · Event schema evolution

Your log is immutable; the law says a person can ask to be forgotten. Those two facts collide the first time a data-protection officer reads your design doc. This lesson gives you the four ways out, a production-shaped crypto-shredding sketch in Java, the end-to-end purge map a Staff engineer owns — and then turns time itself into a feature: as-of versus valid-time queries, retroactive events and bi-temporal modelling.

1. The collision: immutability vs erasure

GDPR Art. 17 (“right to erasure”) obliges you to delete a data subject’s personal data on request, without undue delay (Art. 12(3) gives you one month by default). Event sourcing promises the opposite: never update, never delete. If your events contain email, name, iban or a free-text note, you have a problem that grows with every append — and with every copy of those events downstream.

PII hides in places you don’t look

Payloads are the obvious place. Less obvious: stream ids (customer-alice@example.com), metadata (IP address, user agent), tags, Kafka message keys, log lines that print events, and error messages in your dead-letter table. Use opaque ids (customer-42) everywhere identity is structural.

2. The four options

TechniqueHowTrade-offs
Keep PII out of eventsEvents reference customerId; PII lives in a separate, deletable CRUD storeSimplest; best default. Replays still work; erasure is a plain DELETE. Costs a lookup when projecting.
Crypto-shreddingEncrypt PII fields with a per-subject key held in a key store/vault; delete the key to “forget”Events stay immutable; replay shows [erased]. Most popular approach when PII must travel with the fact. Adds key-management ops.
Stream deletion / truncationDelete or truncate the whole stream (e.g. customer-42)Supported by most stores; projections must handle tombstones; breaks global replay determinism for that subject.
Copy-transform excluding dataRewrite history into a new store/stream without the subject’s dataHeavy, risky, audited migration. Last resort.

In practice you combine them: keep most PII out, crypto-shred the few fields that genuinely belong to the fact (a payment memo, a claim’s free-text description), and keep stream deletion for subjects whose entire stream is personal (a user-preferences stream).

CustomerRegistered{id: 42, email: ENC(k42,…)}→ OrderPlaced{customerId: 42, total: 80}→ CustomerDataErased{id: 42}

3. Crypto-shredding, step by step

4. A Java sketch: field-level encryption with a key store

Keep the crypto behind a narrow interface so the decider never sees it, and so you can swap the backing store (Postgres table + KMS wrapping, HashiCorp Vault Transit, AWS KMS data keys).

// ---- The only mutable thing: per-subject keys ----
public interface SubjectKeyStore {
    SecretKey getOrCreate(String subjectId);          // write path
    Optional<SecretKey> find(String subjectId);       // read path; empty after erasure
    void destroy(String subjectId);                   // GDPR erasure = crypto-shred
}

// ---- What is stored inside the event payload ----
public record Encrypted(String subjectId, String iv, String ciphertext) {}

public final class PiiCipher {
    private static final int IV_BYTES = 12, TAG_BITS = 128;
    public static final String ERASED = "[erased]";

    private final SubjectKeyStore keys;
    private final SecureRandom random = new SecureRandom();

    public PiiCipher(SubjectKeyStore keys) { this.keys = keys; }

    public Encrypted encrypt(String subjectId, String plaintext) {
        try {
            byte[] iv = new byte[IV_BYTES];
            random.nextBytes(iv);                                   // fresh IV per field
            Cipher c = Cipher.getInstance("AES/GCM/NoPadding");
            c.init(Cipher.ENCRYPT_MODE, keys.getOrCreate(subjectId), new GCMParameterSpec(TAG_BITS, iv));
            c.updateAAD(subjectId.getBytes(UTF_8));                 // bind ciphertext to subject
            byte[] ct = c.doFinal(plaintext.getBytes(UTF_8));
            return new Encrypted(subjectId, b64(iv), b64(ct));
        } catch (GeneralSecurityException e) {
            throw new IllegalStateException("PII encryption failed", e);
        }
    }

    /** Never throws for a missing key: erasure is a normal, expected outcome. */
    public String decryptOrErased(Encrypted f) {
        return keys.find(f.subjectId()).map(k -> decrypt(k, f)).orElse(ERASED);
    }

    private static String decrypt(SecretKey key, Encrypted f) {
        try {
            Cipher c = Cipher.getInstance("AES/GCM/NoPadding");
            c.init(Cipher.DECRYPT_MODE, key, new GCMParameterSpec(TAG_BITS, unb64(f.iv())));
            c.updateAAD(f.subjectId().getBytes(UTF_8));
            return new String(c.doFinal(unb64(f.ciphertext())), UTF_8);
        } catch (GeneralSecurityException e) {
            throw new IllegalStateException("Corrupt ciphertext for " + f.subjectId(), e);
        }
    }
    private static String b64(byte[] b) { return Base64.getEncoder().encodeToString(b); }
    private static byte[] unb64(String s) { return Base64.getDecoder().decode(s); }
}

// ---- The event: PII is a value object, the rest is clear text ----
public sealed interface CustomerEvent {
    record CustomerRegistered(String customerId, Encrypted email, Instant at) implements CustomerEvent {}
    record CustomerDataErased(String customerId, Instant at) implements CustomerEvent {}   // no PII!
}

// ---- Projection side ----
case CustomerRegistered e -> jdbc.update(
        "INSERT INTO customer_view(id, email) VALUES (?, ?) ON CONFLICT (id) DO NOTHING",
        e.customerId(), cipher.decryptOrErased(e.email()));
case CustomerDataErased e -> jdbc.update(
        "UPDATE customer_view SET email = ?, name = ? WHERE id = ?", ERASED, ERASED, e.customerId());
-- Postgres-backed key store: data keys wrapped by a KMS master key (envelope encryption)
CREATE TABLE subject_keys (
    subject_id   TEXT PRIMARY KEY,
    wrapped_key  BYTEA       NOT NULL,      -- data key encrypted by KMS; never stored raw
    kms_key_ref  TEXT        NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- Erasure: the row goes, and with it every readable copy of the subject's PII.
DELETE FROM subject_keys WHERE subject_id = 'customer-42';
Make erasure itself an event

Append a PII-free CustomerDataErased after destroying the key. It gives you an auditable record that the request was honoured (when, by whom, under which ticket) and it is the trigger every projection and downstream consumer uses to scrub its own copy. Deleting the key alone does nothing to a read model that already holds plaintext.

Crypto-shredding gotchaMitigation
Key-store backups or KMS soft-delete keep the key alive past the deadlineBackup retention < legal deadline; explicit purge of soft-deleted keys
Encrypted fields can’t be indexed or searchedSearch on projections (plaintext, deletable) or on keyed hashes — but a hash of an email is still personal data
Key lookup on every replay is slowCache keys per projection batch; bulk-fetch by subject
Losing the key store = losing all PIITreat it as tier-0 infra: replicated, backed up (within the retention window)
Is it “erasure” in law?Widely accepted as rendering data unrecoverable, but get your DPO to sign off in the ADR

5. The end-to-end purge map (the Staff part)

The event store is one copy. A Staff engineer owns the data map: every place an event, or something derived from it, comes to rest.

WhereHolds PII asErasure action
Event storeciphertext (or nothing)destroy key / delete stream
Read modelsplaintextprojection handles CustomerDataErased; verify rebuilds yield [erased]
Snapshotsplaintext if state holds PII (it shouldn’t)delete subject’s snapshots; they rebuild from events
Kafka topicswhatever your integration events carrypublish ciphertext or ids only; compacted topics: tombstone the key; otherwise rely on retention < deadline
Backupsfull copiesretention window shorter than the deadline, or documented restore-then-re-erase procedure
Data lake / warehouseoften raw event dumpsingest decrypted-at-source fields as separate deletable columns, or keep ciphertext
Logs, DLQ, caches, searchaccidental plaintextdon’t log payloads; TTLs; erasure handler in each
Snapshot trap

A snapshot is serialised aggregate state. If you decrypted PII into state, the snapshot holds it in plaintext and survives key deletion. Keep PII out of aggregate state entirely — deciders rarely need an email to enforce an invariant.

6. Temporal queries: two different “whens”

Event sourcing gives you time travel for free — but there are two clocks, and mixing them up produces subtly wrong answers in HR, insurance, payroll and finance.

QuestionTime axisComes from
“What did we know on 1 March?”System time (as-of, transaction time)recorded_at / global position — free with ES
“What was true on 1 March?”Valid time (business, effective time)an explicit effectiveFrom in the payload — you must model it

A retroactive event is one recorded today but effective in the past. That’s where the axes split apart:

-- As-of (system time): what did we KNOW at :as_of?
SELECT event_type, data
FROM   events
WHERE  stream_id = 'employee-E7' AND recorded_at <= :as_of
ORDER  BY stream_version;

-- Valid time, as known now: what WAS the salary on :on_date?
SELECT (data->>'amount')::numeric AS salary
FROM   events
WHERE  stream_id = 'employee-E7' AND event_type = 'SalaryChanged'
  AND  (data->>'effectiveFrom')::date <= :on_date
ORDER  BY (data->>'effectiveFrom')::date DESC, stream_version DESC
LIMIT  1;

-- Fully bi-temporal: what did we believe on :as_of about :on_date?  Add both predicates.

These raw queries are fine for an audit tool or a test. For request-path reads, build a bi-temporal projection: a table with valid_from, valid_to, recorded_from, recorded_to (PostgreSQL tstzrange columns with a GiST index work well). 

public record SalaryChanged(String employeeId, BigDecimal amount,
                            LocalDate effectiveFrom,   // valid time: business decides
                            Instant recordedAt)        // system time: the clock decides
        implements EmployeeEvent {}
Staff differentiator

Most teams discover bi-temporality after an auditor asks “why did the March payslip say 4,000?”. If you put effectiveFrom in the event at design time in HR, insurance (policy endorsements), payroll or pricing domains, you’ve avoided a painful schema-evolution project later. Ask in every design review: “can this fact be back-dated?”

Try it in your own system
  • Grep one of your event schemas (or Kafka topics) for PII: payloads, keys, headers, metadata. List every field.
  • For each field decide: remove (reference an id) or crypto-shred. Justify any field that stays in plaintext.
  • Draw the data map: every store an event lands in. Write the erasure action and owner next to each.
  • Find one fact in your domain that can be back-dated. Does its event carry an effectiveFrom?
