Event Sourcing · Lesson 06

Rebuilds & Living with Eventual Consistency

◷ ~14 min read • Level 2 · The read side • Prereq: Lesson 05

Two things make or break an event-sourced read side in production. First: can you change a projection and rebuild it without downtime? If not, you’ve thrown away one of the main reasons you chose event sourcing. Second: can you answer the product team’s inevitable “I clicked save and the list doesn’t show my change” with a concrete technique rather than a shrug? This lesson gives you both.

1. Changing a projection means rebuilding it

A read model is a pure function of the log: readModel = fold(projectionLogic, allEvents). Change the logic — fix a rounding bug, add a column, split a table — and the existing rows are now the output of the old function. The only correct fix is to re-run the new function over all events. Hand-written UPDATE migrations on a read model are a smell: they produce a state that no version of your code would ever have produced.

Rebuilding in place (truncate, reset checkpoint to 0, replay) works on a laptop. In production it means an empty or half-filled table for minutes or hours. The production pattern is blue/green: build the new version beside the old one, verify it, then swap atomically.

2. The mechanics of a blue/green rebuild

Versioned names everywhere

Name the projection and its storage with a version: orders-summary-v2 → checkpoint row orders-summary-v2 → table rm_orders_v2. That’s what lets two versions coexist. Bump the version for any logic change that alters output; leave it alone for pure refactors.

The swap: Postgres

Postgres DDL is transactional, so a view swap is atomic even if v2 changed the columns:

BEGIN;
DROP VIEW IF EXISTS rm_orders;
CREATE VIEW rm_orders AS SELECT * FROM rm_orders_v2;
COMMIT;
-- CREATE OR REPLACE VIEW also works, but only if v2 keeps v1's columns
-- (same names/types/order; new columns may be appended at the end).

Alternatives: keep each version in its own schema (orders_v1, orders_v2) and swap the API’s search_path, or ALTER TABLE … RENAME both tables inside one transaction.

The swap: OpenSearch / Elasticsearch

Use an index alias; the _aliases API applies remove + add atomically:

POST /_aliases
{ "actions": [
    { "remove": { "index": "orders_v1", "alias": "orders" } },
    { "add":    { "index": "orders_v2", "alias": "orders" } }
] }

Verify before you swap

-- 1. Same population?
SELECT (SELECT count(*) FROM rm_orders_v1) AS v1, (SELECT count(*) FROM rm_orders_v2) AS v2;

-- 2. Rows whose unchanged columns differ (should be empty)
SELECT order_id, customer_id, status FROM rm_orders_v1
EXCEPT
SELECT order_id, customer_id, status FROM rm_orders_v2;

-- 3. Spot-check the columns you DID change, on a random sample
SELECT v1.order_id, v1.total AS old_total, v2.total AS new_total
  FROM rm_orders_v1 AS v1 TABLESAMPLE SYSTEM (1)   -- ~1% of v1's pages
  JOIN rm_orders_v2 AS v2 USING (order_id);

Compare at a moment when both checkpoints are equal (or stop v1 first), otherwise in-flight events show up as false differences.

3. Rebuild speed — and why it is an SLO

Rebuild time is an operational SLO

“How long to rebuild the slowest projection from zero?” Measure it, publish it, alert when it trends up. If the answer is days, you’ve lost one of event sourcing’s main benefits: fixing a read-model bug becomes a multi-day incident, so teams start patching rows by hand — and the read model silently drifts from the log. Typical fixes: faster rebuild techniques above, narrower projections, or closing the books so history is shorter (Lesson 07).

4. Eventual consistency: the product conversation

The #1 objection from product teams: “I clicked save and the list doesn’t show my change.” The lag is real (milliseconds to seconds; much longer during an incident), and “it’s eventually consistent” is not an answer a PM can ship. Staff engineers solve it pragmatically with a menu of techniques:

TechniqueHowTrade-off
Return the result from the commandCommand handler returns new version / computed values; UI updates optimisticallySimplest; covers most cases
Read-your-writes via position tokenCommand returns globalPosition; query passes ?minPosition=…; API waits (bounded, e.g. 2 s) until checkpoint ≥ tokenStrong UX, small latency cost
Inline / synchronous projectionUpdate the critical read model in the same transaction as the append (store and read model share Postgres; Marten calls these “inline projections”)Couples write latency & failures to the projection; fine for 1–2 critical views
Read from the aggregateFor “get by id”, just rehydrate the streamAlways consistent; only works by id
Push to the clientWebSocket/SSE notification when the projection has caught upBest UX, more infrastructure
Design the UI“Your order is being processed”Often the business is fine with it — ask

5. Read-your-writes with a position token

The insight: the global position is a logical clock shared by every projection. If your write landed at position 1,042, then any projection whose checkpoint is ≥ 1,042 has already seen it. So the client carries that number from the command response to the next query. 

// Command side: return the token
public record CommandResult(String streamId, long newVersion, long globalPosition) { }

// Query side: wait (bounded) until the projection has caught up to the caller's write
public OrderView getOrder(String orderId, Optional<Long> minPosition) {
    minPosition.ifPresent(p -> checkpoints.awaitAtLeast("orders-summary-v2", p, Duration.ofSeconds(2)));
    return repo.findById(orderId).orElseThrow(NotFound::new);
}

// A simple, honest implementation
public boolean awaitAtLeast(String projection, long position, Duration timeout) {
    long deadline = System.nanoTime() + timeout.toNanos();
    while (true) {
        Long current = jdbc.queryForObject(
            "SELECT position FROM projection_checkpoints WHERE name = ?", Long.class, projection);
        if (current != null && current >= position) return true;
        if (System.nanoTime() >= deadline) return false;   // caller decides: stale-but-flagged
        LockSupport.parkNanos(Duration.ofMillis(20).toNanos());
    }
}
Details that matter in production
  • Don’t hard-code the projection version in the query path. Resolve “the projection currently behind the rm_orders alias” so a blue/green swap doesn’t silently make you wait on the retired v1.
  • The token is only as good as the checkpoint. If your poller can skip events (the gap problem, Lesson 08), “checkpoint ≥ token” doesn’t prove your event was applied.
  • Polling the checkpoint table from every request is fine at modest QPS; at scale, cache the checkpoint in memory and refresh it from LISTEN/NOTIFY.

6. Inline projections: when consistency must be immediate

When the event store and the read model share one Postgres database, you can update a critical read model in the same transaction as the append. Marten calls these inline projections; the read model is then strongly consistent with the write. 

@Transactional
public CommandResult handle(AddItem cmd) {
    var state  = load(cmd.orderId());
    var events = Order.decide(cmd, state);
    long pos   = store.append(cmd.orderId(), state.version(), events);
    inlineOrderSummary.apply(events, pos);   // same tx: both commit or neither
    return new CommandResult(cmd.orderId(), state.version() + events.size(), pos);
}
You getYou pay
Zero lag for that viewEvery append now waits for the projection’s writes
No position tokens neededA projection bug now fails the command
Simple mental model for the UIRow locks on read-model rows add write contention
Still needs an async path for rebuilds (replaying from 0)

Rule of thumb: inline for one or two views that genuinely need it; async for everything else.

7. Choosing a strategy

SituationReach for
The user needs to see the effect of their own actionReturn the result from the command; optimistic UI
The next screen is a list/search including the user’s changePosition token + bounded wait
A detail page by idRead from the aggregate (rehydrate)
Other users must see changes quickly (dashboards, collaboration)Push (SSE/WebSocket) on checkpoint advance
A single view must be transactionally exact (e.g. available balance shown at checkout)Inline projection
Back-office reports, analyticsPlain eventual consistency — agree the freshness SLO with the business
Ask the business before you engineer

“How stale can this screen be before someone makes a wrong decision?” is a product question. Many teams spend weeks on strong consistency for a report read once a day. Turn the answer into an explicit freshness SLO per read model (“p99 projection lag < 2 s”) and alert on it.
