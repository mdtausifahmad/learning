Event Sourcing · Lesson 08

Subscriptions & the Global-Ordering Gap

◷ ~16 min read • Level 3 · Production engineering • Prereq: Lesson 07

Projections, snapshotters and Kafka publishers all share one hidden dependency: a subscription that hands them every event, in order, exactly as many times as they can cope with. On a home-grown Postgres store, that innocent SELECT … WHERE global_position > :checkpoint hides a bug that skips events forever, silently, under load. Asking “how do you guarantee global ordering and visibility?” in a design review separates people who have run event sourcing in production from people who have read about it.

1. How events reach projections and handlers

ModelDescriptionExamples
Polling catch-upConsumer polls readAll(fromPosition) in a loop, tracks its own checkpointSimple Postgres stores, Marten async daemon
Push catch-upStore pushes from a position; consumer tracks its checkpointEventStoreDB / KurrentDB catch-up subscriptions

LISTEN/NOTIFY + pollPostgres NOTIFY as a wake-up signal, then pollLowers latency of polling

Two axes matter when choosing. Who owns the checkpoint (consumer vs server) decides how you make processing atomic — a consumer-owned checkpoint can live in the read-model database, in the same transaction (Lesson 05). Ordering decides what you can build: projections that fold state need strict order; independent side-effects (send an email per event) can tolerate competing consumers.

2. Exactly one active instance per projection

You run three replicas of your service for availability. If all three run the account-balance-v1 projection, they read the same events, race on the same rows and the same checkpoint, and can apply events out of order: pod A handles #501 while pod B, slightly ahead, already wrote checkpoint 503. Run exactly one active instance per projection (or per partition of a projection); the others stand by. 

// Single active instance per projection using a Postgres advisory lock
boolean leader = jdbc.queryForObject(
    "SELECT pg_try_advisory_lock(hashtext(?))", Boolean.class, projection.name());
if (!leader) return;   // another pod owns it; try again later
The connection-pool trap

pg_try_advisory_lock is a session-level lock: it belongs to the database connection, not your thread. With HikariCP, the JdbcTemplate call above borrows a connection, takes the lock, and returns the connection to the pool — still holding the lock, now owned by whatever request borrows it next. Hold leadership on a dedicated, long-lived connection outside the pool, keep it alive with a heartbeat query, and stop processing immediately if that connection drops (the lock is gone and another pod may already be running). Alternatives: Kubernetes Lease, ShedLock, or the store’s built-in coordination (Marten’s async daemon, Axon’s token claims).

try (Connection leaderConn = DriverManager.getConnection(url, user, pwd)) {   // NOT from the pool
    var ps = leaderConn.prepareStatement("SELECT pg_try_advisory_lock(hashtext(?))");
    ps.setString(1, projection.name());
    try (var rs = ps.executeQuery()) { rs.next(); if (!rs.getBoolean(1)) return; }
    while (running && leaderConn.isValid(2)) {   // lost the session? lost the lock.
        projection.runOnce();                        // its own pooled connections for work
    }
}   // closing the session releases the lock

Lower latency: LISTEN/NOTIFY + poll

Polling every 500 ms adds up to 500 ms of lag; polling every 10 ms hammers the database. Instead, have the append transaction NOTIFY and let workers sleep until woken (or a fallback timeout). Postgres delivers notifications only when the transaction commits, so a wake-up never arrives before the data is visible. 

-- inside the append transaction
SELECT pg_notify('events_appended', '');

// worker loop (pgjdbc)
PGConnection pg = listenConn.unwrap(PGConnection.class);
listenConn.createStatement().execute("LISTEN events_appended");
while (running) {
    pg.getNotifications(1_000);   // block up to 1 s; a missed NOTIFY just means we wait 1 s
    projection.runOnce();         // ALWAYS poll — the notification is a hint, not the data
}

3. The gap problem

With a Postgres IDENTITY/SEQUENCE as the global position, positions are assigned at insert time but become visible at commit time. Transactions commit out of order. Watch what a naive poller does:

4. Fixes used in practice

#FixIdeaTrade-off
1Transaction-id visibility filterOnly read rows written by transactions older than the oldest still-running transactionLag bounded by your longest open transaction
2Gap detection with timeoutOn a hole, wait a few seconds for it to fill; if it doesn’t, assume rollback and skip (Marten’s “high-water mark”)A transaction slower than the timeout is lost
3Serialise appendsSingle writer / lock, so commit order = sequence orderSimple; caps append throughput
4Purpose-built storeKurrentDB/EventStoreDB, Axon Server guarantee a gap-free, commit-ordered $allAnother database to operate

Fix 1 — the transaction-id visibility filter

The events table from Lesson 04 already stores tx_id XID8 DEFAULT pg_current_xact_id() per row. pg_snapshot_xmin(pg_current_snapshot()) is the oldest transaction id still in flight; every transaction below it has finished (committed or rolled back). Read only those rows: 

SELECT * FROM events
 WHERE global_position > :checkpoint
   AND tx_id < pg_snapshot_xmin(pg_current_snapshot())
 ORDER BY global_position
 LIMIT 500;

In the animation, at step 4 Tx A is still in flight, so xmin ≤ A’s id and row 102 (from the younger B) is held back. Nothing is read past the in-flight transaction.

The Staff-level refinement: checkpoint on (tx_id, position)

Transaction ids and sequence values are allocated independently. A transaction with a younger id can still obtain a lower position (e.g. if it inserted its event first). If that older-id transaction commits first, the filter releases its higher position, the checkpoint jumps past it, and the lower one is skipped when it commits. The robust form orders and checkpoints by the pair:

SELECT * FROM events
 WHERE (tx_id, global_position) > (:ckpt_tx, :ckpt_pos)
   AND tx_id < pg_snapshot_xmin(pg_current_snapshot())
 ORDER BY tx_id, global_position
 LIMIT 500;
-- index: CREATE INDEX ix_events_tx_pos ON events (tx_id, global_position);

Every transaction that can still commit has an id ≥ xmin > your checkpoint’s tx_id, so nothing can land behind it. (The simulator above simplifies by assuming ids and positions are allocated in the same order.)

Operational consequence of fix 1: one long-running writing transaction stalls every subscription — even one touching unrelated tables, because transaction ids (and so xmin) are shared across the whole Postgres instance. Set idle_in_transaction_session_timeout and keep reporting jobs off the primary.

Fix 2 — gap detection with a timeout (high-water mark)

// Highest position P such that every position <= P is either visible or declared dead
long highWaterMark(long checkpoint, List<Long> visiblePositions, Clock clock) {
    long hwm = checkpoint;
    for (long p : visiblePositions) {                // sorted ascending
        if (p == hwm + 1) { hwm = p; continue; }     // contiguous: advance
        Instant firstSeen = gaps.computeIfAbsent(hwm + 1, k -> clock.instant());
        if (Duration.between(firstSeen, clock.instant()).compareTo(GAP_TIMEOUT) > 0) {
            log.warn("skipping gap {}..{} (assumed rolled back)", hwm + 1, p - 1);
            hwm = p;                                  // give up on the hole
        } else break;                                 // wait for it to fill
    }
    return hwm;   // projections only read up to here
}

This is conceptually how Marten’s async daemon works: it computes a high-water mark — the highest sequence with no outstanding gaps — and only lets projections advance to it, skipping a gap once it has been stale long enough. The timeout must exceed your longest legitimate append transaction; enforce that with a statement timeout on appends, and alert on every skipped gap.

Fix 3 — serialise appends

BEGIN;
SELECT pg_advisory_xact_lock(42);   -- one appender at a time, released at COMMIT/ROLLBACK
INSERT INTO events (...) VALUES (...);
COMMIT;

The next appender can’t take a sequence value until the previous transaction has committed, so sequence order equals commit order. Rollbacks still leave holes, but no hole can ever be filled later, so a plain > checkpoint poll is safe. Throughput is now bounded by one append transaction at a time — fine for many line-of-business systems, a ceiling for high-volume ones.

Fix 4 — let the store own it

Purpose-built stores (KurrentDB/EventStoreDB, Axon Server) assign the global position at commit, so the $all stream is gap-free and commit-ordered by construction. This is one of the concrete reasons to graduate from a home-grown Postgres store (Lesson 11).

The design-review question

“How is global ordering and visibility guaranteed for your subscribers?” Good answers name one of the four fixes and its operational consequence. “We use a BIGSERIAL” with nothing else is the bug, waiting for load. The same question applies to any table-based outbox polled by sequence — not just event stores.
