Event Sourcing · Lesson 07

Snapshots & Closing the Books

◷ ~14 min read • Level 3 · Production engineering • Prereq: Lesson 06

Every command rehydrates its aggregate by folding the stream. Fifty events: microseconds. Five hundred thousand: your p99 is now a problem. The junior reflex is “add snapshots”. The Staff reflex is to ask first why the stream is that long — and very often the answer is a missing business event that would let you close the books and start a fresh, short stream. This lesson gives you both tools and the judgement to pick between them.

1. The cost you’re fighting: rehydration

Loading an aggregate is readStream(id) + fold(evolve). Its cost grows linearly with stream length: rows read, bytes transferred, JSON deserialised, evolve calls. For most aggregates — an order, a claim, a booking — streams stay in the tens or low hundreds of events and none of this matters. It starts to matter for long-lived entities: a bank account over ten years, a warehouse bin, a loyalty card, an IoT device.

Stream shapeTypical lengthRehydrationAction
Short lifecycle (order, booking, claim)10–200 eventsnegligibleNothing. Don’t snapshot.
Long-lived, natural periods (account, subscription)grows foreverdegrades slowlyClose the books per period
Long-lived, no natural period, read-heavythousands+measurableSnapshot (after measuring)
Very high write rate on one idhuge, fastbad and conflictsRe-model: hot aggregate (§6)

2. Snapshots: a cache of folded state

A snapshot stores the aggregate’s state at version N. Loading becomes: read the snapshot, then fold only the events after N.

Schema

CREATE TABLE snapshots (
    stream_id       TEXT PRIMARY KEY,
    stream_version  BIGINT NOT NULL,
    schema_version  INT    NOT NULL,   -- snapshot SHAPE version!
    state           JSONB  NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

Loading with a snapshot

static final int CURRENT_SNAPSHOT_SCHEMA = 3;

AccountState load(String streamId) {
    var snap = snapshots.find(streamId)
            .filter(s -> s.schemaVersion() == CURRENT_SNAPSHOT_SCHEMA);   // stale shape? ignore it
    AccountState state = snap.map(Snapshot::state).orElse(Account.INITIAL);
    long from = snap.map(Snapshot::streamVersion).orElse(0L);
    for (var e : store.readStream(streamId, from)) state = Account.evolve(state, e);  // events after 'from'
    return state;
}

Writing snapshots asynchronously

public record Snapshot(String streamId, long streamVersion, int schemaVersion, AccountState state) { }

// A subscriber, like a projection. Runs off the command path.
public void onEvent(EventEnvelope env) {
    if (env.streamVersion() % 500 != 0) return;            // every N events per stream
    AccountState state = load(env.streamId());              // uses the previous snapshot
    jdbc.update("""
        INSERT INTO snapshots (stream_id, stream_version, schema_version, state)
        VALUES (?, ?, ?, ?::jsonb)
        ON CONFLICT (stream_id) DO UPDATE
           SET stream_version = EXCLUDED.stream_version,
               schema_version = EXCLUDED.schema_version,
               state          = EXCLUDED.state,
               created_at     = now()
         WHERE snapshots.stream_version < EXCLUDED.stream_version   -- never go backwards
        """, env.streamId(), state.version(), CURRENT_SNAPSHOT_SCHEMA, json.write(state));
}

Note that load may already be past env.streamVersion() by the time it runs; storing state.version() (not the triggering event’s version) keeps the snapshot honest.

3. Five Staff-level rules for snapshots

#RuleWhy it matters
1Snapshots are a cache, never a source of truth.Delete them all and the system must still work (slower). No business logic may read them except load.
2Don’t add them until you measure a need.Many aggregates never exceed ~100 events. A premature snapshot is one more schema to version, test and migrate.
3Version the snapshot schema.When state changes shape, ignore old snapshots and rebuild from events. Otherwise you deserialise yesterday’s shape into today’s record and get silent nulls.
4Take snapshots asynchronously.Every N events, by a background process — don’t add a write to the command path.
5Huge streams? First question the aggregate boundary.“Snapshot because the stream is big” often means “you missed a lifecycle event” (§4).
The bug that rule 3 prevents

You add overdraftLimit to AccountState. Old snapshots deserialise with overdraftLimit = null (or 0) — but the events that set it were folded into the snapshot and are now skipped. Commands run against a state no replay would ever produce. Bump CURRENT_SNAPSHOT_SCHEMA with every shape change and let stale snapshots fall through to full replay; the background snapshotter will refresh them.

4. Closing the books

Accountants close the books every period and carry the balance forward. They don’t open a ten-year ledger to answer “what’s the balance today?”. Do the same: model the period end as a real business event, and start a new stream for the next period whose first event carries the opening state.

What you gain

  • Short streams → fast rehydration, no snapshots needed, and no snapshot schema to version.
  • Archiving: closed streams are immutable and read-only, so they can move to cheap storage (S3/Glacier-class object storage) while remaining replayable for audits and rebuilds.
  • Better domain language: “year-end close”, “shift handover”, “billing cycle closed” are things the business already talks about — and often wants to report on.

Implementing the hand-over

One command changes one stream. So the close and the open are two steps: the close is decided by the old-period aggregate; a small handler reacts and opens the next period. Making the open idempotent (expected version “no stream”) makes retries safe. 

public sealed interface AccountEvent permits /* … */ AccountingPeriodClosed, AccountingPeriodOpened { }
public record AccountingPeriodClosed(String accountId, Year period, BigDecimal closingBalance) implements AccountEvent { }
public record AccountingPeriodOpened(String accountId, Year period, BigDecimal openingBalance) implements AccountEvent { }

static String streamId(String accountId, Year period) { return "account-" + accountId + "-" + period; }

// Reacts to the close; safe to run twice.
public void on(AccountingPeriodClosed e) {
    Year next = e.period().plusYears(1);
    try {
        store.append(streamId(e.accountId(), next), ExpectedVersion.NO_STREAM,
                     List.of(new AccountingPeriodOpened(e.accountId(), next, e.closingBalance())));
    } catch (ConcurrencyException alreadyOpened) {
        // retry after crash: the next period already exists — nothing to do
    }
}

5. Archiving closed streams

Once a stream is closed, nothing will ever append to it. That gives you options for storage growth:

  • Mark it in the streams table (archived = true) and reject appends to it at the store level.
  • Copy its events to object storage (e.g. Parquet/JSON lines per stream or per period), verify, then delete or detach the hot rows. Partitioning the events table by time or global_position range makes this a cheap DETACH PARTITION.
  • Keep the archive replayable: your rebuild tooling must be able to read archived periods, or new projections can’t backfill history.
Archiving is not deleting

Moving events to cold storage changes where they live, not whether they exist. Removing events for legal reasons (GDPR) is a different problem with different tools — crypto-shredding, covered in Lesson 13.

6. Briefly: hot aggregates

A hot aggregate is a single stream receiving a very high write rate — a global stock counter, a popular auction, a platform-wide “likes” total. You’ll see it first as a high concurrency-conflict rate, then as a long stream. Snapshots don’t help: the problem is contention, not rehydration.

TechniqueHowTrade-off
Split the aggregatePer-shard counters (stock-sku42-shard-0..7); sum in a projectionInvariants across shards become harder
Commutative events, expectedVersion = AnyIf order doesn’t matter (LikeAdded), skip the concurrency checkOnly when no invariant depends on current state
Model it as a queueAccept requests as events, process them sequentially downstreamAsync result; needs a UX for “pending”
In-memory aggregate cacheKeep hot state in memory keyed by stream id, validated by versionNeeds single-writer routing (sticky sessions or a partitioned actor)

Try it in your own system
  • Query your store: SELECT stream_id, count(*) FROM events GROUP BY 1 ORDER BY 2 DESC LIMIT 20; — what does the long tail look like?
  • Add a Micrometer timer around load() and record rehydration p99 per aggregate type. Decide on snapshots from that number, not intuition.
  • For your longest-lived aggregate, name its natural period and sketch the …Closed / …Opened pair.
  • If you do add snapshots: run your test suite once with snapshots truncated before every test. It must stay green.
