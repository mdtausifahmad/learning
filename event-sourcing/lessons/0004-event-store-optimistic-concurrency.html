Event Sourcing · Lesson 04

The Event Store & Optimistic Concurrency

◷ ~16 min read • Level 1 · Core mechanics • Prereq: Lesson 03

Your Decider is pure; something has to remember the facts it produces. An event store is a surprisingly small thing — three operations and one unique constraint — and you can build a production-shaped one on the PostgreSQL you already run. The hard part isn’t storage, it’s concurrency: making sure two decisions made on the same stale state can never both become history.

1. What an event store must do

public interface EventStore {
    /** Atomically append; fail if the stream's current version != expectedVersion. */
    AppendResult append(String streamId, long expectedVersion, List<EventEnvelope> events);

    /** Read one stream in order (for rehydrating an aggregate). */
    List<EventEnvelope> readStream(String streamId, long fromVersion);

    /** Read ALL events across streams in global order (for projections). */
    List<EventEnvelope> readAll(long fromGlobalPosition, int maxCount);
}
OperationUsed byGuarantee it needs
appendCommand handlersAtomic multi-event write + expected-version check
readStreamRehydration (Lesson 03)Events of one stream, in stream-version order
readAllProjections, publishers (Lessons 05, 08, 09)Every event across streams, in a stable global order

Notice what’s missing: no update, no delete, no query(where…). The write side answers one question: “what happened to this stream?” Everything else is a projection.

2. A production-shaped PostgreSQL schema

CREATE TABLE events (
    global_position  BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    event_id         UUID        NOT NULL UNIQUE,          -- idempotency
    stream_id        TEXT        NOT NULL,
    stream_version   BIGINT      NOT NULL,                 -- 1, 2, 3 … per stream
    event_type       TEXT        NOT NULL,
    schema_version   INT         NOT NULL DEFAULT 1,
    data             JSONB       NOT NULL,
    metadata         JSONB       NOT NULL DEFAULT '{}',
    occurred_at      TIMESTAMPTZ NOT NULL,
    recorded_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    tx_id            XID8        NOT NULL DEFAULT pg_current_xact_id(),  -- Lesson 08
    CONSTRAINT uq_stream_version UNIQUE (stream_id, stream_version)      -- optimistic concurrency
);

-- Optional: one row per stream for cheap version checks & stream metadata
CREATE TABLE streams (
    stream_id    TEXT PRIMARY KEY,
    stream_type  TEXT    NOT NULL,
    version      BIGINT  NOT NULL,
    archived     BOOLEAN NOT NULL DEFAULT false
);

-- Events are immutable. Enforce it.
REVOKE UPDATE, DELETE ON events FROM app_user;
ColumnWhy it exists
global_positionTotal order across all streams; projections checkpoint on it.
event_id (UNIQUE)Idempotency: a retried append of the same event fails instead of duplicating.
stream_id, stream_versionIdentity and order within one aggregate’s history.
event_type, schema_versionDeserialisation and upcasting (Lesson 12).
data, metadata (JSONB)Payload vs technical context (Lesson 02).
occurred_at vs recorded_atBusiness time vs store time — they differ for imports and offline clients.
tx_idLets subscribers avoid skipping in-flight transactions — the “gap problem” (Lesson 08).
The index you don’t need to add

A UNIQUE (stream_id, stream_version) constraint is backed by a B-tree index on exactly those columns, so readStream’s WHERE stream_id = ? AND stream_version > ? ORDER BY stream_version is already an index range scan. A separate CREATE INDEX … (stream_id, stream_version) is redundant.

3. The unique constraint is optimistic concurrency

Two tellers both see balance €100 and both try to withdraw €80. With CRUD and no locking you’d end at −€60. Here, each writer says “I decided based on version 2, so my event is version 3”. Only one row can be (account-ACC-1, 3).

4. Play with it

Run it twice. With the check on, the second teller’s append fails and the reload-and-redecide rejects it. With it off, both appends land and the balance goes negative — a lost update: Teller 2’s decision was made on a world that no longer existed. Same code, same rules; only the concurrency control differs.

5. Appending with JDBC

public final class PostgresEventStore implements EventStore {

    private final DataSource ds;
    private final EventSerializer serializer;

    @Override
    public AppendResult append(String streamId, long expectedVersion, List<EventEnvelope> events) {
        String sql = """
            INSERT INTO events (event_id, stream_id, stream_version, event_type, schema_version,
                                data, metadata, occurred_at)
            VALUES (?, ?, ?, ?, ?, ?::jsonb, ?::jsonb, ?)
            """;
        try (var conn = ds.getConnection()) {
            conn.setAutoCommit(false);
            try (var ps = conn.prepareStatement(sql)) {
                long v = expectedVersion;
                for (var e : events) {
                    ps.setObject(1, e.eventId());
                    ps.setString(2, streamId);
                    ps.setLong(3, ++v);                       // expected+1, expected+2, …
                    ps.setString(4, e.eventType());
                    ps.setInt(5, e.schemaVersion());
                    ps.setString(6, serializer.toJson(e.data()));
                    ps.setString(7, serializer.toJson(e.metadata()));
                    ps.setTimestamp(8, Timestamp.from(e.occurredAt()));
                    ps.addBatch();
                }
                ps.executeBatch();
                conn.commit();                                // all events or none
                return new AppendResult(v);
            } catch (SQLException ex) {
                conn.rollback();
                if ("23505".equals(ex.getSQLState())) {       // unique_violation
                    throw new ConcurrencyException(streamId, expectedVersion, ex);
                }
                throw ex;
            }
        } catch (SQLException ex) {
            throw new EventStoreException(ex);
        }
    }

    @Override
    public List<EventEnvelope> readStream(String streamId, long fromVersion) {
        String sql = """
            SELECT * FROM events
             WHERE stream_id = ? AND stream_version > ?
             ORDER BY stream_version
            """;
        // … map rows → EventEnvelope (upcasters run here, Lesson 12)
    }
}
DetailWhy it matters
One transaction for the whole batchA command’s events are all-or-nothing (Lesson 02, rule 6).
Versions computed as expected + iThe stale writer collides on its first row; nothing partial survives.
Map only 23505 to conflictOther SQL errors are infrastructure failures, not retriable conflicts.
Check which constraint firedA violation on event_id means “already appended” (idempotent replay), not a conflict. Inspect the constraint name in production code.
Default READ COMMITTED is enoughThe unique index serialises the competing inserts; no SERIALIZABLE or SELECT … FOR UPDATE needed.

6. The command handler: reload, re-decide, retry

public final class AccountCommandHandler {

    private final EventStore store;
    private final EventMapper mapper;     // domain event <-> envelope
    private final Clock clock;

    public long handle(AccountCommand cmd, CommandMetadata meta) {
        String streamId = "account-" + accountIdOf(cmd);

        return Retry.onConcurrencyConflict(3, () -> {          // retry = reload + re-decide
            var history  = store.readStream(streamId, 0);
            var state    = Account.rehydrate(mapper.toDomain(history));
            long version = history.isEmpty() ? 0 : history.getLast().streamVersion();

            var newEvents = Account.decide(cmd, state, clock);

            return store.append(streamId, version, mapper.toEnvelopes(newEvents, meta)).newVersion();
        });
    }
}

final class Retry {
    static <T> T onConcurrencyConflict(int maxAttempts, Supplier<T> attempt) {
        for (int i = 1; ; i++) {
            try {
                return attempt.get();                           // whole load→decide→append
            } catch (ConcurrencyException e) {
                if (i >= maxAttempts) throw e;                  // surface as 409
                sleepWithJitter(i);                             // small backoff
            }
        }
    }
}
Never retry just the append

Re-sending the same events with a bumped expected version is the classic bug: it bypasses the rules, because those events were decided on stale state. A retry must re-run the whole load → fold → decide → append. And keep retries bounded: lots of conflicts on one stream is a design signal (hot aggregate, too-large boundary), not a tuning problem.

7. Expected-version options

Real stores (KurrentDB/EventStoreDB naming shown) offer more than “exact number”:

Expected versionMeaningUse forPostgres implementation
NoStreamStream must not existCreation commands — prevents duplicate createexpected = 0 → insert v1; collides if v1 exists
Exact(n)Stream must be at exactly nNormal commands (the default)insert n+1… as above
StreamExistsMust exist, any versionRareread current max in the same tx; fail if none; append at max+1
AnyNo checkAppend-only facts with no invariants (telemetry) — sparinglyappend at current max+1; retry on 23505
 
public sealed interface ExpectedVersion {
    record NoStream()        implements ExpectedVersion {}
    record Exact(long value) implements ExpectedVersion {}
    record StreamExists()    implements ExpectedVersion {}
    record Any()             implements ExpectedVersion {}
}
Any ≠ safe

Any means “I don’t care what happened since I looked”. That is only true if decide doesn’t look at state at all. If it reads state, Any brings back the lost update you just watched in the simulator.

8. Pushing the version to the client: ETag & If-Match

The handler’s retry catches machine-level races measured in milliseconds. There’s a second race measured in minutes: a user opens an order, goes for coffee, and edits it after a colleague has already changed it. Expose the stream version as an HTTP ETag and require it back as If-Match: 

@GetMapping("/accounts/{id}")
ResponseEntity<AccountView> get(@PathVariable String id) {
    var view = accountViews.find(id);
    return ResponseEntity.ok().eTag("\"" + view.version() + "\"").body(view);
}

@PostMapping("/accounts/{id}/withdrawals")
ResponseEntity<Void> withdraw(@PathVariable String id,
                              @RequestHeader("If-Match") String ifMatch,
                              @RequestBody WithdrawRequest body) {
    long expected = Long.parseLong(ifMatch.replace("\"", ""));
    try {
        // like handle(), but appends with the CLIENT's version and never auto-retries
        long newVersion = handler.handleExpecting(new Withdraw(id, body.amount()), expected);
        return ResponseEntity.noContent().eTag("\"" + newVersion + "\"").build();
    } catch (ConcurrencyException e) {
        return ResponseEntity.status(HttpStatus.PRECONDITION_FAILED).build();         // 412
    }
}
Conflict kindDetected byResponse
Two requests racing in the same instantServer-side expected version from the loadRetry (reload + re-decide); 409 if retries exhausted
User acted on a stale screenClient-supplied If-MatchNo auto-retry; 412 — let the human look again

9. Stream design: what is “one stream”?

  • One stream per aggregate instance (order-123) is the default and the right answer ~95% of the time.
  • Naming: {aggregateType}-{id}. The prefix lets you build category projections (KurrentDB’s $ce-order) or WHERE stream_id LIKE 'order-%'; prefer a separate stream_type column for indexing in Postgres.
  • Keep streams short-lived where the domain allows. A stream that grows forever (inventory-sku-42 with 10M events) is a smell — see “closing the books” in Lesson 07.
  • Stream id = consistency boundary. If two facts must be checked together, they belong to one stream; if not, splitting reduces contention.

Preview of a classic production bug

Identity values are assigned at INSERT, but rows become visible at COMMIT. Transaction A takes position 10, B takes 11; B commits first. A projection reading WHERE global_position > 9 sees 11, checkpoints it, and never sees 10. That’s why the schema carries tx_id. Lesson 08 fixes it properly.
