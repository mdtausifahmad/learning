Event Sourcing · Lesson 10

Sagas, Process Managers & Cross-Aggregate Invariants

◷ ~16 min read • Level 3 · Production engineering • Prereq: Lesson 09 · Publishing & Kafka

The aggregate rule you learned in Lesson 03 — one command changes one aggregate, in one transaction — is what makes event sourcing scale. It is also what makes the business uncomfortable: “reserve stock, take payment, confirm the order” spans three aggregates and maybe three services; “usernames must be unique” spans every user. This lesson gives you the toolkit Staff engineers reach for: process managers vs choreography, compensations, timeouts-as-events, set-validation options, and the newer Dynamic Consistency Boundary — plus the judgement to know which to use.

1. Two ways to coordinate: choreography vs process manager

There is no distributed transaction here. A long-running business process is a sequence of local transactions, each on one aggregate, glued together by events. When a later step fails, earlier steps are undone by compensating actions, not rollbacks. The pattern is usually called a saga; there are two ways to drive it.

ChoreographyProcess manager (orchestration)
ShapeEach service reacts to events with commands (event → command)A stateful coordinator receives events and issues commands
Where the flow livesImplicit, smeared across servicesExplicit, in one place you can read and test
Good for2–3 steps, few failure pathsBranching, compensations, timeouts, “what state is order 42 in?”
RiskCyclic dependencies; nobody can answer “where is it stuck?”Coordinator becomes a god object if it starts holding domain rules
StateNone (or scattered)Its own — ideally event-sourced
Process manager ≠ aggregate

A process manager tracks where the process is (“awaiting payment, timeout at 14:05”); it should not decide domain rules. Inventory decides if stock can be reserved; Payment decides if a card can be charged. The process manager only reacts to their decisions. If your coordinator is computing discounts, it has swallowed an aggregate.

3. The process manager is a decider too

A process manager is an excellent candidate for event sourcing itself: its state (AwaitingPayment, pending timeout) must survive restarts and deploys, and its history is the perfect debugging trail for “why was order 42 cancelled?”. Model it with the same decide/evolve shape as an aggregate — except its inputs are events from others and its outputs are commands to others. 

sealed interface FulfilmentInput permits OrderPlaced, StockReserved, StockUnavailable,
        PaymentCaptured, PaymentFailed, PaymentTimeoutElapsed {}
record OrderPlaced(UUID orderId, Money total, List<Line> lines) implements FulfilmentInput {}
record StockReserved(UUID orderId, UUID reservationId)          implements FulfilmentInput {}
record StockUnavailable(UUID orderId)                           implements FulfilmentInput {}
record PaymentCaptured(UUID orderId, UUID paymentId)            implements FulfilmentInput {}
record PaymentFailed(UUID orderId, String reason)               implements FulfilmentInput {}
record PaymentTimeoutElapsed(UUID orderId)                      implements FulfilmentInput {}

sealed interface Outgoing permits ReserveStock, CapturePayment, ScheduleTimeout,
        ReleaseStock, ConfirmOrder, CancelOrder, RefundPayment {
    UUID commandId();                     // deterministic → receivers can dedupe
}

sealed interface FulfilmentState {
    record NotStarted()                                                     implements FulfilmentState {}
    record AwaitingStock(UUID orderId, Money total, List<Line> lines)       implements FulfilmentState {}
    record AwaitingPayment(UUID orderId, Money total, UUID reservationId)   implements FulfilmentState {}
    record Completed(UUID orderId)                                          implements FulfilmentState {}
    record Cancelled(UUID orderId, String reason)                           implements FulfilmentState {}
}

final class OrderFulfilment {
    private record Step(FulfilmentState s, FulfilmentInput in) {}

    /** decide: which commands to issue. Pure, no I/O. */
    static List<Outgoing> react(FulfilmentState state, FulfilmentInput input) {
        return switch (new Step(state, input)) {
            case Step(NotStarted n, OrderPlaced p) ->
                List.of(new ReserveStock(id(p.orderId(), "reserve"), p.orderId(), p.lines()));
            case Step(AwaitingStock a, StockReserved r) -> List.of(
                new CapturePayment(id(a.orderId(), "capture"), a.orderId(), a.total()),
                new ScheduleTimeout(id(a.orderId(), "pay-timeout"), a.orderId(), Duration.ofMinutes(15)));
            case Step(AwaitingStock a, StockUnavailable u) ->
                List.of(new CancelOrder(id(a.orderId(), "cancel"), a.orderId(), "OUT_OF_STOCK"));
            case Step(AwaitingPayment w, PaymentCaptured c) ->
                List.of(new ConfirmOrder(id(w.orderId(), "confirm"), w.orderId()));
            case Step(AwaitingPayment w, PaymentFailed f)         -> compensate(w, "PAYMENT_FAILED");
            case Step(AwaitingPayment w, PaymentTimeoutElapsed t) -> compensate(w, "PAYMENT_TIMEOUT");
            case Step(Cancelled c, PaymentCaptured late) ->          // money arrived after we gave up
                List.of(new RefundPayment(id(c.orderId(), "refund"), late.paymentId()));
            default -> List.of();     // duplicate, late or irrelevant input → no-op (idempotent)
        };
    }

    /** evolve: next state. Pure, deterministic. */
    static FulfilmentState evolve(FulfilmentState state, FulfilmentInput input) {
        return switch (new Step(state, input)) {
            case Step(NotStarted n, OrderPlaced p)          -> new AwaitingStock(p.orderId(), p.total(), p.lines());
            case Step(AwaitingStock a, StockReserved r)     -> new AwaitingPayment(a.orderId(), a.total(), r.reservationId());
            case Step(AwaitingStock a, StockUnavailable u)  -> new Cancelled(a.orderId(), "OUT_OF_STOCK");
            case Step(AwaitingPayment w, PaymentCaptured c) -> new Completed(w.orderId());
            case Step(AwaitingPayment w, PaymentFailed f)   -> new Cancelled(w.orderId(), "PAYMENT_FAILED");
            case Step(AwaitingPayment w, PaymentTimeoutElapsed t) -> new Cancelled(w.orderId(), "PAYMENT_TIMEOUT");
            default -> state;
        };
    }

    private static List<Outgoing> compensate(AwaitingPayment w, String reason) {
        return List.of(new ReleaseStock(id(w.orderId(), "release"), w.reservationId()),
                       new CancelOrder(id(w.orderId(), "cancel"), w.orderId(), reason));
    }

    private static UUID id(UUID orderId, String step) { return Uuids.v5(orderId, step); }
}

Note the Cancelled + PaymentCaptured case. A naive “ignore everything after cancel” default would silently keep a customer’s money. Enumerating late arrivals is where most saga bugs hide; the sealed types and record patterns make each combination an explicit, testable decision.

Running it safely

void on(StoredEvent<FulfilmentInput> incoming) {
    var streamId = "fulfilment-" + orderIdOf(incoming.data());
    var history  = store.readStream(streamId);
    if (history.containsCausation(incoming.eventId())) return;          // already handled
    var state    = history.fold(OrderFulfilment.initial(), OrderFulfilment::evolve);
    var commands = OrderFulfilment.react(state, incoming.data());
    // One atomic append: the input we reacted to + the commands we intend to send.
    store.append(streamId, history.version(),
                 toPmEvents(incoming, commands));                       // causationId = incoming.eventId()
}
// A separate dispatcher subscription reads CommandIssued events from PM streams and sends them.
// Crash anywhere → re-sent; receivers dedupe on commandId. Same outbox idea as Lesson 09.
RuleWhy
Every step idempotentAfter a crash the process manager will re-send commands; receivers dedupe on a deterministic commandId
Timeouts are eventsPaymentTimeoutElapsed from a durable scheduler (a scheduled_messages table polled with FOR UPDATE SKIP LOCKED, or your platform’s scheduler) — never an in-memory timer
Compensations are semanticReleaseStock, RefundPayment — new facts, not deletes. Some steps can’t be undone (an email was sent): compensate with another business action
Correlate everythingcorrelationId = order id across all streams; causationId = the event that triggered each command
Order pivot steps lastPut the hardest-to-compensate step (shipping, external payment) as late as possible
Saga smell

If two aggregates need a saga for every operation and you are constantly compensating, the boundary is probably wrong. Sagas are for genuinely independent consistency boundaries (different services, different lifecycles), not a workaround for an aggregate split too finely.

4. Set validation: “usernames must be unique”

This invariant spans all user streams, so no single aggregate can enforce it. You have options; the right one depends on how bad a violation really is.

OptionHowStrengthCost
1. Reservation stream / tableAppend UsernameClaimed to stream username-alice with NoStream, or insert a row in a unique-constraint table in the same transaction as the append (same DB)StrictExtra write; releasing on rename/delete; two-step + compensation if the store can’t append to two streams atomically
2. Check read model, compensate racesQuery a projection; on the rare duplicate, detect and fix (rename prompt, merge)EventualNeeds a detection job + a business process for the fix
3. Single aggregateIf the set is small and bounded (seats on one flight), make the set the aggregateStrictContention on a hot stream; only for small sets
4. Dynamic Consistency BoundaryConditional append over a query (next section)StrictNewer; store support & scaling to evaluate
 
-- Option 1 with a DIY Postgres store: the claim is part of the WRITE model, not a projection.
CREATE TABLE username_claims (
    username  TEXT PRIMARY KEY,          -- store normalised (lower-cased, trimmed)
    user_id   UUID NOT NULL
);

BEGIN;
INSERT INTO username_claims (username, user_id) VALUES (lower(:username), :userId);  -- 23505 → "taken"
INSERT INTO events (event_id, stream_id, stream_version, event_type, data, occurred_at)
VALUES (:eventId, 'user-' || :userId, 1, 'UserRegistered', :data::jsonb, now());
COMMIT;
The Staff move: ask the business

“What happens if two customers briefly share an email?” is a product question before it is a technical one. Often the honest answer is “we’d email support and merge them” — which makes option 2 perfectly acceptable and removes a write-path dependency. Spend strictness where a violation costs money or breaks law, not everywhere.

5. Dynamic Consistency Boundary (DCB) — the newer frontier

Classic event sourcing forces you to choose aggregate boundaries up front; invariants that cross them become sagas or reservation tricks. DCB, introduced by Sara Pellegrini and Milan Savić and documented at dcb.events, drops the fixed “one stream per aggregate” rule:

  • All events live in one log, each carrying tags (course:c1, student:s7).
  • A command handler queries exactly the events relevant to its decision, by type and tag.
  • On append it passes an append condition: fail if any event matching this query was appended after position P (the position it read up to).
// Illustrative Java — API names vary by implementation; concepts follow dcb.events.
var query = Query.anyOf(
    QueryItem.types("CourseDefined", "CourseCapacityChanged", "StudentSubscribedToCourse").tag("course:c1"),
    QueryItem.types("StudentSubscribedToCourse").tag("student:s7"));

var read  = store.read(query);                                  // matching events + last position P
var state = read.events().stream().reduce(SubscriptionState.EMPTY, SubscriptionState::evolve, (a, b) -> b);

if (state.courseFull("c1"))          throw new CourseFull("c1");
if (state.coursesOf("s7") >= 5)      throw new TooManyCourses("s7");

store.append(
    new StudentSubscribedToCourse("s7", "c1").withTags("course:c1", "student:s7"),
    AppendCondition.failIfEventsMatch(query).after(read.position()));   // conflict → re-read, re-decide

This enforces an invariant spanning “course” and “student” without a saga and without a contrived Enrolment super-aggregate. It is genuinely elegant — and it deserves a sober evaluation:

EvaluateQuestion to ask in the spike
MaturityWhich stores implement it, and who runs them in production at your scale? (Axon and others have adopted it; the ecosystem is still young.)
ScalingThe conflict check runs over a query, not one stream key. How does the store make check-then-append atomic (locks per tag, serialisation)? What is throughput under contention?
DIY riskOn a home-grown Postgres store, “nothing matching after P” interacts with the global-ordering gap from Lesson 08. Easy to get subtly wrong.
ModellingWithout aggregates, where do invariants live and how do new engineers discover them? Tag conventions become a contract.
Know it, evaluate it, don’t bet blind

DCB is a strong option to mention and reason about in design reviews and interviews. Do not bet a core system on it without a time-boxed spike that measures contention behaviour and failure modes on your target store.
