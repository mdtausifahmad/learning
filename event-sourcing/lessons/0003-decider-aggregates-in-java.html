Event Sourcing · Lesson 03

The Decider: Aggregates in Java 21

◷ ~16 min read • Level 1 · Core mechanics • Prereq: Lesson 02

You now know what good events look like. The next question is: where do they come from? The modern, testable answer is the Decider pattern — three pure functions that hold all your business rules and know nothing about databases, Spring or Kafka. Get this shape right and your domain tests run in milliseconds, your replays are deterministic, and a new event type is a compiler error until every rule handles it.

1. Three functions, no I/O

Popularised by Jérémie Chassaing, the Decider is the formal version of the equation from Lesson 01: 

initialState : State
decide       : (Command, State) -> List<Event>   // business rules; may reject
evolve       : (State, Event)   -> State         // pure state transition; never throws

Everything with side effects — loading events, appending, clocks, HTTP — lives in a thin application service (the “imperative shell”) wrapped around this “functional core”.

2. The full bank-account Decider

Events and commands: sealed hierarchies of records

public sealed interface AccountEvent permits
        AccountEvent.AccountOpened, AccountEvent.MoneyDeposited,
        AccountEvent.MoneyWithdrawn, AccountEvent.AccountClosed {

    record AccountOpened(String accountId, String ownerId, String currency, Instant at) implements AccountEvent {}
    record MoneyDeposited(String accountId, BigDecimal amount, Instant at)            implements AccountEvent {}
    record MoneyWithdrawn(String accountId, BigDecimal amount, Instant at)            implements AccountEvent {}
    record AccountClosed(String accountId, String reason, Instant at)                 implements AccountEvent {}
}

public sealed interface AccountCommand permits
        AccountCommand.OpenAccount, AccountCommand.Deposit,
        AccountCommand.Withdraw, AccountCommand.CloseAccount {

    record OpenAccount(String accountId, String ownerId, String currency) implements AccountCommand {}
    record Deposit(String accountId, BigDecimal amount)                   implements AccountCommand {}
    record Withdraw(String accountId, BigDecimal amount)                  implements AccountCommand {}
    record CloseAccount(String accountId, String reason)                  implements AccountCommand {}
}

State: only what decide needs

public sealed interface AccountState {
    record NotOpened()                                 implements AccountState {}
    record Open(String accountId, BigDecimal balance)  implements AccountState {}
    record Closed(String accountId)                    implements AccountState {}
}

Modelling state as a sealed type (rather than one class with a status enum and nullable fields) makes illegal states unrepresentable: a NotOpened account simply has no balance to read.

The Decider

public final class Account {

    public static final AccountState INITIAL = new AccountState.NotOpened();
    private static final BigDecimal OVERDRAFT_LIMIT = BigDecimal.ZERO;

    private Account() {}

    public static List<AccountEvent> decide(AccountCommand cmd, AccountState state, Clock clock) {
        var now = clock.instant();
        return switch (cmd) {
            case AccountCommand.OpenAccount c -> switch (state) {
                case AccountState.NotOpened n -> List.of(
                        new AccountEvent.AccountOpened(c.accountId(), c.ownerId(), c.currency(), now));
                default -> throw new DomainException("Account already exists");
            };
            case AccountCommand.Deposit c -> {
                var open = requireOpen(state);
                requirePositive(c.amount());
                yield List.of(new AccountEvent.MoneyDeposited(open.accountId(), c.amount(), now));
            }
            case AccountCommand.Withdraw c -> {
                var open = requireOpen(state);
                requirePositive(c.amount());
                if (open.balance().subtract(c.amount()).compareTo(OVERDRAFT_LIMIT.negate()) < 0) {
                    throw new DomainException("Insufficient funds");
                }
                yield List.of(new AccountEvent.MoneyWithdrawn(open.accountId(), c.amount(), now));
            }
            case AccountCommand.CloseAccount c -> {
                var open = requireOpen(state);
                if (open.balance().signum() != 0) throw new DomainException("Balance must be zero to close");
                yield List.of(new AccountEvent.AccountClosed(open.accountId(), c.reason(), now));
            }
        };
    }

    /** Pure. Never validates, never throws for business reasons: the event already happened. */
    public static AccountState evolve(AccountState state, AccountEvent event) {
        return switch (event) {
            case AccountEvent.AccountOpened e  -> new AccountState.Open(e.accountId(), BigDecimal.ZERO);
            case AccountEvent.MoneyDeposited e -> {
                var o = (AccountState.Open) state;
                yield new AccountState.Open(o.accountId(), o.balance().add(e.amount()));
            }
            case AccountEvent.MoneyWithdrawn e -> {
                var o = (AccountState.Open) state;
                yield new AccountState.Open(o.accountId(), o.balance().subtract(e.amount()));
            }
            case AccountEvent.AccountClosed e  -> new AccountState.Closed(e.accountId());
        };
    }

    public static AccountState rehydrate(List<AccountEvent> history) {
        AccountState s = INITIAL;
        for (var e : history) s = evolve(s, e);
        return s;
    }

    private static AccountState.Open requireOpen(AccountState s) {
        if (s instanceof AccountState.Open o) return o;
        throw new DomainException("Account is not open");
    }

    private static void requirePositive(BigDecimal amount) {
        if (amount.signum() <= 0) throw new DomainException("Amount must be positive");
    }
}

Note the cast (AccountState.Open) state in evolve. It is not a validation: a MoneyDeposited can only exist because decide already checked the account was open. If that cast ever fails during replay, you have a bug or a broken migration, not a business error — and failing loudly is exactly right.

Pure ⇒ Given/When/Then tests

Because both functions are pure, a test is just data in, data out:

class AccountTest {

    static final Clock CLOCK = Clock.fixed(Instant.parse("2026-10-22T10:00:00Z"), ZoneOffset.UTC);
    static final Instant T = CLOCK.instant();

    List<AccountEvent> given(AccountEvent... history) { return List.of(history); }

    List<AccountEvent> when(List<AccountEvent> history, AccountCommand cmd) {
        return Account.decide(cmd, Account.rehydrate(history), CLOCK);
    }

    @Test
    void withdraw_within_balance_emits_MoneyWithdrawn() {
        var history = given(
                new AccountOpened("ACC-1", "u-1", "EUR", T),
                new MoneyDeposited("ACC-1", new BigDecimal("100"), T));

        assertThat(when(history, new Withdraw("ACC-1", new BigDecimal("50"))))
                .containsExactly(new MoneyWithdrawn("ACC-1", new BigDecimal("50"), T));
    }

    @Test
    void withdraw_beyond_balance_is_rejected() {
        var history = given(new AccountOpened("ACC-1", "u-1", "EUR", T));

        assertThatThrownBy(() -> when(history, new Withdraw("ACC-1", BigDecimal.ONE)))
                .isInstanceOf(DomainException.class)
                .hasMessage("Insufficient funds");
    }
}

Read those tests aloud: given these facts, when this command, then these facts (or this rejection). That is a spec a product owner can review. Lesson 14 scales this up.

Minimal state

The state holds only fields needed to enforce invariants. ownerName, transactionHistory, lastLoginAt — none of those protect a rule, so they belong in read models. A classic smell is an aggregate state class that looks like the API response DTO. If you need a field to display something, project it; if you need it to decide something, keep it.

evolve never throws (for business reasons)

decideevolve
Inputcommand + statestate + event
Contains rules?Yes — all of themNo — only transitions
May reject?Yes (DomainException / result type)Never — the event is a fact
Runs during replay?NoYes, for every event, forever
Changing its logicAffects future decisions onlyChanges how all of history is interpreted
The rule that moves into evolve

A common mistake: someone adds if (amount > limit) throw inside evolve after the limit is lowered. Now every account that legally withdrew above the new limit in 2024 can’t be loaded. Rules go in decide; history is never re-judged.

Injected clock

decide receives a java.time.Clock rather than calling Instant.now(). The same applies to id generators and anything random: inject them, or pass the values in on the command. evolve takes time only from the event (e.at()), never from a clock.

Sealed exhaustiveness

Add record AccountFrozen(…) implements AccountEvent {} to the permits list and every switch (event) without a default branch stops compiling until it handles the new case. That is why the code avoids default -> on event switches: a default turns a compile error into a silent replay bug.

5. Making the shape explicit: a generic Decider

Many teams capture the pattern as a type, so infrastructure (handlers, test fixtures, snapshotting) can be written once for every aggregate: 

public record Decider<C, S, E>(
        S initialState,
        BiFunction<C, S, List<E>> decide,
        BiFunction<S, E, S> evolve,
        Predicate<S> isTerminal) {

    public S fold(List<E> events) {
        S s = initialState;
        for (E e : events) s = evolve.apply(s, e);
        return s;
    }
}

// wiring the bank account
Decider<AccountCommand, AccountState, AccountEvent> account = new Decider<>(
        Account.INITIAL,
        (cmd, state) -> Account.decide(cmd, state, clock),
        Account::evolve,
        s -> s instanceof AccountState.Closed);

6. The OO alternative (Axon / Vernon style)

The classic object-oriented shape — seen in Axon Framework and Vaughn Vernon’s Implementing Domain-Driven Design — is equivalent: methods for commands, an apply that mutates fields, and a list of uncommitted changes the repository saves. 

public class AccountAggregate {
    private String id;
    private BigDecimal balance = BigDecimal.ZERO;
    private boolean open;
    private long version;
    private final List<AccountEvent> uncommitted = new ArrayList<>();

    public void withdraw(BigDecimal amount, Clock clock) {      // "decide"
        if (!open) throw new DomainException("Account is not open");
        if (balance.compareTo(amount) < 0) throw new DomainException("Insufficient funds");
        raise(new MoneyWithdrawn(id, amount, clock.instant()));
    }

    private void raise(AccountEvent e) { apply(e); uncommitted.add(e); }

    void apply(AccountEvent e) {                                  // "evolve", mutating
        switch (e) {
            case AccountOpened o  -> { id = o.accountId(); open = true; }
            case MoneyDeposited d -> balance = balance.add(d.amount());
            case MoneyWithdrawn w -> balance = balance.subtract(w.amount());
            case AccountClosed c  -> open = false;
        }
        version++;
    }

    public List<AccountEvent> uncommittedChanges() { return List.copyOf(uncommitted); }
    public void markCommitted() { uncommitted.clear(); }
}
Functional DeciderOO aggregate
StateImmutable recordsMutable fields
Output of a commandReturned List<Event>Accumulated in uncommittedChanges

Both are industry standard. Pick one style per codebase and document it; mixing them is what hurts. This course uses the Decider because it’s easier to test and reason about.

7. Aggregate = consistency boundary

An aggregate is not “an entity with events”. It is the unit of transactional consistency: everything inside it is checked and changed atomically by one decide and one append to one stream. Anything outside is eventually consistent.

Design choiceToo bigToo smallRight-sized
SymptomMany concurrency conflicts, huge streamsInvariants need cross-stream transactionsEach command touches one stream
ExampleCustomer holding all ordersOrderLine as its own aggregateOrder containing its lines
HeuristicDraw the boundary around the invariant, not the noun. “What must be true immediately after this command?”
Staff instinct

When someone asks for a rule spanning many aggregates (“usernames must be unique”, “total stock across warehouses ≥ 0”), the answer is rarely “make the aggregate bigger”. Ask the business how often it is violated and what it costs; usually a reservation, a dedicated uniqueness table, or a compensating process is cheaper. Lesson 10 covers the options, including Dynamic Consistency Boundaries.

Try it in your own system
  • Implement the Account decider plus an in-memory store (Map<String, List<AccountEvent>> with a version check). Write three Given/When/Then tests.
  • Model a shopping cart: CartCreated, ItemAdded, ItemRemoved, CartCheckedOut. Invariants: no changes after checkout; max 50 items. What is the minimal state?
  • Add AccountFrozen to the sealed interface and watch the compiler list every place to update.
  • Pick an entity at work and write its invariants first; then draw the aggregate boundary around them.
