Event Sourcing · Lesson 09

Publishing: Integration Events & Kafka

◷ ~15 min read • Level 3 · Production engineering • Prereq: Lesson 08 · Subscriptions & the gap

Your event store now holds the truth, and subscriptions can read it reliably. The next question every real system faces is: how do other teams find out? This lesson is where most event-sourced systems either stay clean or quietly turn into a distributed monolith. You’ll learn to make commands safe to retry, to separate private domain events from a public integration contract, to publish to Kafka without dual writes, and to give a crisp, defensible answer to the Staff-interview favourite: “Can Kafka be my event store?”

1. Idempotency starts on the command side

Clients retry. Load balancers retry. Users double-click. Your mobile app re-sends a request after a flaky 4G timeout that actually succeeded. If a retried command appends the same facts twice, every downstream consumer — projections, Kafka, other services — will faithfully process the duplicate. Fix it at the source, with three complementary tools:

Command kindTechniqueWhat happens on retry
Create (OpenAccount)Client-supplied id + expectedVersion = NoStreamSecond append finds the stream exists → fails safely; return the existing resource
Any other (Withdraw)Idempotency-Key header stored with the result (event metadata or a dedupe table)Key already seen → return the original response, append nothing
Every appendDeterministic eventId = UUIDv5(commandId + index)Retried insert hits UNIQUE(event_id) → no duplicate fact, even if the first attempt’s response was lost

The last one is the cheapest and most underused. A random UUID.randomUUID() per attempt makes every retry look like a new fact; a name-based UUIDv5 makes the same command always produce the same event ids. Java’s standard library only ships v3 (MD5) via UUID.nameUUIDFromBytes, so v5 (SHA-1) is a ten-line helper: 

public final class Uuids {
    // Any fixed UUID works as a namespace; keep it constant forever.
    private static final UUID EVENT_NS = UUID.fromString("6f1c2b1e-5a8e-4c43-9a43-0b7d6a7d9e10");

    public static UUID v5(UUID namespace, String name) {
        try {
            var sha1 = MessageDigest.getInstance("SHA-1");
            sha1.update(toBytes(namespace));
            byte[] h = sha1.digest(name.getBytes(StandardCharsets.UTF_8));
            h[6] = (byte) ((h[6] & 0x0f) | 0x50);   // version 5
            h[8] = (byte) ((h[8] & 0x3f) | 0x80);   // IETF variant
            var bb = ByteBuffer.wrap(h, 0, 16);
            return new UUID(bb.getLong(), bb.getLong());
        } catch (NoSuchAlgorithmException e) { throw new IllegalStateException(e); }
    }

    public static UUID eventId(UUID commandId, int index) {
        return v5(EVENT_NS, commandId + ":" + index);
    }

    private static byte[] toBytes(UUID u) {
        return ByteBuffer.allocate(16).putLong(u.getMostSignificantBits())
                                      .putLong(u.getLeastSignificantBits()).array();
    }
}
One unique-violation, two meanings

With deterministic ids, Postgres error 23505 can now mean two different things. A clash on uq_stream_version is a genuine concurrency conflict (reload and retry the decision). A clash on the event_id constraint is a duplicate command — treat it as success and return the original result. Inspect the constraint name (PSQLException.getServerErrorMessage().getConstraint()) instead of mapping every 23505 to ConcurrencyException.

-- Idempotency-Key store for non-create commands (same transaction as the append)
CREATE TABLE command_dedupe (
    idempotency_key  TEXT        PRIMARY KEY,
    stream_id        TEXT        NOT NULL,
    result_version   BIGINT      NOT NULL,
    response         JSONB       NOT NULL,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now()
);

2. Domain events vs integration events

This is one of the most important — and most commonly botched — distinctions in the whole course. Your event store is optimised for you: fine-grained facts shaped exactly for rebuilding your aggregate’s state. Other teams need something else: a small number of stable, coarse, well-documented facts they can build on for years.

Domain events (internal)Integration events (public)
AudienceYour own bounded contextOther teams / services
Stored inEvent store (source of truth)Kafka topic / broker
GranularityFine (ItemAddedToCart)Coarse, stable (OrderSubmitted with full summary)
Change frequencyEvolves with your modelVersioned contract; changes need consumer coordination
ContainsExactly what’s needed to rebuild stateWhat consumers need (often enriched)
Typical formatJSON/JSONB (debuggable, weak schema)Avro / Protobuf + schema registry (enforced contract)

The translator is just another subscription with a pure mapping function at its core:

sealed interface OrderEvent permits ItemAdded, ItemRemoved, ShippingAddressSet,
                                    DiscountApplied, OrderSubmitted {}

/** Public, versioned contract. Lives in a shared schema module, NOT in the domain package. */
record OrderSubmittedV1(String orderId, String customerId, List<Line> lines,
                        String currency, String totalAmount, Address shipTo, Instant submittedAt) {}

final class OrderIntegrationTranslator {
    private final OrderReadModel orders;   // enrichment from our own projection

    Optional<OrderSubmittedV1> translate(StoredEvent<OrderEvent> e) {
        return switch (e.data()) {
            case OrderSubmitted s -> {
                var o = orders.get(s.orderId());                 // full summary for consumers
                yield Optional.of(new OrderSubmittedV1(s.orderId(), o.customerId(), o.lines(),
                        o.currency(), o.total().toPlainString(), o.shipTo(), e.occurredAt()));
            }
            case ItemAdded a          -> Optional.empty();       // internal detail: not published
            case ItemRemoved r        -> Optional.empty();
            case ShippingAddressSet a -> Optional.empty();
            case DiscountApplied d    -> Optional.empty();
        };
    }
}

Because the switch is exhaustive over a sealed interface, adding a new domain event forces a compile-time decision: is this public? That’s exactly the conversation you want to be forced to have. One subtlety: enrichment from a projection must read a model that is at least as fresh as the event you are translating (e.g. an inline projection, or state carried in the event itself) — otherwise you publish stale summaries.

Anti-pattern: publishing the raw event store to the company

It feels efficient: “we already have events, just mirror the events table to Kafka with Debezium.” You have now made your internal model a public API. Every rename, every split aggregate, every upcaster becomes a cross-team migration, and consumers start re-implementing your evolve to reconstruct state. Publish integration events through an anti-corruption layer; treat the event store as private as your database schema.

3. No dual writes: the event store is your outbox

The tempting code is two lines, and it is wrong:

store.append(stream, v, events);   // ✅ committed
kafka.send(topic, events);         // 💥 crash, timeout or broker outage here → consumers never hear about it

Two systems, no shared transaction: one write can succeed while the other fails. Flip the order and you get the opposite bug — consumers react to events that were never committed (“phantom messages”). In a CRUD service the fix is the transactional outbox: write an outbox row in the same transaction as the business change, then relay it. In an event-sourced service you get that for free: the event store already is the outbox. A publisher is just a subscription (Lesson 08) that reads the global log from a checkpoint and produces to Kafka.

The producer side

# Kafka producer for the integration publisher
bootstrap.servers=kafka:9092
key.serializer=org.apache.kafka.common.serialization.StringSerializer
value.serializer=io.confluent.kafka.serializers.KafkaAvroSerializer
enable.idempotence=true                     # broker dedupes retries within this producer session
acks=all                                    # required by idempotence; wait for in-sync replicas
max.in.flight.requests.per.connection=5     # <= 5 keeps ordering with idempotence on
retries=2147483647
delivery.timeout.ms=120000
compression.type=zstd
void publishBatch(List<StoredEvent<OrderEvent>> batch) throws Exception {
    var futures = new ArrayList<Future<RecordMetadata>>();
    for (var e : batch) {
        translator.translate(e).ifPresent(msg -> {
            var rec = new ProducerRecord<String, Object>("orders.public", e.streamId(), msg);
            rec.headers().add("eventId", e.eventId().toString().getBytes(UTF_8))
                         .add("traceparent", e.metadata().traceparent().getBytes(UTF_8));
            futures.add(producer.send(rec));
        });
    }
    for (var f : futures) f.get();                      // all acked (or throw → retry batch)
    checkpoints.save("orders-publisher", batch.getLast().globalPosition());
}
Know what the idempotent producer does — and doesn’t

enable.idempotence=true stops the broker from writing duplicates when the producer retries an in-flight send within one producer session (producer id + sequence numbers). It does not help when your publisher process restarts and re-reads from its last checkpoint — that’s a brand-new send. Hence the end-to-end rule: consumers must dedupe on eventId. Kafka transactions don’t remove that need either, because your checkpoint lives in Postgres, not in Kafka.

The consumer side

CREATE TABLE processed_events (
    event_id      UUID        PRIMARY KEY,
    processed_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Inside ONE local transaction with the side effect:
INSERT INTO processed_events (event_id) VALUES (:eventId)
ON CONFLICT (event_id) DO NOTHING;           -- 0 rows → duplicate: skip the side effect
-- … apply side effect (insert payment request, update read model) …
COMMIT;                                      -- then commit the Kafka offset

Partition keyAggregate id (orderId)Per-aggregate ordering survives; parallelism across aggregates
Message idEvent store eventId in a headerStable across re-publishes → dedupe key

4. “Can Kafka be my event store?”

A favourite Staff interview question. The short, defensible answer: Kafka is an excellent event log for distribution, but a poor event store for aggregate write models. The reason is not “Kafka loses data” — it’s that the write model needs two operations Kafka doesn’t offer: read one entity’s history cheaply and append only if nobody else appended first.

RequirementPurpose-built event storeKafka
Read one aggregate’s events quickly✅ indexed by stream❌ a partition holds many aggregates; scan, or keep a separate state store
Optimistic concurrency per aggregate (expectedVersion)✅❌ no conditional append per key
Millions of tiny streams✅❌ topic-per-aggregate doesn’t scale
Infinite retention as source of truth✅⚠️ possible (retention -1, tiered storage), but compaction keeps the latest value per key, not history
Fan-out to many consumers, high throughput⚠️ ok✅ excellent

When it does work

Teams do build event sourcing on Kafka with Kafka Streams: commands are produced to a topic keyed by aggregate id, a single stream task owns each partition, it validates the command against current state held in a local state store (RocksDB, backed by a changelog topic) and emits events. Because exactly one writer processes each partition sequentially, there is no concurrent append to guard against — single-writer-per-partition sidesteps optimistic concurrency. It works, but notice what you just built: a stream index, a concurrency model, rehydration, and rebalancing semantics. You are building an event store yourself, and synchronous “did my command succeed?” responses become an async request/reply problem.

The well-trodden architecture

Event store (Postgres, KurrentDB, Axon Server, DynamoDB…) as the source of truth → publisher subscription → Kafka for integration. Each tool does what it’s best at: the store gives per-stream reads and conditional appends; Kafka gives durable, scalable fan-out to the rest of the company.
