Event Sourcing · Lesson 02

Events, Commands & Designing Good Events

◷ ~15 min read • Level 0–1 · Foundations → Core mechanics • Prereq: Lesson 01

In event sourcing, events are not log lines or integration messages you can tweak next sprint — they are your permanent public contract with the future. Every projection, every replay, every auditor and every downstream team will read them for years. This lesson gives you the vocabulary to talk precisely about them, and the design rules that separate a living domain record from a slow, expensive audit table.

1. The vocabulary, learned cold

Staff-level design reviews go wrong when people use the same word for different things. These are the terms you will use for the rest of the course. Learn them until you can define each in one sentence.

2. Event vs command vs query — the interview trap

“What’s the difference between a command and an event?” sounds trivial and is where many candidates wobble. The cleanest answer is about time, authority and audience:

CommandEventQuery
GrammarImperative: ShipOrderPast tense: OrderShippedQuestion: GetOrder
TimeFuture — a wishPast — a factPresent — a look
Can it fail?Yes, it can be rejectedNo — it already happenedCan fail technically, not by rule
AudienceExactly one intended handler0..N subscribers, unknown to senderOne handler (read side)
Changes state?May cause eventsIs the state changeNever
CouplingSender knows the receiverPublisher doesn’t know consumersCaller knows the read API
Why the distinction matters in code

If a consumer can “reject” your event, it wasn’t an event — it was a command in disguise, and you just built a distributed transaction with no coordinator. When downstream needs a say, model it explicitly: a command they handle, and a new event they emit (ShipmentRefused). Lesson 10 builds sagas on exactly this.

Rule 1 — past tense, business language

Event names are the ubiquitous language made permanent. Ask a domain expert to read only the event names of a stream: InvoiceDrafted → InvoiceIssued → PaymentReminderSent → InvoicePaid tells the story. InvoiceCreated → InvoiceUpdated × 4 tells nothing. Avoid technical verbs (Created / Updated / Deleted / Set) unless they are the business word.

4. Intent, not diffs: the same column, two different facts

A customer’s address changes. In CRUD both cases are UPDATE customer SET address = ?. In the business they are completely different things, and they trigger different behaviour. 

// ❌ Diff-shaped: every consumer must reverse-engineer the business meaning
record CustomerUpdated(String customerId, Map<String, Object> changedFields) implements CustomerEvent {}

// ✅ Intent-shaped: the business fact is the type
record ShippingAddressCorrected(String customerId, Address corrected, String correctedBy) implements CustomerEvent {}
record CustomerRelocated(String customerId, Address newAddress, LocalDate movedOn)      implements CustomerEvent {}

A useful test: could a consumer want to react to one but not the other? If yes, they are two event types. Intent is also what you can never recover later — you can always derive “the address changed” from CustomerRelocated, but never the reverse.

5. Pure apply & historical inputs

Replay runs evolve over years-old events. If evolve reads the clock, a random number, a database or a config table, replay produces a different past than the one that actually happened. So an event must carry everything needed to apply it.

The subtle case is derived values whose derivation can change. VAT is 19% today; in 2027 it might be 21%. If OrderPlaced stores only the net amount and evolve recomputes tax from the current table, every replay silently rewrites historical totals. 

// ❌ evolve depends on a mutable lookup — replay is no longer deterministic
case OrderPlaced e -> state.withTotal(e.net().multiply(taxTable.currentRate(e.country())));

// ✅ the decision captured its inputs; evolve is pure arithmetic over the fact
record OrderPlaced(String orderId, Money net, BigDecimal taxRate, Money tax, Money gross,
                   String taxRuleVersion, Instant placedAt) implements OrderEvent {}

case OrderPlaced e -> state.withTotal(e.gross());
Store in the event…Why
The exchange / tax / discount rate usedTables change; history must not.
The price charged, not the product id aloneThe catalogue price will change next week.
The rule or policy version appliedExplains “why was this approved?” years later.
Not the running balanceDerivable by fold and the derivation (addition) never changes; storing it invites inconsistency.
Don’t overcorrect into fat events

“Self-contained” means enough to apply and to understand the fact, not “copy the entire customer record into every event”. Fat events leak PII into a store you can’t easily delete from (Lesson 13) and couple consumers to fields they shouldn’t use. Carry ids for reference data that is stable; carry values for inputs that can change.

6. CRUD events & granularity

OrderUpdated { status, items, address, total, … } is the most common way teams accidentally build an expensive audit table and call it event sourcing. Symptoms: one event type per aggregate, a status field that consumers switch on, and projections that diff before/after snapshots to work out what happened.

The opposite failure is too fine: OrderLineQuantityFieldSet on every keystroke. The right grain is one event per business fact — something a domain expert would name. When one command produces several facts, emit several events and append them atomically in one call: 

// One command, two facts, one atomic append (same stream, consecutive versions)
case PlaceOrder c -> List.of(
        new OrderPlaced(c.orderId(), c.lines(), net, rate, tax, gross, now),
        new CouponRedeemed(c.orderId(), c.couponCode(), discount, now));

7. The envelope: data vs metadata

Every stored event is wrapped in an envelope. The payload (data) holds the business fact and is what evolve uses. The metadata holds technical context that infrastructure, tracing and auditing need but the domain logic must not depend on.

8. Correlation & causation: drawing the causal graph

Two ids, two different questions. correlationId: “which business flow does this belong to?” — identical for every message spawned by one user request. causationId: “what directly caused this?” — the id of the parent message. The rule is mechanical: when handling message M, every message you emit gets correlationId = M.correlationId and causationId = M.id. 

public record MessageContext(String messageId, String correlationId) {

    /** Metadata for every message emitted while handling this one. */
    public Map<String, String> childMetadata() {
        return Map.of("correlationId", correlationId,
                      "causationId",   messageId);
    }
}
Correlation id vs trace id

They overlap but aren’t the same. A W3C traceparent lives for one distributed trace and is often sampled; a correlationId must survive days-long sagas, retries and replays and is never sampled. Store both: the trace links you to latency data, the correlation links you to the business flow.

Try it in your own system
  • Take the busiest UPDATE endpoint in a service you own. List each distinct reason a user calls it — each reason is a candidate event name.
  • For each candidate, mark which fields could change meaning over time (rates, prices, policies) and must be captured in the event.
  • Check your logs and Kafka headers: do you propagate a correlationId and a causationId? If only one, which question can’t you answer today?
  • Read just your event names aloud to a product owner. Do they recognise the story?
