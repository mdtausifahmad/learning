Event Sourcing · Lesson 11

Choosing an Event Store & Operating It

◷ ~15 min read • Level 3 · Production engineering • Prereq: Lesson 10 · Sagas & invariants

By now you could build an event store on Postgres in a week. The Staff question is different: should you, and what will it cost to run for five years? This lesson gives you a map of the store landscape with honest trade-offs, the metrics that tell you an event-sourced system is healthy (and which ones should page someone), how to stitch one OpenTelemetry trace across asynchronous hops, and the performance and scaling levers you’ll pull — including multi-tenancy and multi-region.

1. The landscape

Every option below can run a serious event-sourced system. They differ in what you own: ordering guarantees, subscriptions, archiving, clustering — and how much new operational and conceptual surface your team takes on.

OptionStrengthsWatch out for
PostgreSQL (DIY or library)Team already knows it; ACID; inline projections in the same DB/transaction; familiar backups & opsYou own ordering/gaps (Lesson 08), subscriptions, archiving. Libraries: Marten (.NET), Emmett (TypeScript), Eventuous (.NET), or your own thin module (~500 LOC + tests)
KurrentDB (formerly EventStoreDB)Purpose-built: streams, gap-free $all, catch-up & persistent subscriptions, server-side projections, expected versionsAnother database to operate and learn; licensing has changed over time — check current terms for the features you need
Axon Framework + Axon Server (Java)Full Java/Spring ecosystem: aggregates, sagas, event processors, snapshots, upcasters; DCB support in recent versionsFramework lock-in shapes your domain code; clustering/enterprise features depend on edition — check current terms
Akka / Apache Pekko Persistence (JVM)Actor-based, high throughput, pluggable journals (Cassandra, JDBC, DynamoDB)Actor-model learning curve; Akka moved to the Business Source Licence in 2022, which led to the Apache Pekko fork — check current terms
DynamoDB / Cosmos DBServerless scale; conditional writes give expectedVersion; DynamoDB Streams / Change Feed for subscriptionsNo global ordering across partitions; per-item size limits; stream retention windows (DynamoDB Streams keeps 24 h) — subscribers must keep up
Kafka (+ Streams)Superb distribution and fan-outNo per-key conditional append or cheap per-stream reads (Lesson 09)
 
// DynamoDB as an event store: PK = streamId, SK = version. The condition IS optimistic concurrency.
var put = PutItemRequest.builder()
    .tableName("events")
    .item(Map.of(
        "streamId", AttributeValue.fromS("order-42"),
        "version",  AttributeValue.fromN(Long.toString(expectedVersion + 1)),
        "type",     AttributeValue.fromS("OrderSubmitted"),
        "data",     AttributeValue.fromS(json)))
    .conditionExpression("attribute_not_exists(streamId)")   // that (PK, SK) must not exist yet
    .build();
// ConditionalCheckFailedException → someone else appended version N+1 first → reload & retry.
Staff heuristic

If your team is new to event sourcing and already runs Postgres, start with Postgres and a thin, well-tested event-store module. You learn the patterns without learning a new database at the same time. Graduate to a dedicated store when you hit concrete limits (throughput, subscription complexity, operational pain) — not before. Keep the store behind an EventStore interface so the switch is a migration, not a rewrite.

-- Lag per projection: in events, and as the age of the oldest unprocessed event.
SELECT c.name,
       (SELECT max(global_position) FROM events) - c.position            AS lag_events,
       now() - (SELECT min(recorded_at) FROM events e
                 WHERE e.global_position > c.position)                  AS lag_age
FROM projection_checkpoints c;
// Micrometer: export lag so Prometheus/Grafana can alert on it.
Gauge.builder("es.projection.lag.events", lagService, s -> s.lagEvents("orders-summary-v2"))
     .tag("projection", "orders-summary-v2")
     .register(meterRegistry);

Timer.builder("es.append.latency").tag("stream_type", "order").publishPercentileHistogram()
     .register(meterRegistry);
Counter.builder("es.append.conflicts").tag("stream_type", "order").register(meterRegistry);
Cardinality trap

Tag metrics by stream type and projection name, never by stream id or aggregate id — that mints one time series per order. Per-stream detail belongs in traces and logs.

3. One trace across asynchronous hops

In a request/response system, trace context flows through HTTP headers automatically. In an event-sourced system the request ends at the append; the interesting work — projections, publishing, downstream consumers — happens later, in other processes. The fix: store correlationId, causationId and the W3C traceparent in event metadata and restore them wherever the event is read. 

private static final TextMapSetter<Map<String, String>> SETTER = Map::put;
private static final TextMapGetter<Map<String, String>> GETTER = new TextMapGetter<>() {
    public Iterable<String> keys(Map<String, String> c) { return c.keySet(); }
    public String get(Map<String, String> c, String key) { return c == null ? null : c.get(key); }
};
private final TextMapPropagator propagator = GlobalOpenTelemetry.getPropagators().getTextMapPropagator();

// Write side: put the current context into the event's metadata.
Map<String, String> metadata = new HashMap<>(Map.of(
        "correlationId", cmd.correlationId(), "causationId", cmd.commandId().toString()));
propagator.inject(Context.current(), metadata, SETTER);

// Read side (projection): new span, LINKED to the origin — it may run long after the request.
Context origin = propagator.extract(Context.root(), event.metadata(), GETTER);
Span span = tracer.spanBuilder("project " + event.type())
        .setSpanKind(SpanKind.CONSUMER)
        .setNoParent()
        .addLink(Span.fromContext(origin).getSpanContext())
        .setAttribute("es.global_position", event.globalPosition())
        .startSpan();
Parent or link?

Use a parent when the work is a direct, timely continuation (publisher → Kafka → consumer). Use a link when processing is decoupled in time or batched (projections, rebuilds): otherwise a rebuild run next year attaches thousands of spans to a trace that closed long ago. Never put traceparent in the event data — it’s operational metadata, not a business fact.

4. Performance & scaling levers

ConcernTechnique
Append throughputBatch appends; keep transactions small; partition the events table (by global_position range or time); avoid hot aggregates
Hot aggregates (thousands of writes/sec on one stream)Split the aggregate (e.g. per-shard counters); use commutative events with expectedVersion = Any; or model it as a queue, not an aggregate
Rehydration latencyShort streams → snapshots → in-memory aggregate cache keyed by stream id and validated by version
Projection throughputBatch writes; parallelise by partition key; COPY/bulk APIs; a separate database for read models
Storage growthArchive closed streams to object storage; compress data; tiered storage
Multi-tenancytenant_id column + row-level security, or schema/database per tenant for isolation and per-tenant rebuilds
Multi-regionUsually a single writer region per aggregate (home region) + async replication; multi-writer needs conflict-free (CRDT-like) event design — avoid unless essential
 
-- Multi-tenancy with row-level security on a shared events table
ALTER TABLE events ADD COLUMN tenant_id TEXT NOT NULL;
ALTER TABLE events ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON events
    USING (tenant_id = current_setting('app.tenant_id'));
-- Per request/transaction:  SET LOCAL app.tenant_id = 'tenant-eu-1';
-- Note: RLS does not apply to the table owner or superusers — run the app as a dedicated role.
Numbers are hypotheses until measured

A single Postgres primary on decent hardware can typically sustain thousands to low tens of thousands of small event appends per second with batching. Use that to sanity-check a design, then load-test with your own payloads, indexes and fsync settings before committing to an architecture or a vendor.
