Distributed Systems Cheat Sheet

Compressed from Lesson 01•Print-friendly
Mindset

Name the guarantee and the failure model before you name a technology. “Strong” and “eventual” are not guarantees; linearizable, causal and convergent are.

The three lenses

PropertyStaff+ question
Reliability — correct despite faultsWhich failures do we assume, detect, mask or accept?
Scalability — handles more load without collapsing costWhich load dimension grows (reads, writes, fan-out, tenants, regions), and what breaks first?
Maintainability — others can operate and evolve it for yearsCan a new team change this without rediscovering hidden invariants?

Schema evolution rules

  • Backward — new code reads old data. Forward — old code reads new data. Rolling upgrades need both.
  • Add only optional fields with defaults — old readers ignore them, new readers default them.
  • Reserve removed tags / names — never reuse an identifier for a different meaning.
  • Semantic compatibility — cents → dollars still parses but breaks every consumer.
  • Compatibility tests in CI — check schemas against the registry before merge.

Partial failure: what “no response” can mean

  • Network — drops, delays, duplicates, reorders, partitions.
  • Process pauses — GC, VM suspension, CPU throttling, page faults; a paused node may still think it holds a lease.
  • Clocks — time-of-day clocks jump (NTP); use monotonic clocks for durations; never assume zero skew.
  • Overload — a slow dependency is indistinguishable from a dead one.
  • Failure model — business systems assume crash/omission; Byzantine tolerance costs far more.

Design-review questions

  • Which invariant needs which guarantee (durability, ordering, idempotency, linearizability, freshness)?
  • What happens mid-upgrade when v1 and v2 producers and consumers coexist?
  • Where is partial failure drawn in the diagram, the tests and the runbook?
  • Is consensus required, or will a lease, queue or idempotent workflow do?
  • What is the replay story — time to rebuild, poison messages, schema drift?
Traps
  • Treating remote calls as local calls with extra latency.
  • Last-write-wins where concurrent edits carry user intent.
  • “Eventually consistent” used to mean “no contract”.
  • 2PC as the default for cross-service consistency.
  • Microservices before data ownership, idempotency and operational maturity.
  • Streams without replay, schema evolution or poison-message handling.
