Design Docs, RFCs & ADRs Cheat Sheet

Compressed from Lesson 05•Print-friendly
Mindset

Writing is how your judgment scales beyond meetings, time zones and your own availability. Make disagreement cheap while change is still cheap.

Pick the right artifact

SituationArtifact
Local, reversible, well understood; no real trade-offsJust write the code
Small change with a few real trade-offsMini design doc (1–3 pages)
Substantial, cross-team, long-term operational impactFull design doc (~10–20 pages)
Proposal that needs wide input and a named decision ownerRFC / tech spec
One architecturally significant decision future readers will ask “why?” aboutADR

Meetings exclude the absent and lose rationale; chat threads fragment; PR-only review arrives too late for architectural trade-offs.

Design doc anatomy

SectionQuestion it answers
Context & scopeWhat world are we operating in?
GoalsWhat must be true when this ships?
Non-goalsWhat are we intentionally not solving?
DesignWhy this shape and not another?
Alternatives consideredDid we fairly explore the decision space?
Cross-cutting concernsSecurity, privacy, observability, reliability, migration, cost?
Rollout & operationsMigration, launch, rollback, ownership — how does it survive production?

Design section must-haves

  • System-context diagram — actors and dependencies.
  • Contracts — APIs, event schemas, interface boundaries.
  • Data — model, storage, ownership, retention.
  • Failure modes — retries, idempotency, backpressure, degradation.
  • Observability — logs, metrics, traces, dashboards, alerts, SLO impact.
  • Trade-offs stated directly and a clear recommendation.

Lifecycle

Create (enough known to frame the problem, before implementation inertia) → Review (dependent owners, security, privacy, SRE, data, operators, constructive dissenters) → Decide → Implement (doc guides milestones; material changes update it or add an ADR) → Maintain → Archive with status and links to code, runbooks, dashboards, ADRs.

RFC template & practices

Template (8 sections)Practice → why
1. Summary · 2. MotivationShort review window → no indefinite debate
3. Goals & non-goals · 4. ProposalExplicit decision owner → no consensus theatre
5. Alternatives · 6. Risks & mitigationsOpen-questions section → unknowns separated from blockers
7. Rollout plan · 8. Open questionsDecision-log link → outcome survives the comment thread

Gather input widely, write alone. Record unresolved disagreement explicitly. Prefer good over perfect: a timely decision beats a beautiful doc that arrives after implementation is entrenched.

ADR anatomy

  • Title — short and specific (“Use managed PostgreSQL for customer configuration”).
  • Status — proposed · accepted · deprecated · superseded.
  • Context — forces, constraints, problem.
  • Decision — the chosen path, in active voice.
  • Consequences — benefits, costs, risks, follow-up obligations.
  • Immutable — timestamped; when the decision changes, write a new ADR that supersedes it. The collection is the Architecture Decision Log. Templates: Nygard, MADR.

Craft: open with SCQA, lead with the answer

ElementExample
SituationSettlement events are emitted from three services
ComplicationConsumers see inconsistent ordering and duplicate reconciliation
QuestionHow do we create one reliable settlement stream?
AnswerAn owned settlement event service with idempotent publication and explicit schemas

Make risk concrete: not “may have scalability issues” but “at 2,000 writes/s the single-writer partition saturates; shard by tenant after milestone two”.

Review comments

GoodBad
Challenges assumptions with evidenceRe-litigates declared non-goals
Separates must-fix from preferenceDemands a favourite technology without context
Names missing stakeholdersBlocks on style, not decision quality
Asks whether it fails safely; ties back to goalsHides disagreement in side channels
Traps
  • A long doc written to avoid making a decision.
  • Treating an RFC as a vote instead of a recommendation plus accountable decision.
  • Omitting non-goals → infinite scope.
  • Security, privacy, observability and migration hidden until late.
  • Editing accepted ADRs instead of superseding them.
  • Polished prose mistaken for clear thinking; diagrams as decoration.
