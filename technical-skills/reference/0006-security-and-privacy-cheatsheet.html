Technical Skills · Reference 06

Security & Privacy Cheat Sheet

Compressed from Lesson 06•Print-friendly
Mindset

Security and privacy are design concerns, not clean-up tasks. Raise them in the design doc, make the safe path the easy path, and fund the work by translating risk into business language.

Design-review questions

  • Exposure — does the design expose data it doesn’t need to?
  • Boundary — is permission checked at the right boundary, per object?
  • Compromise — what happens if a dependency is compromised?
  • Abuse — can requests be replayed, tampered with or enumerated?
  • Logs — do they detect abuse without leaking PII or secrets?

Use it as a checklist, not a substitute for thinking; the worst risks are specific to your domain and trust boundaries.

Identity building blocks

ConceptAnswers / does
AuthenticationWho are you? (password, passkey, SSO, MFA, OIDC)
AuthorizationWhat may you do? (RBAC, ABAC, policy engine, ownership checks)
AccountingWhat did you do? (audit, access logs, change history)
OAuth2Delegated authorization framework
OIDCIdentity layer on OAuth2; standard login claims (ID token)
JWTSigned, self-contained claims; hard to revoke — short expiry, key rotation
SessionServer-side state behind an opaque cookie; easy central revocation
MFAMore than one factor; cuts account-takeover risk

Validate every token: signature (expected algorithm), issuer, audience, expiry — then still run the authorization check.

API controls & secure defaults

ControlPrevents
Input validation (allowlists)Unexpected types, sizes, formats
Output encodingXSS and downstream interpretation bugs
Object-level authorization“Logged in” treated as “may access this record”
Rate limitingBrute force, scraping, accidental overload
Least privilege & CORS disciplineOverbroad access; cross-origin mistakes
Idempotency keysUnsafe retries of mutations
Audit loggingInvisible sensitive actions

Deny by default when policy can’t be evaluated · return sensitive fields only when requested and authorised · make pagination resistant to enumeration · treat internal APIs as hostile.

Five principles

  • Defence in depth — assume one control fails; layer independent ones.
  • Least privilege — narrowest scope, shortest duration.
  • Zero trust — the internal network is not a credential; verify at every boundary.
  • Fail secure — deny on uncertainty or dependency failure.
  • Secure defaults — people under deadline follow defaults.

Crypto & secrets

  • TLS in transit; encryption at rest (disk, DB, object store, or application level).
  • Passwords — bcrypt or Argon2 with unique salts; never SHA-256 alone, never reversible.
  • Use vetted libraries and managed services — no home-grown crypto.
  • Secrets in Vault / KMS / a secret manager; rotate; keys apart from data; never logged; prefer workload identity to long-lived credentials.

ThreatQuestion
SpoofingCan someone pretend to be someone or something else?

DFD elements: external entities, processes, data stores, data flows, trust boundaries. Keep it light enough that teams actually do it.

Privacy checklist

  • Minimise — collect only what is needed, not “might be useful someday”.
  • Purpose limitation and retention limits with real deletion.
  • Access control on PII; pseudonymise for analytics.
  • Data-subject rights (GDPR): access, correction, deletion, portability, objection.
  • Encryption is not privacy — if you can decrypt and use it, you must still govern it.
Traps
  • Authentication treated as authorization.
  • Logging tokens, secrets or unnecessary PII.
  • The internal network as the security boundary.
  • Copying OAuth2/JWT samples without checking issuer, audience, expiry and signature.
  • Rate limits and monitoring added only after abuse.
